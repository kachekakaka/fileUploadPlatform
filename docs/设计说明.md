## D01 模块与入口边界

对应 R01、R10。采用独立的 API Server 与 Worker Runtime 运行角色，核心业务通过 Application Services 组织；CLI 的业务操作通过 REST，后续 SDK 通过公开 REST 调用，Dashboard 只走 REST/SSE。

Core MVP 已确认的落地边界：API 和 Worker 为两个独立进程，CLI 的业务操作只走 REST；准备命令可读写用户指定的作品描述文件，但不访问数据库。Scheduling 的计算、选材与派发循环放在 Worker Runtime，API 只管理规则和查询；多 Worker 通过持久化的触发唯一约束、短期派发所有权和条件提交协调，不增加第三个常驻调度进程。具体目录、接口及实现步骤见 [Core MVP 方案](../archive/方案/20261116-Core-MVP实施方案.md)。

| 模块 | 职责与依赖边界 |
| --- | --- |
| Domain | 领域实体、状态转换及不变量；不依赖 FastAPI、SQLAlchemy、SQLite、httpx 或具体 Adapter |
| Application | 提交、查询、取消、重试及业务流程协调；各入口复用业务语义 |
| Scheduling | 定时规则计算、触发记录生成和到期分发 |
| Execution | Worker、领取、租约、进程监督、取消和恢复 |
| Adapters | 目标平台能力及协议实现；通过独立受监督的执行宿主运行，可替换 |
| Infrastructure | 数据库、文件、进程等外部能力，提供 Repository、Unit of Work 和事务支撑 |
| API / SDK / CLI / Dashboard | 各自入口和呈现，不另造一套业务规则；SDK 与 Dashboard 不直接读库 |

初始代码目录建议仍可在任务书中查阅，实际文件布局随实施方案确定。Core 不依赖旧项目或第三方上传程序；Bilibili 兼容后端如被采用，只处于 Adapter 边界内。

## D02 领域与数据约束

对应 R03—R07。UploadWork、UploadUnit 组织作品与投稿配置，Task、Schedule、ScheduleRun、Attempt 分离生命周期；Account、Asset、TaskAsset、Worker、任务及账号名额的 Lease、Receipt、DomainEvent 承载相应状态。名词含义见 [CONTEXT](../CONTEXT.md)。

- 使用稳定资源标识和带时区的 UTC 时间；初始基线采用 UUID。状态变化经统一规则处理，不允许任意覆盖。
- 同一规则版本、同一计划触发点最多一个 ScheduleRun；一个 ScheduleRun 可关联零个或多个 Task，每个展开投稿及目标按 D04 的共享提交约束去重。一个 Task 最多一个活动 Attempt，一个账号名额最多一个活动 Lease。
- 状态、事件和领取结果按所需原子性提交；不能先对外宣称成功再补关键持久化。
- 数据访问经 Repository 和 Unit of Work 组织，写事务保持短小。网络上传、文件复制或扫描、等待进程等耗时操作不放入数据库写事务。
- 当前持久化使用 SQLAlchemy 2 Core 的表模型、查询与 Unit of Work，以及 SQLite WAL；数据库仅放单主机的可靠本地文件系统，不做跨主机共享。空库初始化已实现，逐连接设置外键、FULL 同步与有限忙等待；已有库校验 schema 和版本，不自动升级。物理结构唯一正文为[数据库实现](../src/upload_platform/infrastructure/database.py)，旧库升级见[待办](待办.md)。

Bilibili 集成首版的数据库承接（2026-11-17 已确认、实施中）：使用新的独立运行目录和数据库，旧 Core 数据库及历史记录原样保留，不迁移、不覆盖或重建旧库；新环境暂不呈现旧库历史。旧库升级继续作为暂缓事项，不随本轮集成隐式开展。确认来源见[集成方案 Q2](方案/20261116-Bilibili集成与自维护方案-v1.2.md#18-审查后逐项确认2026-11-17)。

Bilibili 账号身份（2026-11-17 已确认、实施中）：以平台与经验证的 MID 唯一识别远端账号，同一身份对应唯一 Core Account；account_id 仍作为内部关联标识。昵称或本地名称变化不产生新账号，重复登记不能分裂账号名额与投稿去重记录。确认来源见[集成方案 Q5](方案/20261116-Bilibili集成与自维护方案-v1.2.md#18-审查后逐项确认2026-11-17)。

字段、外键、CHECK、唯一索引及部分索引在对应数据库方案与实际资产中落定，并用真实临时 SQLite 验证；不把候选 SQL 或表名存在当成约束已生效。

Bilibili 账号维护（2026-11-17 技术细化、实施中）：账号手动启用与自动阻塞原因分别保存，维护操作有独立身份、代次和结果，不清除其他原因或覆盖较新的停用。登录/续期先暂停新领取、等已有执行退出，上传只读使用凭据，跨进程维护写入互斥。凭据版本发布与 Core 引用更新按可恢复操作协调，不假设跨文件和数据库原子提交；错 MID 不更换账号身份。新库增加身份唯一约束和维护记录，旧库仍按 Q2 保留。具体见[方案 19.4](方案/20261116-Bilibili集成与自维护方案-v1.2.md#194-凭据维护账号暂停与登录恢复)。

**元数据解析已确认（2026-11-16）**：按[需求 R03](需求说明.md#r03-任务与重复提交)区分整份投稿与分 P 信息。independent 的每个视频按 Work 默认值、UploadUnit 覆盖值、Video 覆盖值的顺序解析独立投稿 metadata；multipart 的整组 metadata 仅按 Work、UploadUnit 解析，视频标题另存为有序分 P 信息，不覆盖整组总标题，单视频简介、标签和封面不进入整组覆盖链。同一 Asset 可在不同单元中复用，各单元按自身模式解析并在预览中明确各字段的作用范围，不误报独立投稿字段在多 P 中已生效。平台映射负责转换和能力校验，不构成额外的用户字段覆盖层；目标不支持的配置在创建 Task 前报错，不静默舍弃。Task 快照分别保留投稿级字段、素材顺序和适用的分 P 标题，提交前预览与创建快照复用同一解析服务，后续编辑不改写既有快照。确认来源见 [Core MVP 方案 Q13](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

## D03 文件引用、接收与清理

对应 R02，取舍见 [ADR 0001](adr/0001-reference-local-upload-files.md)。本地登记保存原文件引用；执行时读取当前路径，不额外复制、冻结内容或比较提交后的变化。网页接收则由平台持有接收中的文件，完整落位后才向任务提供可用素材。

网页接收的初始方向是用操作记录跟踪接收与落位，在受控目录保存未完成文件，并以适用的原子改名和持久写入机制完成落位。对应方案须说明中断和写入失败如何恢复；本地引用不走这套复制暂存过程。任何路径的接收完成都不能替代远端上传成功证据。

Bilibili 文件适配（2026-11-17 技术细化、实施中）：实际打开时仍校验路径准入与可读性，不依赖 Core 先前检查；引用不代表冻结内容。不沿用上游按文件变化复用 checkpoint 的流程，不 glob 扩大上传集合，不生成内容摘要、不复制或删除原件。执行证据以执行身份保存，与媒体 checkpoint 区分。具体见[方案 19.7](方案/20261116-Bilibili集成与自维护方案-v1.2.md#197-文件部署新库与入口)。

TaskAsset 保存素材角色与顺序。清理重新核对 Task、Attempt 和 Recovery 引用，只处理平台拥有且符合条件的文件，保留幂等恢复能力。远程 API 的素材提交不接受任意服务器绝对路径；Core MVP 本机入口的路径准入由下述目录入口及其关联方案约束。

**目录入口已确认（2026-11-16）**：本机普通任务直接登记用户指定的作品目录，无需预先逐个添加目录配置；周期规则保存父目录引用，按 R04 仅枚举直接子目录中的作品。TaskAsset 固定记录本任务采用的目录引用、角色和相对路径；manifest 内路径统一相对于作品目录，API 与 Worker 共用解析器。作品移动后新位置使用新的目录映射，既有 Task 不被 Work 当前位置更新而悄悄改指向，原文件丢失按实际错误处理。内部目录标识不代表用户必须预配白名单。本机 API 仅供可信本机非浏览器客户端，loopback、请求来源与路径准入契约见[方案第 3.4 节](../archive/方案/20261116-Core-MVP实施方案.md#34-部署边界)，不增加目录监视或远程路径读取能力。确认来源见 [Core MVP 方案 Q2 及收尾确认](../archive/方案/20261116-Core-MVP实施方案.md#文档收尾确认)。

**作品身份已确认（2026-11-16）**：按[需求 R04](需求说明.md#r04-定时与队列)以 manifest 中的固定编号识别作品，沿用 UUID 基线，由工具生成并持久保存，不以路径或媒体内容摘要派生。重复准备或登记复用已有合法编号；缺少编号时，先可靠保存再提交登记，保存失败不能以仅内存编号创建资源。同编号重复出现按同一作品处理，移动、改名或复制不产生新身份，不改写既有 Task 的素材引用。描述变化按 R03 的 Q14 直接采用，不检测历史差异或要求确认更新；准备工具契约见[方案 CLI](../archive/方案/20261116-Core-MVP实施方案.md#7-cli-契约)。确认来源见 [Q5、Q14](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

**作品就绪已确认（2026-11-16）**：工具生成编号与准备方声明可上传是两个动作，前者不得自动完成后者。准备方确认素材准备完成后，通过工具可靠保存 manifest 的就绪标记；标记缺失、为否或尚未完整保存时，周期选材不得创建该作品的上传任务，也不得写入已提交记录。就绪声明与 Work 的聚合执行状态分开保存，不把准备完成解释成上传成功；路径、普通文件和可读性检查仍正常执行，不扫描媒体内容判断准备状态。确认来源见 [Core MVP 方案 Q6](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)；具体工具契约由方案承接。

## D04 提交、定时与到期分发

对应 R03、R04。TaskSubmissionService 组织即时、定时、取消、重试、查询和列表。重复提交按请求标识与提交内容判断，不为此读取媒体文件；具体存储结构在方案中确定。

Schedule 带规则版本与 IANA 时区；修改规则只影响后续生成。Evaluator 计算下次触发并物化 ScheduleRun，以规范化 UTC 时刻标识一次触发。Due Dispatcher 按 Q12 以单个作品为派发事务边界，原子提交本作品新建的任务、提交对应关系、触发任务关联及 Event/Outbox，防止并发生成重复或部分任务；整轮不使用覆盖所有作品的大事务。

**周期目录选材已确认（2026-11-16）**：触发时按[需求 R04](需求说明.md#r04-定时与队列)选择新作品，持久化作品与已生成任务的对应关系，不能仅依赖进程内记录或“当前目录是否还有文件”避免重复。下一触发点不把失败任务当作新作品重新提交；原任务仍按重试及恢复规则处理。该跨触发点的重复判定与同一次请求的幂等、同一触发点的去重分开定义，不读取媒体内容来判重。作品身份按 D03，跨规则与跨目标范围按下文 Q7；一轮多任务关系按 Q11。确认来源见 [Core MVP 方案 Q3](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

**投稿提交去重已确认（2026-11-16）**：手动与自动入口经同一 Application 提交服务维护共享投稿对应关系，以作品固定编号、上传单元稳定标识、展开项和目标平台/账号区分实际投稿；multipart 的整组是一个展开项，independent 的每个视频各是一个展开项。入口类型、周期规则 ID、规则版本和触发时刻不属于该业务去重身份，目录移动也不改变身份。共享记录保存当前提交轮次及任务，普通提交通过数据库唯一约束返回或关联当前任务；仅 Q16 的显式再提交可以开启下一轮，不能将业务身份在 tasks 表中设成永久只容许一条历史任务。按需求 R03 的 Q14，不把描述变化加入业务去重身份、不做同作品历史描述差异比较；需要创建的任务直接解析当前描述并持久化快照，已存在的任务保持不变。Task 的排队、运行或终态不因另一入口的重复提交而被重置；共享去重与请求级幂等分别保证业务唯一性和响应重放。确认来源见 [Core MVP 方案 Q7、Q14、Q15、Q16](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

**显式再提交已确认（2026-11-16）**：以当前最新 Task 为操作对象，仅允许已经结束且结果明确的 SUCCEEDED、FAILED、CANCELLED、EXPIRED 进入再提交流程；非终态、RECOVERY_PENDING 和 UNCERTAIN 拒绝，不能按已停止进程就推定结果明确。校验当前描述与目标后，在同一短事务内核对共享记录仍指向该任务、增加提交轮次、创建新 Task 及素材关联、切换当前指针并写入幂等响应和事件；历史 Task/Attempt/Receipt 保留，新任务关联前一任务，使用新的 metadata 快照和执行安排。同一请求标识重放返回同一个新 Task；不同请求并发基于同一旧任务再提交时，只允许一次切换，另一请求返回状态冲突及当前任务，防止双击产生两轮。普通提交及周期触发关联新一轮当前任务而不另开轮次。重新上传与失败重试分开，后者仍在原 Task 下创建 Attempt。确认来源见 [Core MVP 方案 Q16](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

错过时间、夏令时、队列公平性与重试到期规则遵循需求 R04。方案细化计算和事务边界，并用可控时间及并发持久化测试证明这些规则。

**周期补执行已确认（2026-11-16）**：按[需求 R04](需求说明.md#r04-定时与队列)在恢复时将同一规则错过的周期合并为一轮选材，保留计划触发时间与实际处理时间，不能把恢复时间伪装为原计划时间。根据持久化触发进度协调并发恢复和正常调度，补执行采用与正常触发相同的就绪筛选、投稿去重和任务创建原子性；不得因反复重启重复补建任务，也不得把未实际执行的历史周期记成上传成功。迟到窗口按 R04 的 Q9 决定保存为规则配置，以最近一次错过的计划触发点为基准，使用 UTC 时刻差计算实际经过时长，差值等于上限时仍可补执行；超过上限持久化跳过结论并推进到下次计划，不写作品提交对应关系。该窗口约束周期派发，不是已创建任务的上传耗时或排队时限；一次性定时及已经生成的 Task 不自动套用周期合并规则。确认来源见 [Core MVP 方案 Q8、Q9](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

Core MVP 的调度模块范围按[需求 R04](需求说明.md#r04-定时与队列)纳入每日、每周规则及相应目录选材、持久化触发与重启恢复（2026-11-16 Q4 已确认），不实现 Cron。规则管理契约、时间边界和运行归属见[Core MVP 方案](../archive/方案/20261116-Core-MVP实施方案.md)；不得将一份规则与一次实际上传 Task 混为同一生命周期。

本轮规则契约与 Worker 内调度循环已在方案第 4.10、6、7 节落定。触发记录的派发状态独立于上传结果；持久化候选作品清单、逐作品处理结果和带代次的派发所有权，故障后只续做未完成项。派发所有权到期可由新 Worker 接管，旧代次不能提交；它不代表 Adapter 执行资格，不能绕过 D05 的执行恢复检查。规则修改只影响新触发，停用不撤销已物化的触发或已创建任务。

请求幂等与投稿身份去重分开：请求按操作路由、资源与 Idempotency-Key 保存规范化请求及响应，直接比较规范化 JSON，不采用内容摘要算法；同请求返回原响应，不重新读取文件或创建任务。CLI 在发送前可靠保存请求标识与请求体，断线后可重放；投稿记录则决定普通提交是否已有当前任务。字段、重放顺序及保存边界见[方案请求幂等](../archive/方案/20261116-Core-MVP实施方案.md#61-请求幂等与-cli-重放)。

重试按 R04 收尾确认配置持久化：领取创建 Attempt 时递增次数，安全可重试失败在进程退出后写入 RETRY_WAIT 及 next_attempt_at；时间从该次失败确认时计算，不能因重启或规则再次触发提前重试或重置预算。仅在下一次到期且仍有预算时新建 Attempt；永久失败或预算耗尽转 FAILED，结果不明转 UNCERTAIN。具体转换与安全恢复计数见[方案第 5.7 节](../archive/方案/20261116-Core-MVP实施方案.md#57-状态转换与重试)。

**一轮多任务已确认（2026-11-16）**：一个 ScheduleRun 表示一轮选材与派发，可关联零个或多个 Task；通过规则 ID、规则版本与计划触发 UTC 时刻保证触发记录唯一，通过 Q7 保证实际投稿不重复。记录本轮各展开项及任务关联，区分本轮新建任务与去重后关联的已有任务，查询可追踪各任务结果；不能仅以派发完成认定整轮上传成功。多个任务进入队列而非绕过账号名额同时启动，各 Task/Attempt 的结果与重试独立。确认来源见 [Core MVP 方案 Q11](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)；部分作品错误按 Q12 隔离。

**按作品隔离已确认（2026-11-16）**：周期选材先在写事务外校验单个作品及其启用目标，再按作品提交所有本次应新增的 Task 与关联；该作品事务失败时整体回滚，不影响其他作品已提交的任务，也不回滚以往已存在的任务。单个作品的解析、文件校验或可隔离派发错误通过单独的短事务保存到本轮作品处理记录，记录目录定位、可用的作品编号和错误原因；不创建虚假的失败上传 Task，不留下该作品的新提交标记。整轮查询能区分成功派发、作品错误和未执行，修复后仍可重新选取该作品；跨轮去重保留其他作品的既有结果。若数据库或其他共享环境不可用，无法确认回滚或保存结果，则保留已完成进度并停止依赖步骤，将剩余项视为未执行，不能伪称所有错误均已隔离。确认来源见 [Core MVP 方案 Q12](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

**一次性定时过期已确认（2026-11-16）**：将[需求 R04](需求说明.md#r04-定时与队列)的 Q10 迟到配置随该次安排持久保存，任务首轮领取以原定执行时刻加允许迟到时长判定，等于上限仍允许领取，超过上限则将尚未领取执行、无 Attempt 的 QUEUED 任务转为 EXPIRED。过期与领取必须通过条件更新和短事务互斥，过期结果与对应事件原子提交，不为过期任务启动 Adapter 或占用账号名额。EXPIRED 不自动重排；重新安排须保留原过期记录。已经领取、有执行记录或进入恢复的任务仍走既有取消、重试与恢复流程，不以原定时间已过为由覆盖其状态。确认来源见 [Core MVP 方案 Q10](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)；重新安排接口及并发约束见方案第 6 节。

## D05 Worker、执行宿主与恢复

图形登录会话由 Core API 进程内的协调器持有引擎 JobHost 与管道，无需 Worker 监督。mumu 账号页经同机 FastAPI 后端调用限定的 Core 会话接口，终端 CLI 入口也可单独使用。会话沿用 schema v2 的 account_maintenance，非敏感元数据存其 execution JSON，二维码只存内存。恢复时先核验原协调器和执行树，以新代次收尾。已发布的凭据版本可用于收尾，无需重新扫码。字段由[公开契约](../schemas/README.md)维护，交互、取消和真实扫码结果见[界面扫码方案](方案/20261117-mumu界面扫码登录接入方案.md)。

对应 R05、R06。Worker Registry 记录 Worker 身份、主机启动身份、进程身份、角色、心跳和状态。领取时，在同一个短事务内核对到期任务、账号与名额，创建 Attempt、取得任务及账号名额 Lease、递增执行代次令牌并写入状态与事件。

B18 专用部署从本机配置载入清单。创建任务的写事务核对作品和名额，将本轮编号写入冻结快照。受控 Worker 领取带该标记的任务，并在交接事务中按当前清单核对账号、构建、作品目录、有序素材和最终投稿字段。多 P 在创建及交接两处都要求同轮单 P 已有可信回执，且最新独立回查成功。普通部署继续按引擎能力接单。[B18 准入与验证](方案/20261116-Bilibili集成与自维护方案-v1.2.md#214-b18-真实投稿验收)

B18 补测清单额外绑定原单 P 任务、原多 P 任务和原执行。Core 验证封存结果和进程树退出证据，在原账本上创建唯一后继任务，交接前重新核对条件。[多 P 补测设计及验证](方案/20261116-Bilibili集成与自维护方案-v1.2.md#2310-b18-多-p-补测)

Worker Supervisor 负责启动 Adapter Execution Host、核对进程身份、收集事件、续租、取消、等待退出、判断结果并提交状态；Adapter 不自行续租。代次令牌拒绝旧执行者写入本地终态，但不能凭此断言旧进程已停止远端请求。

**Bilibili 直接执行（2026-11-17 修订确认、实施中）**：Core 的 Bilibili Adapter 模块转换冻结快照和结果，Worker 直接监督独立上传引擎，不额外启动 Bridge 中间进程。引擎收到任务后自动完成上传及投稿，直接回传结构化结果；不在视频上传完成后等待 Core 的第二次许可。用户取消按[需求 R08](需求说明.md#r08-bilibili)以是否已交接为边界，后述通用执行中取消流程不套用于首版 Bilibili 已交接任务。进程身份、结果所属执行、退出证明和恢复仍需核验。该决定替代原 Q1；交接持久化与失败窗口等协议细节由[集成方案 Q10](方案/20261116-Bilibili集成与自维护方案-v1.2.md#18-审查后逐项确认2026-11-17)承接，不表示当前 Fake 专用代码已经支持。

**Bilibili 账号提交互斥（2026-11-17 已确认、实施中）**：Core 保留同账号三个 Task 并发执行名额，引擎内部按已核验的平台与 MID 共享跨进程提交锁，使三个任务可以并发上传、最终投稿按账号串行，不同账号互不占用该锁。等待锁属于当前调用内部执行，不建立引擎业务任务队列，也不向 Core 申请第二次投稿许可。锁的释放与异常接管不能仅凭等待超时认定原提交执行已停止；具体持有范围、退出核验与故障验证见[方案 19.3](方案/20261116-Bilibili集成与自维护方案-v1.2.md#193-账号提交锁与异常接管)。确认来源见[集成方案 Q11](方案/20261116-Bilibili集成与自维护方案-v1.2.md#18-审查后逐项确认2026-11-17)。

**取消与完成竞争已确认（2026-11-16）**：按[需求 R03](需求说明.md#r03-任务与重复提交)的 Q18，在短事务内条件核验任务和当前 Attempt。QUEUED 且尚未领取时可直接提交 CANCELLED 与事件，Claim 不能再取得资格；Claim 已先完成则只能记录取消意图，由 Supervisor 检查执行并收尾。RETRY_WAIT 仅在前次执行已退出、结果明确且无活动 Attempt 时取消，阻止后续领取；有活动执行或恢复未决时不得仅按状态名认定安全。Supervisor 结合有效结果与进程退出证据判定：有效成功证据保留 SUCCEEDED 并记录取消未生效；确认安全停止且无远端结果疑点才记 CANCELLED；无法确认则进入或保持 UNCERTAIN。已结束任务不被迟到取消改写，UNCERTAIN 不被取消请求洗成已取消；旧代次、无效或迟到结果不能绕过完成条件。取消请求、结论及对应事件一致持久化，重复请求返回当前结果。确认来源见 [Core MVP 方案 Q18](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

Lease 过期先进入待恢复检查。Recovery 结合实际进程、事件、进度记录、结果、回执和远端阶段判断后续动作；不能直接再次上传。无法确认远端结果时保留 UNCERTAIN，由明确处置流程承接，不自动重试。

退出证据独立于执行结果：命名 Job 无法打开，即使宿主已退出，也不能据此认定子进程全部退出。Supervisor 在持有 Job 句柄并核实活动进程数为零、宿主退出后，按当前执行所有权持久保存该 Attempt 的退出证据和事件；此步骤不释放名额、不提交业务终态。恢复所有者可复用这份可靠证据，再独立核验结果，最终事务统一提交结论与名额释放。没有可靠退出证据时继续保留 RECOVERY_PENDING 和名额。

**Core MVP 已确认（2026-11-16）**：采用自动检查和收尾。恢复程序先核验旧执行进程身份，只对确认属于该次执行的存活进程及其子进程尝试停止；身份或退出情况无法确认时，不盲目终止进程，继续占用对应账号名额并提示处理。确认该执行进程及其子进程全部退出后，才可释放名额供其他任务使用；租约到期本身不能使该名额重新可领取。名额释放与原任务结果分开判断：停止进程不证明远端操作被撤销，结果仍不明确的原任务保持 UNCERTAIN，不自动重传。确认来源见 [Core MVP 方案 Q1](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

先用可控 Fake Adapter 验证正常、失败、崩溃、超时、迟到/无效结果及取消等行为，再接真实平台。具体故障窗口、覆盖范围和证据写入对应方案，长期方法由[测试规范](测试/README.md)维护。

**人工处置已确认（2026-11-16）**：按[需求 R06](需求说明.md#r06-执行监督与恢复)对 UNCERTAIN 接收三种人工结论，追加独立 Resolution，保存操作标识、来源、时间、理由、证据引用以及 Task/Attempt 关联。确认成功在满足既有进程退出与结果证据边界后将 Task 转为 SUCCEEDED，保存注明人工确认来源的 Receipt；确认未成功须核验旧执行及其子进程已退出，将 Task 转为 FAILED，允许后续 Q16 显式再提交但不自动重试；无法确认则仅追加处置记录并保持 UNCERTAIN。前置证据不足或进程退出未确认时不强行终结任务、释放名额或开放再提交。原 Attempt 的 UNCERTAIN 终态、原始异常和事件不回写，人工结论作为后续记录解释 Task 当前状态。Resolution、必要 Receipt、Task 状态与 Event/Outbox 原子提交，按请求标识幂等，并通过条件更新防止相互冲突的并发结论同时生效。Fake 场景的人工回执仍明确标记模拟，不能冒充真实远端回执或 Adapter 自动核验。确认来源见 [Core MVP 方案 Q17](../archive/方案/20261116-Core-MVP实施方案.md#逐项确认记录)。

**Bilibili 执行时限分工（2026-11-17 已确认、实施中）**：依据[需求 R08](需求说明.md#r08-bilibili)，Core 的 Bilibili 执行路径不套用固定总执行超时，上传内部的网络超时和请求重试交由引擎处理。现有 Fake 执行时限不随该规划改写；引擎内部重试仍需满足最终投稿结果不明时不得盲目重复提交的边界。具体上游机制按选定导入版本审查，不能以存在重试代码代替故障验收。

## D06 契约、事件与结果

Bilibili 交接与证据（2026-11-17 技术细化、实施中）：交接前取消与开始交接在同一短事务竞争，交接决定持久化后才发送任务；发送失败不等于肯定未执行。引擎在最终投稿前可靠保存意图，之后保存关联执行的响应和终态；Core 结合阶段证据和独立退出证明收尾。进度、异常退出或没有投稿标记不构成安全重传依据。恢复所有者可采用原执行的有效结果，旧 Worker 不能写终态；已处置记录和后继任务不被迟到结果覆盖。具体见[方案 19.1—19.2](方案/20261116-Bilibili集成与自维护方案-v1.2.md#191-一次交接取消竞争与进程组织)，不把待实现契约套到 Fake。

对应 R01、R07—R09。REST 初始方向为 `/api/v1` 和 OpenAPI 3.1；平台 metadata 由相应 Adapter 契约约束。Adapter Request/Event/Result 在实际建立时明确版本和业务语义，不能原样复制候选 schema。

事件带版本和聚合内递增序号，与需要保证一致的状态及 Outbox 在同一事务持久化。发布允许至少一次投递，消费按事件标识避免重复业务效果；SSE 支持续接。日志脱敏，结果必须关联到任务、执行尝试和相应远端证据。

平台协议的具体字段、错误分类、远端查询和恢复策略由对应方案细化。凭进程退出码、结果文件存在或单个接口成功不足以提交业务成功；也不得借契约对齐恢复已取消的本地文件内容扫描。

Bilibili 契约同步（2026-11-17 技术细化、实施中）：Target 与执行协议按平台判别，真实回执不复用 Fake 验证。版本化能力清单约束发布方式、字段和接口，预览/提交复用验证并冻结配置，不支持项明确拒绝。审核观察与受理结果分开，查询失败保留可靠旧观察，迟到查询不覆盖新结果；模糊匹配仅作候选。人工处置保留原 Attempt 和独立 Resolution。映射与证据见[方案 19.5—19.7](方案/20261116-Bilibili集成与自维护方案-v1.2.md#195-target元数据与能力映射)，schemas 已由实际模型与路由统一生成，生成方式见 [schemas 说明](../schemas/README.md)。
