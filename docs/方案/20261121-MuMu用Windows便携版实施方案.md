# MuMu 用 Windows 便携版实施方案

创建、更新于 2026-11-21。状态为 **待验证**。用户于当日确认采用本方案并授权实施，指定通过 UU 连接台式机执行测试和验收。便携功能已落地，实机和真实平台结果以下方记录为准。实际投稿、本人扫码及故障注入沿用下文规定的账号、素材、次数和故障窗口。

本方案承接 `BILIBILI-RELEASE` 的便携版候选交付、`DASHBOARD-BILI-POSTING-MODES` 中统一提交受理后的多 P 投稿验证，以及 `DASHBOARD-BILI-RECOVERY` 中的异常恢复。MuMu 客户端用于整套实机验收。手动单片补验仍按原待办跟踪。[本机统一投稿](../需求说明.md#r01-独立应用与统一入口) · [任务与重复提交](../需求说明.md#r03-任务与重复提交) · [Bilibili 要求](../需求说明.md#r08-bilibili) · [运行角色](../设计说明.md#d01-模块与入口边界) · [待办](../待办.md)

## 用户拿到包后怎样用

1. 在运行 MuMu 的 Windows x64 电脑上，把 ZIP 解压到一个新文件夹，双击根目录的 `启动上传平台.cmd`。首次选择 MuMu 已配置的**录像输出目录**，接受建议的数据位置或另选一个新目录，点「保存并启动」。以后双击沿用这份设置。
2. 启动窗口分别显示接口、后台上传进程（Worker）和 B 站引擎的状态。三项就绪后显示「MuMu 可以连接」和本机地址 `http://127.0.0.1:8765`。初装还没有投稿账号时，提示从 MuMu 的「自动投稿 → 管理投稿账号」扫码。账号尚未登录也能启动平台。
3. 录制结束后由 MuMu 按现有流程自动交单。用户从原场次点「查看任务」，看本次稿件、分 P 顺序和 B 站回执。首次配置和日常启动都无需手输命令、编辑 JSON 或安装系统 Python、Node.js、PowerShell 7。打包人员仍通过 PATH 使用 PowerShell 7。

现有 0.2.0 联调包已经验过解压启动、同库重启和 MuMu 回包丢失后的查回。它带 Python 和面板，需分窗口启动两个进程，并另配引擎。真实整场单片私密投稿也已跑通。此前一次 MuMu 自动三 P 在最终投稿时收到 `601`，原任务仍待核验。后来在 B 站官方网页另投的三 P 验证了那份网页稿，只能用来参考逐段核对方法。[联调包验收](../../archive/方案/20261120-fileUploadPlatform-Dashboard与统一提交实施方案.md#windows-联调包收尾) · [MuMu 实机记录](../测试/报告/20261120-MuMu整场自动投稿真实使用测试记录.md)

## 包里带什么，数据放哪里

| 位置 | 拟交付内容或处理方式 |
| --- | --- |
| ZIP 根目录 | 双击入口、简明使用说明和版本清单。沿用现有嵌入式 Python、后端及锁定依赖、构建后的 Dashboard、公开契约。以当前源码重新构建面板，带上 11 月 21 日的 `601` 提示。 |
| `engines/<build_id>/` | 随包交付独立引擎的 Windows x64 正式 EXE、该 EXE 的 `capabilities` 原始输出及所需运行依赖。优先复用已在本机验过的 `bue-0.2.0-dev6`。构建时运行实际 EXE，核对构建号、协议、扫码、上传和本次使用的私密投稿能力。能力不符、文件缺失或输入为测试引擎时停止出包。 |
| 版本与来源 | 固定上传平台、引擎的来源版本和构建号，登记配套 MuMu 验收版本，随附引擎、上游及随包依赖的许可和版权材料。发行号在构建候选时确定，候选 ZIP 与已验的 0.2.0 联调 ZIP 分开命名、保存。 |
| 用户数据 | 解压目录只放程序。拟在 `%LOCALAPPDATA%\fileUploadPlatform\MuMu` 保存首次设置，默认数据根为其下的 `data`，也可另选本机目录。数据根下用同级的 `core` 和 `bilibili-private` 分别存数据库与引擎私有状态，保留引擎既有的目录访问控制。部署配置和日志也放包外。首次用空库，重开沿用同一库、部署编号和账号。旧库格式不符或已保存的原库丢失时显示原路径，停止启动，避免生成另一个部署。 |
| MuMu 录像 | 以用户选的录像输出目录为素材根，以其 `sessions` 子目录为配置根。MuMu 写入 `sessions/<作品编号>/upload.yaml`，媒体可以来自不同 `job-*` 子目录。首次尚无 `sessions` 时，在「保存并启动」前显示将补建的空目录。沿用现有本机路径校验，私有数据根放在开放给 MuMu 的目录之外。始终引用 MuMu 原件。 |

包内只从固定输入清单收集文件。真实账号凭据、业务数据库、录像、运行日志和测试执行器留在各自环境。新包解压到另外的程序目录，运行中的引擎版本目录保留到对应任务收尾。本次沿用 MuMu 的公开接口和嵌入页。旧库迁移、手工选 MP4 的新页面、跨进程分片续传和「仅上传，待本人处理」继续留在各自的后续范围。[引擎部署边界](../operations/bilibili.md#部署边界) · [文件交接决定](../adr/0001-reference-local-upload-files.md)

## 实施顺序与文件

1. **固定并组装候选包。** 扩展 [Windows 打包脚本](../../tools/build_windows_zip.ps1)，从明确指定的引擎版本目录收集生产文件和许可材料，校验能力，再与后端和新面板组装。引擎保持独立仓库维护。把 ZIP 先写到仓外本轮候选目录，保留可识别的构建记录。
2. **接好双击入口。** 拟在 `tools/` 增加 `.cmd` 入口，从自身所在目录调用包内 `runtime\python.exe`。在 `src/upload_platform/` 增加 Windows 启动模块，负责首次选目录、原子保存设置，按当前解压位置生成引擎 EXE 和能力文件的绝对路径。只为两个子进程设置同一组数据目录、引擎配置和允许读取的目录。复用现有 `server`、`worker` 及诊断接口，保留[分角色启动脚本](../../tools/windows_start.ps1)供排查。
3. **管理本次启动的两个进程。** 同一部署的启动操作互斥。先启 API，核对健康接口中的数据库和 `deployment_id`，再启 Worker，等本次 Worker 的心跳并核对 B 站平台报告的引擎构建与能力。再次双击时核对部署编号、进程号及创建时间，只补启已确认缺失的角色。端口被其他程序或其他部署占用时显示冲突。启动失败时给出失败环节和脱敏日志位置，只收尾可确认属于本次启动且尚未处理任务的进程。关闭状态窗口后上传继续。用户另行选择「退出上传平台」时，先让 Worker 停止领单并等已交接的任务收尾，再于账号维护和查询结束后正常关闭本部署的服务。
4. **用实际成品验收并交付。** 扩展[Windows 验包用例](../../tests/e2e/test_windows_package.py)，复用[跨仓库引擎检查](../../tests/integration/test_bilibili_real_engine.py)及[现有故障测试入口](../../tests/README.md)。先检查构建输入和启动异常，再用解压出的候选 ZIP 走隔离联调，最后用同一份 ZIP 做获准的 MuMu、B 站实机验收。验完后直接交付这份 ZIP，重新构建须复核受影响项。

## 双击启动怎样验

在 Windows x64 测试机上以普通用户登录，使用新的数据目录和带中文、空格的解压路径，测试时不从 PATH 提供 Python、Node.js 或 `pwsh`。先在无外网环境从资源管理器双击，首次选录像目录，用健康接口和平台诊断核对 API 就绪、一个本部署 Worker 心跳持续更新、正式引擎版本匹配。记录实际 Windows 版本。恢复联网后，从 MuMu 打开账号页，由测试账号本人扫码，在 MuMu 选中并保存该账号。

连续双击两次，确认进程和 Worker 没有多出一套。在有测试任务时关闭状态窗口，通过 MuMu 继续观察执行。正常退出服务后重新双击，原账号、部署编号及原场次对应的任务仍可查回。另用隔离目录分别制造端口占用、引擎缺失或能力不符、Worker 启动失败和不兼容旧库，逐项观察清楚的提示、旧数据与其他进程完整，以及纠正原因后再次双击能够恢复。正式包独立做引擎核对，故障夹具只在仓外测试环境使用。

## 多 P 投稿怎样验

| 步骤 | 实际操作与通过条件 |
| --- | --- |
| 准备一场 | 使用指定测试账号、一次新投稿和「仅自己可见」。选三段画面或声音容易辨认的素材，让 MuMu 在同一场录制中形成三段切片。设置唯一标题，记录创作中心该标题原有稿件数和本地台账基线。 |
| 由 MuMu 自动交单 | 前两片封口、第三片正在录制时开启该场自动投稿，停止本场并等尾片封口，让 MuMu 正常生成清单并提交一次。记下 P1、P2、P3 的本地片名、时长和各一处可对照的时间点。从原场次点「查看任务」，对照清单和任务快照，确认新增一个作品、一个任务，单个多 P 投稿单元下的三段及顺序完全一致。 |
| 从 B 站核对 | 从原任务取得 BV 号，用该账号主动查回同一 BV。在创作中心按唯一标题和 BV 确认只新增一份私密稿件。在播放页数出三 P，依次播放，在预记位置逐段对照本地画面和声音，核对内容、时长和顺序。留下任务号、BV、三行逐 P 对照结果。 |
| 判定 | 原场次、平台任务和远端稿件能对上，且一稿三 P 全部可按序播放，才记通过。缺 P、错序、出现第二份稿件分别记失败。遇 `601` 或缺可靠回执时保留原任务，按下节查回，证据不足记待核验。另开官方网页重新投稿所得的 BV 不能填入这次结果。 |

## 断线恢复怎样验

先在隔离 Windows 环境使用真实 SQLite、独立 API 和 Worker、MuMu 实际客户端及可控的本地接收端。每次只在表中指定位置制造故障，保存断线前后的任务号、执行次数、阶段记录和接收端计数。引擎端故障用独立测试构建复现，发行包始终保留正式引擎。

| 断在哪里 | 怎样触发和恢复 | 怎样算通过 |
| --- | --- | --- |
| MuMu 发出请求，平台已经建单，MuMu 没收到回复 | 沿用现有验包用例，在 SQLite 提交后丢弃成功回包。重启同库 API，从原场次用原部署号、原 `Idempotency-Key` 查回。隔离用例再用同键同正文重放一次。 | 两次都得到同一作品、同一任务。数据库只增一条受理记录，后台只执行一份投稿。另用新库带旧部署号查回，得到 `409 binding`，新库无新增记录。 |
| 上传第 2 个 P 时短暂断网，最终投稿尚未发出 | 在可控接收端记录已接收的分片，让传输中断，再恢复连接。分别覆盖引擎在本次执行内恢复、引擎报「尚未投稿」并退出两种情况。 | 恢复传输的用例最终只生成一份三 P 稿件。需要新的执行尝试时，必须同时有可靠的「尚未投稿」证据、旧执行树的退出证明和剩余重试次数。新尝试属于原任务。再用耗尽次数的配置核对停在原任务、保留失败记录。 |
| B 站可能已经收稿，最终回复丢失 | 本地接收端先登记一份稿件再断开最终回复。重启 Worker，从原任务做远端查询。分别让查询返回唯一可靠匹配、无匹配或多个候选。 | 旧进程未确认退出时保留恢复等待。能可靠匹配时回执补回原任务并指向同一 BV。证据不足时保持「结果待核验」（`UNCERTAIN`）。恢复及重启后，接收端的最终投稿请求总数始终是一次。 |
| 最终投稿返回 `601` | 在隔离环境返回该业务码，刷新 MuMu 嵌入的原任务页，再重启 Worker。 | 原页提示先查回、可能需要本人验证。没有可靠收稿证据时保留待核验，只查原任务，不自动发第二次投稿。若实机碰到短信验证，由账号本人在官方页面处理。 |

若 MuMu 的请求在抵达上传平台前就已中断，隔离用例应先在原部署用原键查回，核对 `404` 且没有新增记录。投稿意图和原请求仍有效时，用同键同正文发送一次，最终只建一个任务。这里的 `404` 只说明本机尚无这次受理记录。[统一提交与查回](../operations/dashboard.md#程序和网页投稿)

**真实 B 站恢复单独验。** 用最终包和获准的专用测试机，保留 MuMu 与平台的本机连接，只对本轮上传的外网连接制造中断。传输中断选在第 2 段上传、最终投稿前，恢复网络后核对尝试历史和唯一远端稿件。对于最终投稿结果不明的情况，优先在原部署查回已有异常原单。若需新稿，在获准的最终提交窗口中断连接，记录实际断点，用原任务、可靠远端标识和创作中心稿件数交叉核对。查不到唯一匹配时，可验证原任务保持待核验、没有重投，成功查回一项仍待补验。只观察到 MuMu 丢回包或引擎结果写盘失败，就只记录该断点。实际断点无法确认或无法隔离时保留现场，列明未覆盖项。[B 站查询与重试边界](../operations/bilibili.md#投稿配置与查询) · [测试规范](../测试/README.md)

## 完成条件与后续同步

- 实施时先固定候选版本和测试机。新增真实投稿、本人扫码及真实故障操作按指定账号、素材、可见范围、允许次数和故障窗口的授权执行。可在同一份获准稿件上取得多 P 和传输恢复证据。结果不明时停止新增投稿，保留原场次、原件和稿件。
- 最终包双击启动、MuMu 一稿三 P 逐段回放、约定的断线场景均达到各自的通过条件，才能宣告本范围完成。隔离注入与真实 B 站结果分别记录。实机仍有缺口时可标识为试用候选，并在说明中列出已验功能和未验项，对应待办保持开放。历史 0.2.0 结果按调用链、版本和环境复用，新启动入口和本轮实机结果单独验收。
- 每项记录候选 ZIP 版本、引擎构建号、MuMu 版本、操作时间、预期与实测、结论及仓外证据位置。保留首次失败和后续复测。证据摘要用任务号、BV 和脱敏截图串起本地与远端，普通日志及报告不含 Cookie、二维码、短信内容或完整请求键。
- 方案获确认后按[文档规范](../README.md)同步待实现的需求与设计。实施验收后更新[随包说明](../../tools/windows_package_readme.md)、[Windows 运行说明](../operations/dashboard.md)、[B 站运行说明](../operations/bilibili.md)和[测试运行入口](../../tests/README.md)。B 站旧说明仍写库结构版本 2，届时统一引用当前数据库实现和实际验包结果。根 README 标明可用范围，待办按实际覆盖逐项更新，保留手动单片等余项，再按结果归档。
