# Bilibili 集成与自维护方案 v1.2

本文替代原 Bilibili Adapter v1.1 的自研协议路线。v1.1 保留历史追溯，不再作为实施依据。

## 1. 目标

采用独立导入 biliup 源码、建立自己的私有仓库、最终只保留 B 站上传相关功能、由 fileUploadPlatform 统一调度的路线。

1. 将 biliup 上游源码 Import 到自己的私有仓库，不建立 Fork 关系。
2. 完整源码作为裁剪依据；最终维护版本只保留 B 站账号登录、凭据管理、视频上传、封面、单 P / 多 P 投稿及必要依赖。
3. 不纳入直播录制、其他直播平台录制、剪辑工作台、AI 自动切片、Fleet 多机录制等无关功能。
4. 形成独立可运行的 B 站上传引擎，由 fileUploadPlatform 通过本地进程调用。
5. fileUploadPlatform 继续作为唯一的通用作品、任务、调度、并发、执行记录和结果管理平台。

## 2. 已确认决定

| 项目 | 决定 |
|---|---|
| 代码获取 | Import 到独立私有仓库，不保留 Fork 关系 |
| 功能范围 | 只保留 B 站上传相关能力 |
| 上游更新 | 不自动跟随，由用户决定是否导入上游改动 |
| 自主维护 | 私有仓库独立修改、构建和发布 |
| 平台集成 | fileUploadPlatform 通过独立进程调用上传引擎 |
| 业务调度 | 只由 fileUploadPlatform 负责 |
| 登录 | 沿用导入代码中可用的扫码登录；扫码不可用时支持用户主动导入 Cookie |
| 投稿 | 单 P + 多 P |
| 账号 | 多账号，凭据按账号隔离 |
| 并发 | 同账号最多 3 个独立 Core Task；multipart 整体一个 Task，内部 P 顺序处理 |
| 分片并发 | 单视频分片并发设为 1 |
| 成功定义 | 投稿受理并取得可验证 AID/BVID；审核状态独立跟踪 |
| 字幕 | 首版不实现上传 |

## 3. 两个项目的职责

### 3.1 fileUploadPlatform

负责 UploadWork、UploadUnit、Asset、upload.yaml、即时和定时调度、Task、Attempt、Account Slot Lease、取消、进程监督、异常恢复、UNCERTAIN、统一 API/SDK/CLI/Dashboard、Receipt 和未来其他平台 Adapter。

不负责 B 站扫码协议、Cookie 内部格式、UPOS、分片上传、封面上传和 B 站投稿协议。

### 3.2 私有 Bilibili Upload Engine

负责 B 站扫码登录、Cookie/Token 凭据管理、账号验证、B 站 HTTP Client、UPOS、分片上传、封面、单 P / 多 P 投稿、AID/BVID 和 B 站专属错误分类。

不负责任何业务任务调度或投稿队列（包括 B 站上传/投稿队列）、定时任务、整项业务任务的重试调度、跨平台队列、Core Task/Attempt/Lease、直播录制、其他平台录制、剪辑工作台、AI 切片、Fleet 或与 Core 重复的统一管理 Dashboard。一次调用内部的网络超时、有限请求重试与提交互斥由引擎负责，见第 7、19 节。

## 4. 私有仓库策略

### 4.1 Import

建立独立私有仓库，名称例如 kachekakaka/bilibili-upload-engine（仅为建议，创建前由用户确认）。

导入上游 biliup 完整源码作为裁剪依据；尽可能保留可导入的 Git 历史。记录上游 URL、导入日期、commit/tag、根许可证、第三方依赖许可证和导入时目录清单。

不建立 Fork 关系，不配置自动 upstream 同步。导入完成后由用户独立管理。

完整导入源码不代表最终维护版本必须保留所有功能；最终范围以第 5 节为准。

### 4.2 上游更新

- 不自动跟随上游最新提交。
- 用户需要时手动查看上游 Release/commit。
- 只选择对 B 站登录、上传、投稿、安全修复或必要构建依赖有价值的改动。
- 更新前备份私有维护状态；更新后运行自己的测试。
- 如果上游改动冲突，可以不合并，继续维护当前版本。
- 自己的版本标记用于识别和回滚已验证构建，不代表运行时依赖上游版本。

## 5. 功能保留与裁剪

### 5.1 最终保留

1. B 站扫码登录和凭据管理；
2. B 站账号身份验证；
3. Cookie / Token 保存、验证及现有可用续期能力；
4. B 站 HTTP Client 和必要请求参数处理；
5. UPOS 预上传、视频分片上传和完成；
6. 上传线路中支撑 B 站投稿的必要部分；
7. 视频上传完成及远端资源信息解析；
8. 封面上传；
9. 投稿模型和配置解析；
10. 单 P / 多 P 投稿；
11. AID/BVID 获取和稿件状态查询；
12. 登录、验证/续期、上传、查询所需 CLI；
13. 上述能力依赖的通用 crate、配置、资源、测试和第三方依赖。

### 5.2 最终不保留

- biliup 自身的投稿/上传任务队列、定时投稿、目录监控自动投稿、后台任务调度和独立自动重试调度；
- 抖音、斗鱼、虎牙、快手、Twitch、YouTube 等其他直播平台解析与录制；
- B 站及其他平台直播监控、录制调度、断流重连、弹幕录制；
- 直播下载器、录制 Fleet 节点与房间分派；
- 自动切片、AI 高光分析、语音转写和弹幕密度分析；
- 剪辑工作台、多轨时间线、字幕制作、遮挡、转场、渲染和视频导出；
- 面向录制业务的完整 WebUI、用户管理和 Fleet Dashboard；
- 录制任务数据库、录制目录管理和录后保留策略；
- 与 B 站上传无关的下载、评论、合集管理等 CLI 命令。

### 5.3 裁剪原则

不在本方案预先指定源码文件删除清单；先做依赖盘点。被登录、上传、投稿功能依赖的通用模块必须保留。删除功能前检查调用图、Cargo feature、build.rs、前端路由、资源文件和测试依赖。目标是最终构建物不包含无关产品功能，而不是机械删除目录。具体源码裁剪清单属于私有 biliup 仓库的实施任务。

## 6. 与 fileUploadPlatform 的集成

采用独立进程，不把 Rust biliup 代码嵌入 Python Core。

集成链路：fileUploadPlatform 的 UploadWork / Task / Scheduler → Worker Supervisor（Core 内 Bilibili Adapter 负责数据转换）→ 独立私有 Bilibili Upload Engine → Bilibili。进程组织与交接后的行为按[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)及[需求 R08](../../docs/需求说明.md#r08-bilibili)；不额外启动 Bridge 中间进程。

- 首版通过参数数组启动独立可执行程序，不经过 shell 拼接。
- 登录是用户交互操作，由用户在本机终端/用户会话执行，不由后台 Worker 等待扫码。
- 上传是非交互操作，由 Worker 在受监督子进程中启动。
- Core 内的 Bilibili Adapter 将 Task Snapshot 转换为上传引擎配置，并解析引擎直接回传的结构化结果。
- Cookie 明文不放入命令行、环境变量、Task Snapshot 或普通 IPC 消息。
- 登录和上传使用账号专属凭据目录。
- 如果现有 CLI 参数/输出不足以提供可靠进度或结果，可在私有上传引擎增加 machine-readable 命令或本地 IPC；不需要重写 B 站底层协议。

## 7. 调度、并发与任务语义

### 7.1 唯一调度者

fileUploadPlatform 是唯一业务任务调度者，也是唯一的上传/投稿队列所有者。所有即时任务、定时任务、排队顺序、账号并发名额、重试时机和任务状态均由 fileUploadPlatform 决定。

私有 Bilibili Upload Engine 不是第二个任务管理平台。它只提供被调用时执行一次明确操作的能力：登录、验证、上传并投稿、查询结果。它不得保留或启用自己的上传/投稿任务队列、定时投稿器、目录监控自动投稿、后台任务调度或自动重试调度。若导入的 biliup 代码原本包含这些能力，裁剪时应移除其业务入口；底层上传过程中必要的分片顺序、请求重试和协议级恢复不属于业务任务调度，可以保留。

### 7.2 biliup 内部允许保留的执行机制

虽然 biliup 不保留业务任务调度，但允许保留一次上传调用内部必需的执行逻辑，例如按顺序上传分片、处理单个 HTTP 请求的短暂重试、完成当前视频上传所需的内部步骤。这些机制不能创建独立的业务 Task、改变 Core 的排队顺序、越过 Core 账号并发额度或在当前调用结束后自行启动其他投稿。

### 7.3 并发

- Core Account Slot Lease 控制同一账号最多三个独立 Task 同时执行。
- independent：每个视频对应一个 Task。
- multipart：整个多 P 投稿是一个 Task，占一个账号 slot，内部按 P 顺序上传。
- 单视频分片并发显式设为 1，不能使用上游 CLI 默认值。
- 投稿最终提交按账号级串行/限流处理。
- Q11 已确认由引擎内部按账号共享跨进程提交锁，职责见[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)；锁生命周期、限流及崩溃处理按第 19.3 节实施和验证，不再通过 Core 的第二次最终投稿许可实现互斥。
- 上传引擎不得绕过 Core 启动额外并发上传任务。

### 7.4 重复投稿与成功

- 默认同一 Work 展开项 + B 站账号重复提交时返回既有 Task。
- 用户显式重新投稿才创建新执行意图。
- UNCERTAIN / RECOVERY_PENDING 时禁止直接重跑上传命令。
- 不自动删除或覆盖 B 站已有稿件。
- 退出码 0 不是唯一成功依据；成功必须获得并验证 AID/BVID，保存 Receipt。
- 无法验证远端结果时进入 UNCERTAIN / 人工核验。
- Task SUCCEEDED 表示投稿受理；审核状态独立跟踪，首版刷新方式按[需求 R08 的主动查询约定](../../docs/需求说明.md#r08-bilibili)。

## 8. 账号与凭据

- 每个 B 站账号独立保存登录凭据，按 account_id 映射到上传引擎凭据文件。
- 账号唯一身份按[设计 D02](../../docs/设计说明.md#d02-领域与数据约束)以平台与经验证的 MID 判定，昵称与本地名称不用于区分实际账号。
- 登录命令由用户交互执行；成功后只返回账号身份摘要（MID、昵称），不把 Cookie 明文返回 Core。
- 凭据保存在 fileUploadPlatform 数据目录之外的受限私有目录；路径由配置指定。
- 首版使用受限 Windows 文件 ACL，限制到配置的运行身份及必要系统管理权限，拒绝普通其他用户读取；临时文件与备份同样受保护。当前不新增 DPAPI 格式或解密链，不能让上游直接把密文当 Cookie JSON 读取。
- Core 数据库只保存 credential reference、账号身份和状态，不保存 Cookie 明文。
- 多账号不得共用默认 cookies.json。
- 凭据失效时暂停该账号新 Task，提示用户重新登录。
- 不假设凭据文件支持并发写入；登录/续期与该账号上传执行互斥，三个上传调用不得各自续期回写。维护流程、跨进程锁与崩溃恢复见第 19.4 节。
- 用户重新登录时的暂停领取、等待执行收尾、成功后恢复及取消/失败后的旧凭据核验按[需求 R08](../../docs/需求说明.md#r08-bilibili)执行；不将登录中断当作成功，不以恢复登录暂停覆盖手动停用状态。

## 9. 作品包映射

- independent：每个视频生成一个 Core Task，Core 内 Bilibili Adapter 生成一次上传引擎调用。
- multipart：有序视频集合生成一个 Core Task，一次调用按 manifest 顺序形成多 P 稿件。
- Work 提供默认标题、简介、标签、封面；UploadUnit 可覆盖整稿字段；Video 提供单视频/分 P 标题等；Target 指定 B 站账号及专属 options。
- Core 内 Bilibili Adapter 将冻结的 Task Snapshot 转换成上传引擎支持的投稿配置。
- 不支持的字段必须报 UNSUPPORTED_OPTION，不得静默忽略。
- 发布选择按[需求 R08 的 Target 显式配置约定](../../docs/需求说明.md#r08-bilibili)校验与冻结；字段映射、能力声明及不支持项按第 19.5 节，不沿用账号或引擎默认值。

## 10. 取消、崩溃与恢复

Core 不假设可以直接控制上传引擎内部 UPOS checkpoint。

执行时长按[需求 R08](../../docs/需求说明.md#r08-bilibili)和[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)的 Q12 约定：Core 不设任务总时限，上传内部超时与请求重试由引擎负责，不将 Q12 记为同意 Core 根据进度停滞自动终止引擎。本次已锁定只读核查的上游提交及具体调用路径，证据见第 20 节；这不是实际导入或运行验证。

- 启动前失败：确认进程未启动后可安全重试。
- 上传中进程退出：先确认整个进程树退出，再依据上传引擎实际暴露的恢复能力处理。
- 只有取得当前执行的可靠“尚未发出最终投稿”证据、确认整个进程树退出，并符合既有重试预算时，才允许当前 Task 新建 Attempt 重传。缺少稳定恢复接口不等于可以安全重传；multipart 首版不复用旧调用 checkpoint 或仅重传失败 P。具体证据与故障窗口见第 19.2 节。
- 投稿提交可能已发出但无可靠回执：进入 UNCERTAIN，先查询稿件；证据不足则人工核验，不自动重复投稿。
- 人工确认未成功的受理条件、记录保留和显式重新投稿边界遵循[需求 R08](../../docs/需求说明.md#r08-bilibili)，不以机器查询无结果自动代替用户结论。
- 用户取消按[需求 R08 的交接边界](../../docs/需求说明.md#r08-bilibili)处理；已交给引擎的任务首版不支持用户取消。异常退出与恢复仍须核验进程树退出后才能释放账号 slot，不能以不支持取消代替退出核验。
- 远端副作用可能已经发生时，取消不能伪装成“未投稿”。
- 不宣称具有上传引擎没有实际提供的分片级续传能力。

## 11. 私有上传引擎仓库交付物

私有仓库的创建、源码导入和功能裁剪作为独立项目执行。本项目与之集成所需的交付物：
1. 独立私有仓库；
2. 上游来源、导入 commit/tag、许可证和依赖许可证记录；
3. 最终保留/移除功能清单；
4. 可独立构建的 B 站上传引擎；
5. 登录、验证、上传、单 P、多 P、查询入口；
6. machine-readable 结果契约；
7. Windows 构建和运行说明；
8. 独立测试与已知限制。

不在 fileUploadPlatform 仓库存放整份 biliup 源码，不把它作为 Python package 直接依赖。

## 12. 实施阶段（2026-11-17 已授权，进度见第 23 节）

### P1 — 私有仓库导入与功能盘点
导入上游源码，记录来源/commit/许可；盘点 B 站上传依赖图；确定保留/移除清单；先确保完整导入基线可构建。

验收：私有仓库可独立构建导入基线，来源和许可记录完整，功能盘点完成。

### P2 — 上传引擎裁剪
移除非上传业务入口和功能，以及 biliup 自己的投稿队列、定时投稿、目录监控自动投稿、后台任务调度和独立自动重试调度；保留扫码登录、凭据、上传、封面、投稿、查询及必要依赖；建立仅响应显式调用的独立 CLI 命令和配置。

验收：独立上传引擎可完成扫码登录和单 P / 多 P 投稿，不依赖录制、剪辑、AI、Fleet 服务。

### P3 — 机器可读调用契约
按第 19 节定义 capabilities/login/validate/upload/query 机器入口及结果读取契约；定义 JSON 输入、进度事件和终态结果；结果包含执行身份、MID、受理证据和错误分类；敏感凭据不进入输出。login 的扫码交互在用户终端中进行。

验收：第 21 节的独立 Fake Engine Fixture 验证 Core 协议边界，实际 Rust 引擎加本地协议服务器验证请求次数、提交互斥、凭据和持久证据；两者不能相互替代。任务交接后自动上传并投稿，不需要第二次投稿许可，交接后的用户取消不能产生取消命令或伪造 CANCELLED。

### P4 — fileUploadPlatform Bilibili Adapter
实现直接监督引擎启动、Core 内参数/配置/素材转换、引擎结果直接回传、账号凭据映射、交接前取消与交接后拒绝用户取消、启动故障与异常恢复、进程树退出确认、重复投稿和 UNCERTAIN 保护。Bilibili 执行路径不套用 Fake 的总执行时限；不实现额外 Bridge 进程或最终投稿二次许可。

## 19. 本轮补齐的技术实施约定（待实现）

本节按 Q2—Q12 及用户的技术细化授权编写，不重开已确认选择。消息、字段与文件名是拟实施契约，实施时才写入代码、数据库及 schemas，当前公开契约仍仅支持 Fake。长期职责见[设计](../../docs/设计说明.md)，业务要求见[需求 R08](../../docs/需求说明.md#r08-bilibili)。

### 19.1 一次交接、取消竞争与进程组织

1. Core 在新 Attempt 下先保存启动意图及独立执行目录，记录 boot 身份、execution_id、Job 名称、引擎路径/构建版本/协议版本。沿用“挂起创建 → 加入 Windows Job → 保存 PID 与创建时间 → 恢复线程”。引擎不允许 breakaway，网络请求在引擎进程内执行，不启动可脱离 Job 的上传服务。
2. 启动参数只传非敏感执行身份与协议启动信息，供引擎 hello 回显并报告自身构建/能力版本；引擎等待一份完整 upload 请求，收到前不读凭据、不上传、不投稿。握手用于身份/版本核验，不是上传后的投稿许可。Bilibili 使用 hello → upload；Fake 原有 request → hello → go 独立保留。
3. API 取消与 Worker 交接通过同一短事务条件竞争：核验当前 Attempt、执行代次、领取资格及 cancel_requested_at，先持久化 handed_off_at 和交接事件，再发完整请求。事务获胜即进入“正在交接/已交接”不可取消边界，不以引擎回传确认作为分界。取消先提交则禁止交接，空等引擎退出后收尾；交接先提交则取消返回 409 cancellation_not_supported_after_handoff，不写取消意图、不发 cancel。账号维护不撤回此前已取得的领取资格，按 19.4 等待它们收尾，避免双方相互等待。
4. 数据库提交和管道发送不是原子操作。交接提交、发送前/发送中崩溃，只证明“可能交出”，不能证明引擎尚未执行；无可靠终态证据则保守恢复，不重发请求。引擎只接受一个请求，重复/冲突请求不能启动第二次投稿。
5. handed_off_at 是执行阶段信息，不新增 Task 状态。保留既有 RUNNING/RECOVERY_PENDING/UNCERTAIN；启动等待采用有限握手超时，交接后无总执行时限，也不按进度停滞自动终止。Core 自己续租不依赖进度；引擎进度用于观测。
6. 所有权丢失、服务崩溃或协议损坏仍进入既有恢复监督，仅处理核验属于该次执行的进程树。stdout 断开不能触发重投或丢弃唯一结果，持久文件供恢复读取。树未确认退出不释放 slot，成功消息不等同于退出证明。

取消分支还需覆盖：QUEUED 无活动执行可直接取消；RETRY_WAIT 只有前次已安全结束、树已退出且下一次尚未交接时，才可按既有 Core 规则阻止下一次尝试，不能借此撤销前次已交接执行。已结束任务返回既有结果，不写伪造取消；UNCERTAIN 不被取消改成 CANCELLED。重放同一取消请求保持幂等。

### 19.2 阶段证据、结果和重试

引擎在 Core 指定的独立执行目录保存按序执行记录及终态文件。记录包含协议版本、平台、task_id/attempt_id/execution_id/generation、expected_mid、序号、阶段及时间；身份验证成功后增加 verified_mid，验证失败时不得伪造该字段。请求和事件只带凭据引用及非敏感数据。完整请求验证后先保存 request_accepted，再上传，不能把接收任务与平台受理稿件混为一谈。阶段至少有 uploading、waiting_submit、submit_intent、submit_response、finished，均为 Attempt 内部阶段。

- 最终投稿 HTTP 请求前，必须可靠保存 submit_intent，包含实际接口、精确投稿配置及有序远端视频键；刷盘失败不发请求。响应到达后保存脱敏业务 code、MID、AID/BVID 及请求关联，再生成终态；临时写入、刷盘及同目录替换均检查结果，正常返回在终态可靠落盘之后。
- 执行记录是副作用证据，不是引擎业务队列；重启不能自行重投。首版不复用旧 Attempt 的上传 checkpoint；一次调用内部保留分片重试。恢复可读已存结果并判断不确定性，不宣称自动续传到失败 P。
- 没看到 submit_intent、最后进度为 uploading、非零退出码或错误日志，都不能单独证明未投稿。安全失败要求受控路径封存当前执行的 not_submitted 终态、证明状态机未进入 submit_intent，且 Core 独立确认树已退出；被杀、证据缺失/损坏不能生成该结论。
- Bilibili 结果使用 outcome、submission_state（not_submitted/rejected/accepted/unknown）和 error（分类、平台 code、重试理由），不沿用 Fake 的笼统 safe 布尔值。accepted 须核验远端标识/MID；明确拒绝须有对应请求的有效业务响应，未知错误不能证明未受理。
- expected_mid 必须与快照一致；verified_mid 不一致时只能报告身份核验失败，不能作为成功或进入上传。认证失败可返回关联当前执行的 not_submitted 错误，不能因为尚未取得 verified_mid 就伪造身份或将该错误当成有效成功回执。
- 原执行身份与 Core 恢复所有权分离：恢复者可采用被接管 Attempt 的原始有效结果，旧 Worker 无权写终态。重复序号同内容幂等，同序号异内容、错身份/版本、截断及阶段矛盾不能作为终态依据；结果路径不得转向其他执行目录。
- 瞬时进度允许合并；副作用记录不能丢。stdout 逐行 JSON，stderr 单独脱敏；限制消息大小及缓冲并持续排空，防止日志阻塞上传。最终记录链可弥补管道丢失，不把每个分片进度全写 Core DB。
- Result、Receipt、Task/Attempt 结论、事件与 slot 释放在 Core 同一短事务提交，重验所有权及退出证明；回滚后幂等恢复，不能产生重复回执或再次上传。

| 故障窗口或结果 | 允许的处置 |
| --- | --- |
| 未交接，确认引擎不能执行或整个树已退出 | 按既有取消意图或 RetryPolicy 收尾；无远端调用 |
| 已交接、受控失败封存 not_submitted、树已退出 | 瞬时错误 RETRY_WAIT，永久错误 FAILED；重启不重置预算 |
| 交接后崩溃、缺证据/证据损坏，包括仅观察到部分上传 | UNCERTAIN，不凭进度自动重传 |
| submit_intent 后断网/超时/5xx/响应不可解析 | unknown，禁止重发最终投稿或切换接口补投 |
| 平台明确拒绝且 code 已有“不创建稿件”的契约证据 | 白名单分类为永久失败或有限重试；未验证 code 为 unknown，HTTP 状态不够 |
| accepted 结果可靠保存但 Core 未提交 | 核验树退出后幂等入库，只查询、不上传 |
| 已人工处置/已建后继任务后收到迟到结果 | 追加迟到证据和冲突提示，不回写旧终态、不覆盖后继或撤销人工记录 |

预上传/分片/上传完成与最终创建稿件分开处理；禁止通用重试包住整个 upload 或最终 add。沿用审查后的 UPOS 有限预算，消除嵌套重试放大并记录实际请求次数；认证、参数和文件错误不做网络重试。最终 add 传输结果不确定即停止；只有已证明未受理的限流响应可在当前调用内有限重试。Core RetryPolicy 仅在表中安全条件成立时生效。

首版工程基线：预上传/分片最多 3 次重试（含首发共 4 次），上传完成最多 2 次重试（共 3 次），均限定在同一上传会话及已审核的可重试错误，去掉相同请求的第二层重试；最终 add 默认只发一次，明确未受理的限流白名单启用后最多再试 2 次，任何一次结果不明立即停止。沿用已核实的分片 240 秒、完成/投稿 60 秒请求超时；身份验证、封面和只读查询补齐 60 秒单请求上限，分页核验每轮限制页数/时间并返回是否完整。参数归引擎版本管理并用本地服务器验证，不是整项任务总时限；扫码有效期按平台响应处理。

### 19.3 账号提交锁与异常接管

- 统一引擎私有状态根下按平台与十进制 MID 建立固定锁域，不按昵称、Cookie 路径、Core account_id 或临时目录划分。首版单主机、配置的运行身份下，全部 Worker/维护入口共享该根；不承诺多个独立 Core 部署共享账号名额。
- Windows 使用固定锁文件字节范围的 OS 排他锁（LockFileEx），不用“文件存在”或“超过若干分钟删锁”。锁文件不轮换、不删后重建；持有句柄覆盖最终提交准备、intent、HTTP、响应证据及限流退避。上传时不持该排他锁，保留三任务并发。
- 等锁仍占原 slot，报告 waiting_submit，不新建引擎队列；不同 MID 独立。锁错误不能降级为无锁投稿，同进程也需互斥。
- 引擎本进程唯一负责投稿，锁句柄不传给无关子进程；显式释放或退出后由 OS 释放。后继必须真正取得锁，不能仅凭 PID 消失/计时认定；OS 延迟解锁时继续等待。[LockFileEx 依据](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)。
- 本地串行不能撤销已在远端处理的请求，也不提供远端 exactly-once。旧 Task 不确定时保留 UNCERTAIN；树退出后其他 Task 可继续，遵循既有名额与结果分离规则。
- 按已验证限流 code 保存账号 not_before、原因和当前调用重试次数，在锁保护下共享。服务端给有效等待时间则遵循，否则用引擎有限退避；无依据不虚构固定间隔。等待不受 Core 总时限；状态损坏报错而非无冷却，重启保留截止时间。预算耗尽返回明确拒绝或 unknown，不自建业务重试。

### 19.4 凭据维护、账号暂停与登录恢复

- Core 增加（platform, remote_user_id）唯一约束，MID 为规范化十进制字符串，经平台验证，不能凭文件名认定。Task 固定 account_id/预期 MID，修复凭据不改变任务身份。
- 手动启用与自动阻塞原因（凭据失效、登录/续期维护、待核验）分别持久化；领取须启用且无阻塞。维护结果只清除自己拥有且已解决的原因，不能覆盖并发手动停用、其他维护或旧代次消息。
- 登录/续期以操作标识和代次记录；短事务与 claim 竞争并暂停新领取，持久记录此前已领取的活动 Attempt 集合，允许它们交接/收尾，再等所有树（含等提交锁者）退出后写凭据，不能一边禁止这些 Attempt 执行、一边等它们结束。维护期间不启动新的普通查询用凭据进程，维护自身验证在排他锁内完成。交互登录在用户终端，不占上传 Task、不让 Worker 等扫码；租约到期不允许同时启动第二个登录。
- 增加跨进程凭据使用锁：上传/查询持共享使用权，登录、导入、续期持排他使用权；锁文件与凭据文件分离。维护暂停后等排他锁，不持共享锁升级；锁顺序为凭据使用权 → 投稿锁，维护不取投稿锁。
- 上传只读加载/验证，不调用上游可能隐式续期回写的 login_by_cookies。需要刷新时报告结构化维护错误，由 Core 按 Q6—Q8 暂停并等待后调用引擎非交互续期；失败提示重新登录。启动/维护后验证复用此流程，不新增定期业务调度。
- 新登录写操作专属临时凭据，验证 MID 后才能发布；重登错 MID 不覆盖旧凭据、不改账号。新登记遇同 MID 的唯一冲突转既有账号维护，不创建第二套名额。
- 凭据与 Core DB 无跨资源事务：先可靠发布版本化凭据和维护结果，再条件更新 Core 引用/状态。Core 提交失败保持暂停，恢复核验该版本，不重复登录或盲目回滚。旧有效版本保留为操作恢复依据。
- Windows 临时/新旧凭据及备份均有受限 ACL，写入 flush/同卷版本发布检查结果，不能靠 Unix 0600，也不先删旧凭据。替换失败按操作记录核对真实路径，不假定旧文件还在原名；见 [ReplaceFileW 错误语义](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)。首版不增加 DPAPI 格式。
- 登录取消、失败、终端关闭和 Core 重启保留失败记录；自动恢复必须满足 Q8 的登录进程退出、旧凭据有效且 MID 正确，网络未知仍暂停。Cookie/Token、扫码秘密、签名 URL、原始 HTTP body 不进入 Core 日志、事件或异常文本，只返回稳定错误码/脱敏摘要。

### 19.6 查询、回执与人工处置

1. 自动成功须关联本次执行、platform、经验证 MID、AID/BVID 中至少一个合法标识及投稿受理证据；取得两者则核对同一稿件。ID 格式、code=0 或退出码不够。缺 ID 时只查询补证，不再次 add。
2. 有 ID 时以同账号精确查询，验证所有者及本次稿件关联，保存查询时间/脱敏证据。无 ID 时按时间窗分页找候选并用远端视频键关联；仅标题、文件名、时间接近不能自动确认。多候选、分页不全、查询失败、无记录均不证明未投稿。
3. 审核刷新由用户主动查询；保存远端状态、最后成功查询时间及本次失败原因。失败不清空旧可靠状态，迟到查询按查询代次/开始时间条件更新，不能覆盖更新的观察；退回不改原 Task 成功。
4. UNCERTAIN 恢复可做一次有界核验，不是定期审核轮询。证据充分且树退出后由当前恢复所有者提交结论；不足保留 UNCERTAIN/候选，等待主动查询或人工处置，不无限后台扫描。
5. 人工成功需要可核验且属于本账号/任务的稿件标识；人工失败按 Q9 接受明确声明及非空理由/核验依据（允许人工检查记录，不要求伪造机器否定证明）；无法确认只追加记录。请求带 expected_task_version/幂等标识，保留操作来源、时间、理由、证据及 Task/Attempt 关联。
6. Resolution、Task、必要 Receipt 与事件原子提交；人工/自动核验竞争同一版本，不能双成功。原 Attempt 的 UNCERTAIN 不回写；无记录不自动调用人工失败接口，人工失败也不激活重试预算，只开放显式再提交。

### 19.7 文件、部署、新库与入口

- 引擎只读冻结快照指定的有序视频/封面，按作品目录和相对引用打开；在实际打开时核验句柄路径仍在授权目录、普通文件/可读，覆盖 Windows 大小写、Unicode、长路径、junction/reparse 越界；验证后沿用同一已打开句柄读取，避免校验后重新按可变路径打开。句柄路径准入不等于比较内容或提交前后 mtime/size；Core 预检查不能替代引擎检查。
- 不走 upload_by_config 的 glob，不复制、探测/预扫描媒体，不按文件变化复用旧 checkpoint，不清理原件。正常读取大小用于上传协议；源文件不冻结，变动按实际读取，缺失/权限/读取/上传错误如实返回。
- 绕开上游 UploadManifest/checkpoint 命名和复用路径：其中使用 SHA-256 和 size/mtime 比对，不符现有授权。执行证据直接使用 Core UUID execution_id/attempt_id 目录，不引入内容摘要替代方案。P1 继续核查保留调用图；若出现不可绕开且必须采用受限算法的情况，停止该分支再请用户授权，不把源码存在当许可。
- 配置明确 engine_executable、engine_build_id、协议版本、引擎状态/凭据根、Core 执行根和提交接口。绝对可执行路径、参数数组启动，不依赖作品输入拼接 shell 或 PATH 同名程序；结果路径由 Core 指定，不允许消息任意重定向。
- 按版本目录部署引擎，不运行中覆盖；新版本能力通过校验后用于新执行，活动 Attempt 保留构建身份。更新/回滚不自动跟随上游、不重写旧证据或快照，保留旧已验证构建，不隐式回滚数据库。
- 导入只处理已核对的上游受版控源码与来源记录，不搬入本机运行配置、凭据、数据库或媒体；导入历史与受版控配置也须检查敏感材料。遵守本项目不配置 CI 的约束，来源中的 workflow 不作为启用自动构建的授权，首次推送前确保不会触发上游自动化。构建依赖通过锁文件固定，工具链/目标平台记录在引擎交付说明。
- 新空库使用新版 schema，增加账号唯一身份、手动启用/维护原因、凭据版本引用、维护操作、交接时刻、真实回执/查询证据所需结构。实施统一落到 database.py 和生成契约，不靠 JSON 绕过唯一约束。已有库先只读核验版本/结构，再允许打开写路径；旧版/不完整库直接拒绝，不 create_all 补表、不改版本号放行、不借启动修改旧库或其 journal 配置。
- CLI 通过 REST 创建/查询/完成维护操作，在用户终端直接运行引擎交互登录；CLI 不写数据库，Core 不信任 CLI 自报成功，需核验引擎结果/MID/凭据版本。维护请求幂等，异常由操作记录恢复。
- 扩展账号登记/验证/启停/重新登录、稿件主动查询和真实人工处置 REST/CLI，复用 Application 和本机访问规则。实施时才生成 OpenAPI/JSON Schema；SDK/Dashboard/远程部署/监控子页面不纳入本轮。

## 21. 验收矩阵、测试阶段与通过标准

以下为验收设计，实际执行结果见第 23 节；Core 历史通过结果不能覆盖待实现的 Bilibili 契约。遵循[测试规范](../../docs/测试/README.md)，本次实施按适用阶段运行验证，真实投稿须限定获准账号和范围。

### 21.1 验证载体

- 单元/契约验证映射、选项、证据及判定，不只断言函数被调用。
- Core 集成使用真实临时 SQLite、多 Worker、独立 Fake Engine Fixture、Windows Job 和现有 REST/CLI 入口。
- 引擎集成使用真实裁剪 Rust 引擎及本地协议服务器，独立记录请求到达、受理 ID、响应丢弃，证明引擎实际重试/锁/凭据行为；Python Fixture 不替代 Rust 测试。
- 真实平台只用获准账号/合成媒体验证单 P/多 P/发布/查询，不自动删除远端稿件。超时、限流、坏响应、磁盘故障优先本地注入，不靠真实风控制造故障。
- 用事件/管道/数据库屏障卡故障窗口，不靠 sleep 猜；持独立进程句柄核验退出，不用再次调用被测恢复函数证明。证据存仓外独立轮次目录，保留失败现场。

#### 首次实测如何进入正常上传流程

正式引擎 `bue-0.2.0-dev1` 声明 `upload_ready=false`、`verified_publish_modes=[]`。Core 登记、预览、提交作品时检查发布能力，Worker 发送上传请求前也会复核。普通入口遇到未验证的发布方式会返回 `409 UNSUPPORTED_OPTION`。手改能力文件会让其他任务也误以为可以投稿。带 `-fixture` 的构建仅供本地模拟，真实账号使用正式引擎。[Core 作品校验](../../src/upload_platform/application/service.py) · [交接前复核](../../src/upload_platform/adapters/bilibili/mapping.py) · [引擎能力说明](https://github.com/kachekakaka/bilibili-upload-engine/blob/19629b58e8589c9ea54a6c34798029f78f460a7f/ENGINE.md)

本机专用部署通过引擎配置中的 `b18_allowlist_file` 载入仓外清单，绑定本轮编号、专用数据目录、固定构建、一个 MID 及两份作品。Core 在登记、预览和创建任务时检查作品。SQLite 在同一写事务中为每份作品登记唯一任务。Worker 依据冻结快照，在交接前再次核对清单和多 P 的前置查询。每份仅允许一次手动立即任务，单 P 成功受理并单独回查命中后才放行多 P。真实验收沿用 CLI → Core REST → Worker → 正式引擎。[配置与关闭方法](../../docs/operations/bilibili.md#b18-受控投稿入口) · [清单示例](../../docs/operations/b18-allowlist.example.json)

执行前明确获准的测试账号、可公开的合成短片、分区和自制或转载类型。用 `upload-platform work prepare --dir <作品目录>` 为两份作品分别生成编号，在各自的 `upload.yaml` 填写可公开的标题、简介、标签和可选封面。每份只启用一个目标，填写 `platform: bilibili` 和 `account: bilibili:<目标 MID>`。在目标的 `options` 内填写分区 `category_id`、类型 `copyright` 和 `publish_mode: public`。转载另填 `source`。

| --- | --- | --- |
| 单 P | 一个视频，一个 `independent` 上传单元，事先记下总标题和分 P 标题 | 一个 Task 对应一份稿件，稿件内恰有一个视频 |
| 多 P | 一个 `multipart` 上传单元，按 A、B 顺序列出两个画面和分 P 标题都易区分的视频，共用一个总标题 | 另一个 Task 对应另一份稿件，同一稿件内先 A 后 B，各自标题正确 |

#### 执行与核对

1. **认准部署和账号。** 如使用 mumu 已登录的账号，选择当时的专用 Core 数据目录及对应引擎配置。核对 CLI 的 API 地址、Server 和 Worker 的数据目录、正式引擎与私有状态根。通过 `GET /api/v1/accounts?view=summary` 确认目标 MID、账号已启用且 `availability=ready`。账号不符、已有无关任务会被领取或部署归属不明时停止。换部署时通过该部署的登录入口登记账号。确认专用部署就绪后启动或复用其 Worker，用 `upload-platform doctor` 核对 API、数据库和 Worker 的状态。
2. **登记并看预览。** 下列 CLI 子命令均以 `upload-platform` 开头。对每个作品目录执行 `work register --dir <作品目录>`，再执行 `work preview <作品编号>`。把目标账号、分区、类型、公开方式、整稿信息及有序分 P 与上表逐项核对。新作品应只有一项 `create_new_submission`。若显示 `reuse_current`，先查该作品的原任务，避免重复发稿。[作品目录与 CLI 入口](../../docs/operations/core-mvp.md#准备登记与提交作品)
3. **先发单 P。** 预览相符后，对单 P 执行一次 `work upload <作品编号> --max-attempts 1`。记录请求编号和 Task 编号，用 `task status <Task 编号>`、`task attempts <Task 编号>`、`task events <Task 编号>` 查看交接、执行和收尾。CLI 提交响应丢失时使用 `request resume <原请求编号>` 找回同一请求。
4. **按稿件号回查。** 核对原 Task 已成功（`SUCCEEDED`）、执行树已退出，真实回执含本次 MID、有效 AID 或 BVID、按序的视频键及查询证据。执行 `task query <Task 编号>` 发起一次主动查询，用 `task queries <Task 编号>` 查看记录。查询应命中同账号、同稿件和相同的视频顺序。再用该账号在 B 站创作中心按回执的稿件号打开详情，对照预览核对总标题、分区、稿件类型、公开设置、分 P 数量、标题及顺序，并核对所填的简介、标签和封面。审核状态和查询时间单独记录，待审稿件也可以核实平台已经受理。[查询与回执语义](#196-查询回执与人工处置)
5. **再发多 P。** 单 P 的回执、回查和远端内容均吻合后，对多 P 作品重复以上提交和核对。确认两个分 P 同属第二个稿件号，按预览顺序分别显示 A、B 的画面和标题，且该稿件号与单 P 不同。本轮实测范围为这两份投稿及其查询，远端稿件保留。

#### 结果、证据和停止条件

- **通过。** 两份作品各有一个 Task、一份平台受理回执和独立回查记录，创作中心与预览一致。分别记录受理和审核结果。两项均通过后，复核矩阵其余适用项，再为对应的正式版本声明已验证的 `public` 能力，其他发布方式另行验收。
- **失败或结果不明。** 交接前遇到账号、素材或选项错误时记录原因和未执行的步骤。已发出最终投稿后遇到异常响应、缺少可靠 ID、查无记录或多个候选时，按原任务做有界查询或人工核对，保留原 Task、Attempt 和错误。受理情况仍不明确就保留 `UNCERTAIN`。若已有可靠回执、只是主动查询失败，则保留受理结论，单列回查待补。遇到这些情况或远端内容不符即暂停后续投稿。原多 P 已明确未投稿且单独获准时，按[补测入口](#2310-b18-多-p-补测)追加唯一后继任务。
- **留证。** 在仓外 `fileUploadPlatform_tmp/` 的本轮专属目录记录日期、部署与构建、作品编号、请求/Task/Attempt 编号、预览、稿件号、远端核对结果、审核状态与查询时间。每份分别标记通过、失败或未执行，并注明阻断原因或待核事实。仓内只写脱敏摘要和证据位置，二维码、Cookie、Token 和凭据文件不进报告。完成或暂停后关闭本轮准入。
