# mumu 界面扫码登录接入方案

## 1. 目标与范围

用户在 mumu 的账号页面点击“添加 Bilibili 账号”或“重新登录”，页面内显示二维码；手机确认后，页面显示已核验的账号和可用状态。整个用户流程不要求打开终端、输入命令、导出 Cookie 或手动启动登录引擎。

Core 服务托管登录会话和引擎进程。mumu 的本机后端调用 Core，账号页显示二维码和登录状态。Core 负责账号登记、维护互斥与恢复，登录时无需启动上传 Worker。

2026-11-17 本项目完成 P1—P3 的 Core/引擎实现与本地验证，历史结果保留在第 13 节。11 月 18 日，mumu 项目完成页面、桥接和本机启动接入，并用真实账号走通扫码流程。[本机真实扫码验收](#14-本机真实扫码验收)

关联：[需求 R01/R08](../需求说明.md)、[设计 D02/D05/D06](../设计说明.md)、[Bilibili 集成与自维护方案](20261116-Bilibili集成与自维护方案-v1.2.md)、[现有登录操作](../operations/bilibili.md)。本方案补充图形化登录，不替代原方案的上传、查询及真实平台验收。

本方案范围（本轮授权仅覆盖 Core/引擎及对应文档）：

- 引擎结构化扫码交互、Core 托管会话、状态查询、二维码读取、取消与恢复接口。
- 同机 mumu 接入契约、无终端启动约定和页面交互流程。mumu 侧实现归属见第 10 节 P4。
- 保留现有账号互斥、独立身份核验、凭据版本、同 MID 唯一账号和原账号失败恢复规则。

不纳入：远程部署、多用户权限系统、浏览器直接访问 Core、平台密码/SMS 登录、Cookie 导入界面、完整 SDK/Dashboard、上传调度规则变化、自动投稿或删除远端稿件。现有终端登录作为兼容入口保留。

## 3. 职责与取舍

| 层次 | 建议职责 |
| --- | --- |
| mumu 界面 | 发起/取消登录、显示二维码和非敏感状态、恢复已有会话、成功后刷新账号；不持有凭据、不生成引擎命令 |
| mumu 本机接入层 | 按固定目标访问 Core；转发白名单 DTO 和二维码字节；沿用 mumu 自身页面访问控制；按可信安装配置复用或启动 Core |
| Core API 内的登录协调器 | 原子创建维护与会话、独占启动、持有 JobHost、处理 MID 协调、收尾核验、取消竞争与恢复；不依赖浏览器连接或 Worker 驱动 |
| Bilibili 引擎 | 请求二维码、轮询平台、核验身份、在既定锁域内发布凭据；机器模式输出结构化扫码信息；敏感平台轮询材料只留在引擎 |

推荐 Core 托管而非让 mumu 持有引擎进程：页面或 mumu 重启后仍能查询同一操作，也避免在 mumu 再实现一套维护互斥与凭据提交规则。代价是 Core 需要新增登录协调器和恢复逻辑，不能只加一条二维码图片路由。

协调器属于现有 API 进程中的显式登录操作执行器，不新增独立常驻服务、上传队列或扫码定时调度。首版采用单 API 进程部署；跨进程启动竞争仍由数据库条件更新与持久进程身份防护，不用“单线程假设”替代幂等约束。

已验证的部署使用同一台 Windows 电脑。Vue 账号页经 mumu 的 FastAPI 后端访问本机 Core，账号操作限于该电脑的本机控制台。

## 4. Core 公开接口

下表路由均相对 `/api/v1`，Core 侧已落地并由实际模型生成 OpenAPI，精确字段以 [schemas](../../schemas/README.md) 为准。现有低层维护 API 保持 CLI 兼容，GUI 会话由协调器内部复用业务方法，mumu 不调用 start/process/identified/complete。

| 接口 | 请求与返回 | 关键语义 |
| --- | --- | --- |
| `GET /system/capabilities`（新增） | 返回 `gui_login.version=1`、是否可用、安全不可用原因、支持平台；与现有 health 配合 | 依据实际引擎机器扫码能力判断；二维码登录能力和 `upload_ready` 分开，旧服务返回 404 时显示需升级 |
| `POST /account-login-sessions`（新增） | `{platform:"bilibili", account_id:null或已有ID}`；202，返回 `session_id`、`operation_id`、安全状态及查询路径 | 持久接受即返回，不等扫码；同一事务创建原维护操作与托管标记；不接收 EXE/数据目录/Cookie/任意 import_file |
| `GET /account-login-sessions/{id}`（新增） | 下节状态 DTO | 只读，不隐式启动、不生成修改请求记录；UI 轮询建议 1 秒，失联指数退避至 5 秒 |
| `GET /account-login-sessions?active=true`（新增） | 有界安全摘要列表，支持 `account_id` 筛选 | 供页面刷新、mumu 重启时找回已有会话；不返回旧二维码或内部执行记录 |
| `GET /account-login-sessions/{id}/qr?challenge_id=…`（新增） | `image/png`；状态可读但尚无二维码时 409，挑战已失效时 410，未知会话时 404 | 返回引擎产出的二维码图像；挑战 ID 是非敏感不透明标识，URL 不包含真实扫码 URL/令牌 |
| `POST /account-login-sessions/{id}/cancel`（新增） | 空 JSON；202 表示已登记取消意图，或 200 返回已结束快照 | 不承诺扫码立即撤销；最终结果以收尾核验为准；已进入可靠完成阶段时返回 409 `login_finalizing` 及状态 |
| `POST /account-login-sessions/{id}/resume`（新增） | 空 JSON；202/200 返回同一会话 | 只恢复监督与证据收尾，不自动获取新二维码、不新建凭据版本、不重开登录 |

新增 `GET /accounts?view=summary` 的白名单视图，供 mumu 在登录成功后刷新账号。原 `/accounts` 默认返回保持兼容；summary 仅含 id、platform、reference、remote_user_id、display_name、enabled、可用状态和安全阻塞原因，不暴露 credential_reference、路径、原始维护结果。可用状态应区分“登录成功但手动停用/另有阻塞”，不把登录成功显示成所有任务均可运行。

修改请求沿用 UUID `Idempotency-Key` 和 JSON Content-Type。创建重试用原 Key，正文变更返回 409；同一 Key 永不创建第二个引擎，即使原会话已过期。普通响应只保存非敏感内容，因此可以复用现有幂等记录。轮询 GET 才是最新状态来源，幂等重放的旧响应不应让 UI 状态倒退。

同账号已有 CLI/GUI/自动维护时返回 `maintenance_active`，带可恢复的安全操作摘要。未确定 MID 的新登记在同一平台只允许一个活跃扫码登记：与 CLI 共用检查，避免多个引擎堵在 registration 锁后隐藏等待；不得持锁期间擅自杀掉另一登录。不同已知账号继续沿用各自的维护域。

“刷新二维码”首版采用**结束旧会话后显式创建新会话**：失效/失败/取消必须完成退出核验及旧账号恢复后，新点击使用新 Key。旧会话未安全收尾则返回冲突，不设计一个在活跃引擎内无约束换码的接口。每个会话最多一个二维码挑战。

### 4.1 安全状态 DTO

建议字段：`session_id`、`operation_id`、`platform`、`account_id`、`revision`、`phase`、`outcome`、`created_at`、`updated_at`、`can_cancel`、`can_resume`、`can_retry`、`challenge`、`account_summary`、`error`。时间使用 UTC RFC 3339；revision 为单调递增整数，不计算内容摘要。

- `phase`：`queued`、`waiting_for_executions`、`starting`、`waiting_confirmation`、`verifying_identity`、`waiting_for_account`、`finalizing`、`cancelling`、`recovering`、`finished`。这是会话展示阶段，不改写原 Task/Attempt/Account 领域状态。
- `outcome`：进行中为 null，结束为 `succeeded / cancelled / expired / failed`；缺乏退出或身份依据时继续 `recovering`，用安全原因说明需要恢复，不假装终态。
- `challenge`：可用时含非敏感 `challenge_id`、内部图片路径、`expires_at`（平台有可信期限才填）、`deadline_at`（本机会话截止）和 `expiry_source`。其他阶段为 null；不能把本地截止时间标成平台确认的过期时刻。
- `account_summary`：成功提交并独立核验后才出现；只有扫码确认消息不够。
- `error`：稳定码、可显示中文消息及安全请求标识；不透传平台 body、签名 URL、原始 exception 或 stderr。

页面只接受更高 revision；图片请求还要匹配当前 challenge_id。终态响应或失效时立即撤下二维码。显示文案不要求平台能区分扫码与确认：未经证实只显示“请在手机上扫码并确认”。

## 5. 引擎协议补充

现有 login 请求已加入可选 `interaction_mode: terminal | machine`，默认 terminal；machine 要求显式能力 `login_interaction.version=1`。Core 在启动前核对能力/构建版本，不向旧引擎发送新字段后再猜测降级，也不解析终端图案作为兼容办法。增加机器能力使用新 build_id；不原地替换现有生产版本目录。

机器模式复用现有登录协议，新增白名单 NDJSON 消息：

| 消息 | 内容与用途 |
| --- | --- |
| `login_qr_ready` | protocol/interaction 版本、build_id、operation_id、递增 seq、challenge_id、PNG base64、可证实期限；PNG 由引擎根据扫码 URL 在内存生成，不暴露 auth_code |
| `login_progress` | 同一身份关联与安全阶段；不含扫码 URL、Cookie、Token、原始平台返回 |
| `account_identified` | 继续现有持久身份核验及 `maintenance_ready` 协调，不把 stdout 身份提示直接当作允许写凭据的依据 |
| 最终维护结果 | 仍使用当前受保护文件和独立 validate/退出核验；不靠 UI、stdout 或退出码判成功 |

扫码消息属于敏感交互通道：Core 严格校验 operation/build/seq/challenge、内容类型和长度，拒绝旧代次消息和未知字段；首版图片不超过 128 KiB，单消息上限 192 KiB，受限缓冲只保留当前挑战。此限额应单独用于登录协议，不扩大上传协议或通用日志限制。直接生成 PNG，不返回可执行 HTML/SVG，不提供任意 URL 图片代理。

底层 `get_qrcode` 与 `login_by_qrcode` 拆分出安全状态回调/轮询适配，平台 auth_code 始终留在引擎内。已知过期、拒绝、网络失败分别映射稳定码；未知码只报告 `login_platform_error`，不能猜成过期。当前源码没有足够证据承诺所有细分状态，实施时以固定版本及受控真实扫码验证补齐映射。

拟设本机扫码等待上限 180 秒，若平台给出更早的可信截止则取较早者；这是登录会话的本地资源边界，不是平台期限声明，也不套用到上传或维护等待旧执行的总时限。无平台明确过期时，本地超时用 `login_local_timeout`，不显示“平台已撤销授权”。前置等待旧执行期间尚不生成二维码；新登记识别已有 MID 后的等待继续原维护规则。

扫码图像/原始 URL 不写维护结果、事件、Outbox、请求幂等缓存、stderr 日志或追踪系统。Core 只内存暂存 PNG，最终、失效、取消收尾或服务关闭时释放；刷新页面时可读取仍活跃的同一图像，重启后不靠磁盘二维码恢复。机器模式 stderr 继续有界脱敏排空，禁止终端输出二维码。

## 6. Core 托管、持久化与恢复

优先在 account_maintenance.execution 内新增有版本的 `login_session` 元数据：托管标记、phase/outcome/revision、challenge 的非敏感标识和期限、取消意图时间、协调器所有者及代次。`session_id` 可直接使用维护 operation_id，不新增第二套可分叉的业务主键。原 account_maintenance 状态枚举与 schema v2 物理结构不变；cancelled/expired 映射到原维护 FAILED 并保存明确原因，不能让客户端把它等同于账号失效。

所有推进、取消意图和代次判断通过短事务条件更新；网络等待、进程等待、独立验证均在事务外。元数据不存 PNG/URL/auth_code。服务升级时拒绝未知交互版本；降级不得由旧代码接管活跃 machine 会话，应先排空或显式恢复，不能仅因物理 schema 相同就宣称兼容。若实施发现必须改变表结构，另行补充数据库方案；不自动迁移现有库或回退凭据引用。

协调器遵循已实现的创建顺序：持久启动意图→挂起创建可信 EXE→加入 Job→持久 pid/creation/boot 身份→恢复线程。由 Core 持有管道和 Job；不用 shell，不继承控制台，Windows 无窗口启动必须有实际验证。GUI 操作的低层 process/identified/complete 外部入口拒绝客户端驱动；原 CLI 操作仍走原路径，双方共用账号互斥。

已登记账号重登：先暂停新领取，等旧执行和查询安全退出，再生成二维码。新登记识别已有 MID：沿用 identified.json 的独立核验，绑定原账号维护域并等待，再发送 maintenance_ready；不新建重复账号或第二组并发名额。完成时独立验证新凭据版本/MID，事务提交账号引用；失败时独立验证旧凭据，只有有效才恢复，手动停用和其他阻塞保持。

服务重启后先恢复监督，不能自动再次扫码：

1. 启动意图尚未产生进程时，只有能证明没有旧树才允许推进一次启动；创建中间窗口身份不全则保持恢复状态。
2. 正在扫码时管道和内存图像无法重新接续：不再展示旧图，确认旧进程身份后受控停止该登录树，核验结果及旧凭据再结束；只有其后用户才能新开二维码。
3. 已发布凭据/结果或处于 Core 提交窗口时，优先收尾既有操作，不能因会话图像丢失重登。提交失败保留待恢复状态和版本，resume 重用该版本。
4. 无可靠进程树退出证明时保留账号暂停；不能用超时、PID 不存在或图片消失当作已退出。原有机器重启证据规则继续适用。

重启和关闭只操作确认属于该会话的进程，不结束上传或其他维护。普通网络轮询中断不停止登录；Core 与引擎 stdout 的敏感通道断开必须进入失败/恢复处理，避免无人监督继续发布。

## 7. 取消、页面关闭与竞争结果

- 等待且尚未启动时：取消事务与启动领取竞争，取消胜出后禁止创建引擎，收尾原账号暂停。
- 已启动时：先持久取消意图，再停止确认为本会话的进程树；`202` 仅表示受理意图。退出未证实时继续显示“正在取消/需要恢复”，不开放下一次重登。
- 取消与平台确认/凭据发布并发：先核验持久结果及退出证明。若已形成可靠成功版本，则完成同一操作并返回实际成功，界面提示“取消未生效，账号已登录”；不删凭据、不回滚成功、不伪称平台授权已撤销。尚无可靠成功时按原失败恢复规则验证旧凭据。
- 已进入可靠收尾时返回 `login_finalizing`；`can_cancel` 仅为当前提示，不替代服务器竞争检查。重复取消幂等，终态不反转。
- 关闭扫码弹窗与“取消登录”区分：关闭只隐藏，显示仍进行中的账号提示，重新打开可继续；显式取消才提交 cancel。页面刷新、mumu 退出或短暂断网不会被当作取消请求，扫码仍受本机截止约束。服务关闭按上一节恢复，不自动登录。
- 到期与成功同时发生时也按持久证据收尾；本地界面倒计时只能触发重新查询，不能自行写失败终态。

## 8. mumu 接入流程与无需终端的启动

1. mumu 本机接入层核对已登记部署的进程归属，再查询 Core 的 health 与 capabilities。能核实归属的兼容实例可以复用，未知服务占用端口时提示冲突。扫码无需 Worker。
2. 若没有 Core，受信任的本机启动入口按固定安装配置无窗口启动 Core，等待有界就绪；重复点击共用启动锁并复查端口/版本。端口被其他程序占用或配置/版本不符时展示错误，不杀进程、不另起空库、不自动覆盖部署。禁止由页面提供命令、EXE 路径或环境变量。
3. 页面进入账号区先查活跃会话；点击新增/重登时接入层创建会话，保存非敏感 session_id 与幂等 Key。连接中断后使用原 Key找回结果，不再开第二次登录。
4. queued/waiting 阶段展示等待原因；二维码可用后读取 PNG，以受控 Blob/图片显示于 mumu 页面。图片加载失败只重取当前 challenge，不能自动刷新登录。
5. 页面轮询状态；确认后显示“正在核验账号/保存登录信息”，只有 outcome=succeeded 才显示成功并刷新 accounts summary。显示账号 MID、昵称、启用及阻塞状态，不显示内部版本路径。
6. 失败或到期说明原因，can_retry=true 时提供“重新获取二维码”；恢复中提供 resume，不能把恢复按钮实现成重新登录。
7. 登录成功后 mumu 后续上传引用 Core account id/reference；上传引擎不由 mumu 直接调用，凭据由 Core/引擎现有边界管理。登录成功不得自动提交任何上传任务。

mumu 账号页提供部署配置、启动登录服务、添加或重新登录账号，以及从操作记录找回会话的入口。操作步骤由 [mumu 运行说明](../../../mumu_lbcut_tool/docs/最小调度运行说明.md#在账号页扫码登录-bilibili)维护。

Core 的退出由本机服务生命周期入口管理，不随扫码弹窗关闭而停止；mumu 若复用已有服务，不在退出时停止它。由 mumu 自己启动的服务也不得在有上传或未收尾维护时强杀；首版优先保留本机服务运行，提供可说明阻塞原因的停止入口属于后续生命周期细化，不把该入口作为扫码界面上线的前置。

## 9. 本机访问与敏感数据边界

保留 Core 的 loopback、固定 Host 和拒绝浏览器头规则。拟仅在新增 GUI 会话接口、summary 与能力读取约定上支持受信任接入层；修改请求新增明确的 `X-Upload-Platform-Client: gui-bridge-v1` 标识，旧路由的 CLI 标识规则不整体放宽。该标识不是身份认证，不能以此声称隔离同机恶意进程或支持远程多租户。

mumu 页面只经同源后端访问限定的账号路由。本机桥接层检查连接对端、Host、浏览器来源及短期页面凭证，二维码经受控的 PNG 路由返回。现行访问规则见 [mumu 控制台接口契约](../../../mumu_lbcut_tool/docs/控制台接口契约.md#本机-bilibili-账号)。

二维码本身也是登录敏感材料。图片与状态响应使用 `Cache-Control: no-store`，图片加 `X-Content-Type-Options: nosniff`；mumu 代理同样禁缓存，不放入 localStorage、Service Worker 缓存、遥测、错误截图附件或日志。Blob URL 在替换/隐藏/终态时释放。只允许在当前受信任 UI 显示，不提供下载/分享二维码或外部二维码渲染服务。

会话 ID、challenge_id 不携带凭据；第三方平台响应和完整扫码 URL 不进入 HTTP 查询参数、审计消息、OpenAPI 示例或测试报告。既有凭据根的 ACL、版本发布与备份规则继续有效。
