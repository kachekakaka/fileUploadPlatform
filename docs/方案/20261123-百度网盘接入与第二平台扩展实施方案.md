## 1. 目标与交付定位

本轮使 fileUploadPlatform 能独立将本机选定的普通文件或文件夹上传到百度网盘。用户在 Dashboard 选择本地输入、百度账号和网盘目标父目录，预览实际文件树后统一提交；平台提供逐文件结果、目录结果、部分完成汇总、可靠恢复和远端回执。

默认保留原文件名、选中的顶层文件夹及其内部层级。例如选择 `D:/资料/项目A`，目标父目录为 `/备份`，则上传到 `/备份/项目A/...`。目录由用户选择或输入，每个账号记住默认及最近使用目录；不默认把 Work、Unit 或 Asset ID 拼进网盘名称。

推荐按现有 B 站模式，**将 BaiduPCS-Rust 必要协议源码抽取到我们独立维护的百度引擎仓库，编译为受监督的本机执行程序**。P0 先验证固定上游版本，再验证最小抽取可独立构建和执行。上游 HTTP/WebSocket 可用于探针观测；正式接入优先复用 B 站的进程监督与结构化消息形态，具体百度消息在 P1 固定。登录、提交与任务页面仍由本平台提供。[S14] [S15]

BaiduPCS-Go 为轻量备选；官方 OAuth/API 保留条件分支。是否最终采用某个引擎，由受理幂等、账号隔离、冲突与恢复验证决定，不因已有 GUI 或能传一个文件就宣称满足 R09。[G2] [G5] [R1] [R2] [R3]

Core 继续作为唯一业务任务权威，沿用 Work、Task、Attempt、Receipt、Event、统一提交和 Windows 进程监督。新增通用文件资产及 `file_set` 单元，同时保留现有 B 站视频投稿模型，不能把任意附件伪装成 `videos`。[S1] [S2] [S7] [S13]

MuMu 本轮保持现有录制、generated YAML 和 iframe 接入。平台支持百度，不等于 MuMu 已会生成百度目标；MuMu 多目标模板和一对多交付关联属于后续迭代。

## 2. 已确认范围与技术验证条件

### Q1 应用条件：改为技术路线的条件事项

“百度账号”是拥有网盘文件的个人账号；“开放平台应用”是开发者登记的软件接入身份，可包含 AppKey、SecretKey、获准权限和应用目录。它们不是同一件事，也不是注册网盘账号后自动就具备开发者应用。

本方案推荐先验证 Rust 的扫码会话路线。这条路线使用用户自己的百度账号授权，凭据留在本机后端，**不把用户已拥有自建开放平台应用作为前置硬条件**。若后续改用官方 OAuth/API，才需要核实部署者可用的应用、权限、授权方式和可写目录。[G5] [R1] [E1] [E2]

官方材料对开发者准入及体验密钥有不同说明，不能据此保证某个个人应用已具备正式权限。该事项在实际选择官方路线时核实；不用公开体验密钥冒充正式接入，也不把共享 SecretKey 内置进分发包。Q1 当前不是要求用户立即完成的产品选择。

### Q2 百度协议 MD5 与续传一致性：已确认

**用户于 2026-11-23 明确接受以下有限例外：**

> Core 登记、预览和统一提交不扫描文件内容。仅在百度执行阶段，为所选文件准备百度协议必需的 MD5；跨进程续传前，允许重新读取当前任务所选文件并核对协议分片清单，必要时再次读取整份文件。用途限于百度协议和同一上传会话的一致性，不用于作品编号、全局去重或其他平台，不引入 SHA-256、全盘内容扫描或额外完整副本，不承诺提交时文件内容的字节快照。

现行 R02 和 ADR 0001 对额外摘要、整文件扫描及提交后变化比对有限制，本次接受的是上述明确例外，不能因计算发生在 Adapter 或第三方库中就扩大范围。若所选引擎另算非必需的整文件摘要、创建内容缓存或副本，应关闭；确有协议必要性时先在实施记录说明具体读取和用途，超出已接受范围的部分另行处理。[S1] [S3] [E5]

枚举用户明确选择的文件夹及读取文件名、类型、大小等目录元信息，是生成固定清单所需操作，不等于获得扫描其他目录或全盘文件内容的许可。实际代价包括首次上传前读盘，以及恢复时可能再次读盘。发现分片清单变化后停止旧会话复用；原远端结果不明时保留待核验状态。

Q2 的接受仅覆盖上述协议读取范围；数据交付范围已另按 Q3 确认。本轮没有执行登录、真实上传或数据库迁移。

### Q3 数据与部署：已确认开发 A、正式 B

**用户于 2026-11-23 明确确认：“开发测试用 A，最终日常交付用 B。”**

| 阶段 | 已确认安排 | 交付边界 |
| --- | --- | --- |
| A 开发测试 | 独立私有目录、数据库、运行状态及受控进程；需要服务端口时与日常实例隔离 | 进行引擎验证、故障测试和升级副本演练；测试实例不自动继承旧业务记录，不切换 MuMu 日常绑定 |
| B 正式日常交付 | 升级当前基线数据，保留账号、作品、任务/Attempt、回执、台账、原请求结果、定时、事件及部署身份 | 纳入一步升级、配套私有文件备份、演练和回退；通过验收后交付 |

Q3 已不再是待选项。原 DB-MIGRATION 暂缓记录只对本轮明确纳入的当前基线一步升级调整，不扩大成全部历史版本兼容框架。本次确认解决方案范围，本轮对话未实际修改数据库。[S4] [S5]

**Go 必须按版本区分。** 最新发布 v4.0.2 为 2026-08-21，该发布版没有后续恢复的上传断点能力；main 已于 2026-08-25 的提交 `ab0e7996f24a25a518a4f227af60052c12fc488c` 恢复上传断点支持。核对时 main HEAD 为 `1b9131817aaf8ca7dee24bc00e33ebc4c7a5cc73`。不能继续笼统写“Go 不支持续传”，也不能拿 main 的能力保证旧发布包。[G2] [G6] [G7]

**Rust PoC 固定到 v2.4.1 的源码提交 `2906b6a67103dc56649efa25cb17397d0bd4a866`**，该版本发布于 2026-11-10。此前核对的 main `f84481595b6ae0ce4824dab5d9c8426f0a42235e` 与此提交文件树相同；已查阅的源码结论可对应到该版本，但未运行其发行二进制、未登录真实账号。正式交付仍需记录构建来源、桥接补丁和校验值。[G8] [G9]

推荐 Rust 是因为其现有扫码、上传与持久恢复实现可供验证和抽取。上游仍是完整应用，其 lib.rs 和 Cargo 依赖包含 Web 服务、下载、备份等模块，不能把公开模块直接等同于可无依赖抽出的稳定 SDK。P0 同时评估抽取成本；正式维护形态见第 6.4 节。[R7] [R8]

已审查源码中，任务创建、自动调度、账号绑定、文件夹枚举及恢复仍需与 Core 约束衔接；恢复为 Paused 有利于受控接管，但不能单独证明整个恢复链可靠。[R1] [R2] [R3] [R4]

空目录和 0 字节文件尤其不能按“已有递归上传/分片恢复”推断已覆盖：Rust 的文件夹扫描不生成独立空目录项，`total_chunks == 0` 的恢复校验也存在缺口；Go 当前目录扫描会跳过目录节点和 0 字节文件。二者均须通过本方案专门用例，必要时做最小修补；未通过则不标完整支持。[R3] [R4] [G10]

## 4. P0 接入与引擎可行性验证

P0 验证路线和最小抽取是否可行；正式受理、执行及恢复契约分别在 P1 设计、P2/P3 实现验收。P0 使用 A 隔离环境、固定样本、临时稳定操作 ID 和私有证据，不依赖尚未实现的百度 Target、file_set 或新版 Core 账号表。探针协议可以随后调整，不直接冻结为正式消息 Schema。只运行上游原版界面不能证明源码抽取可行。

### 4.1 P0 必须完成的实证

| 验证项 | 最小实证与必须记录的结果 |
| --- | --- |
| 固定引擎与最小抽取 | 记录来源、许可证、依赖；原基线及最小抽取均可独立构建、启动和停止；明确可保留与需解除的应用层耦合 |
| 授权与稳定身份 | 实际完成所选授权，取得真实 UID/owner_uid；观察会话重开、失效及换号行为，确定会话能绑定指定账号 |
| 路径与文件类型 | 实测获准范围的目录列表、目录创建、普通文件上传及查询；记录层级、空目录、0 字节和代表性名称的实际表现及限制 |
| 文件冲突与成品请求 | 实测同名冲突，定位快速上传、预创建、最终合并等成品路径；记录服务端不覆盖条件、并发窗口、响应与错误字段，区分已证实、可修补及无法支持的情况 |
| 跨进程恢复机制 | 至少一次在上传中真正退出进程，确认旧执行停止后重启；验证固定未变化样本的原 uploadid/分片能否恢复，记录实际复用和缺口；暂停/继续按钮不算此项证据 |
| 摘要、输入和结果证据 | 追踪必要读取、摘要、checkpoint 字段及原成功响应；确认执行样本遵守 Q2，记录源变化保护、操作关联及结果查回的不足 |
| 官方路线条件，仅选用时 | 验证自有应用、获准权限、实际授权方式和可写目录；记录令牌换代行为，不使用体验密钥冒充正式能力 |

空目录、0 字节或上游恢复保护存在可修补缺口时，应保留失败证据和具体改动位置；P0 可以据可实现的补丁设计继续进入 P1，不把该能力标为已通过。对无法取得关键证据的环境，记为阻断，不能用源码推断替代真实实证。P0 探针不得因尚未实现产品保护而扩大到日常数据或一般用户输入。

### 4.2 P0 必须给出设计、在后续阶段正式验收的内容

| 待补能力 | P0 需要定位和说明 | 正式设计与验收 |
| --- | --- | --- |
| 持久受理及原操作查回 | 请求进入内存、落盘和调度的先后；operation_id、不可变输入和丢失回复的桥接位置 | P1 固定消息/持久模型；P2 验收幂等受理、查询及受理与开始分离 |
| 执行所有者、账号隔离与许可 | 会话绑定方式、进程边界及未经许可自动执行的入口；给出受控改造方案 | P1 固定 Task/DirectoryOperation 身份；P2 验收监督、代次和账号隔离 |
| 源清单一致性与完整恢复 | 原分片清单、必要摘要及会话配置是否持久；列出恢复前复核和不可变参数补丁 | P1 固定证据关系；P3 验收 Q2 范围内的源复核、接管及恢复 |
| 目录依赖、取消与成品失联 | mkdir、提前成品、合并和自动重试的副作用位置，原响应与查询的证据能力 | P1 固定目录执行和批次契约；P3 验收取消竞争、失联核验和部分完成 |

Rust 原有 HTTP 创建任务能被调用，并不自动具备上述正式保障。P0 要给出实现路径、依赖与成本，不要求在正式契约确定前完成整套产品受理和恢复系统。[R1] [R2]

### 4.3 P0 退出与路线阻断

P0 通过要求：完成 §4.1 的最小实证，形成可独立构建的抽取样本，并为 §4.2 的差距给出代码落点、改动范围、验证归属及可接受的维护成本。关键协议限制没有可行解法、远端副作用无法控制、无法取得必要证据或抽取成本不可接受时，停止当前路线并评估备选。已知可实现补丁允许后续开发，不等于功能验收完成；正式开放能力前仍须通过 P2/P3 及相应验收用例。

官方 FAQ 关于设备码、本地回调和 `/apps/应用名称/...` 的说明，仅约束官方路线及实际应用权限；不能据此把所有 Cookie 引擎目标目录也强制写成该格式。[E3] [E4] [E6]

P0 结果记录采用版本、构建样本、认证路线、实际目录能力、冲突语义、成品请求路径、恢复缺口及补丁清单；每项标明已实证或待实现，分别指向 P1/P2/P3。凭据及敏感原始响应只留在私有证据目录。Q3 已明确采用 A 验证、B 正式交付。

## 5. 通用文件模型与公开契约

### 5.1 保留原身份语义并补充批次身份

| 身份 | 用途 | 规则 |
| --- | --- | --- |
| 请求身份 | 断线重发与原请求查回 | 沿用 Idempotency-Key；相同请求返回原结果，不重新枚举目录或建任务 |
| 批次与源项身份 | 固定一次选择得到的输入集合 | 草稿与源项 ID 稳定；受理时绑定不可变批次及清单版本，冻结文件 Task 和目录操作引用；编辑草稿不改写旧批次 |
| 业务提交身份 | 普通提交去重 | 保留作品、单元逻辑 ID、模式、展开 item_key、平台、账号的既有台账语义；P1 明确 file_set 的稳定展开键，不能与旧视频单元冲突 |
| 目录业务身份 | 目录普通提交去重 | 作品/单元、稳定目录逻辑身份、平台和账号定位目录台账；普通重复提交复用当前轮次，显式重提建立新轮次，与文件 item_key 分区 |
| Core 执行所有者 | 领取、许可和恢复的主体 | 使用带类型的 task 或 directory_operation 身份；目录有独立执行记录，不能借用文件 Task/Attempt |
| 引擎操作身份 | 本地受理和执行关联 | Core 执行所有者及其业务轮次对应稳定 operation_id，与 owner_uid、冻结输入/路径和引擎操作记录绑定；同轮次执行重试沿用原操作身份 |
| 远端文件身份 | 成功核验与恢复 | 由原操作可信响应及其账号、文件标识和证据确定；同路径同大小不等于本次成功 |

资产 ID 不使用文件内容摘要生成。可按稳定输入身份和规范化相对路径建立映射，并持久保存具体 ID；规范化和碰撞规则在 P1 固定。重复点击预览、浏览器断线和原键查回继续使用原草稿/批次身份。用户明确发起新的上传或重新提交，才按现有规则建立新的业务轮次。

`source.application`、`kind`、`external_reference` 用于追踪来源，不取代这些身份。更换远端目录或账号时应重新预览；不能修改已受理任务快照，也不能靠偷偷改变去重键绕过显式重新提交规则。

### 5.2 通用资产与 file_set 单元

现有公开模型只有 videos/covers/subtitles，单元通过 videos 展开，不能宣称已有普通文件支持。[S7] [S13]

P1 新增通用 FileAsset 和 `file_set` 单元：文件有本地源引用、稳定 ID、原始名称和目标相对路径；目录有稳定 ID、目标相对路径和依赖关系。每个文件、每个百度目标账号生成一个 Core Task；目录按 §5.7 生成 DirectoryOperation。两类清单分别表示，支持只有空目录的批次；目录项不假装成 0 字节文件，也不通过 Fake Task 制造执行身份或成功。

现有 B 站 multipart/independent 视频语义保持兼容。file_set 与旧 mode/kind 的判别方式、字段名、Schema 版本策略、目录执行记录及批次持久表在 P1 一次性固定，并从严格 DTO 导出 Schema、OpenAPI 和前端类型。逻辑职责按 §5.7 执行，旧请求规范化必须符合 §5.8；本方案不提前指定新的 Schema 版本号。

以下仅是**概念性 YAML 提案，不是完整的最终 DTO，也不能直接提交当前版本**。示例省略尚未固定的版本字段；`kind`、`files`、`directories` 等字段以 P1 决定为准。假设本地源根为 `D:/资料`：

```yaml
work:
  id: "b6344501-fcaa-4bde-9229-6a43c790ac19"
  title: "项目A备份"
  ready: true

assets:
  files:
    - id: file_notes
      path: "项目A/说明.txt"
    - id: file_video
      path: "项目A/视频/片段.mp4"
    - id: file_empty
      path: "项目A/空文件.txt"

upload_units:
  - id: baidu_backup
    kind: file_set
    files:
      - asset: file_notes
        relative_path: "项目A/说明.txt"
      - asset: file_video
        relative_path: "项目A/视频/片段.mp4"
      - asset: file_empty
        relative_path: "项目A/空文件.txt"
    directories:
      - id: dir_root
        relative_path: "项目A"
      - id: dir_videos
        relative_path: "项目A/视频"
      - id: dir_empty
        relative_path: "项目A/空目录"
    targets:
      - platform: baidu
        account: "core-baidu-account-id"
        enabled: true
        options:
          remote_directory: "/备份"
          conflict_policy: fail
```

作品标题等作为平台内组织信息。B 站专属标题、简介、标签、封面等不会自动转为百度协议参数；用户希望这些文件本身也备份时，应明确列入通用文件集合。预览不得把未选择的附件计作已上传。

### 5.3 文件夹枚举与冻结清单

手动选择或自动输入先生成规范化草稿，记录所选文件和目录树。用户选择文件夹时，默认包含顶层目录名及内部全部普通文件和目录；选择单文件时，保留该文件名放入目标父目录。

清单生成必须保留空目录，允许 0 字节普通文件，检查无权限、消失或类型变化的条目，并明确报告。默认不跟随符号链接、目录联接和其他重解析点扩大选区；遇到此类未支持条目需在预览说明并阻止未经明确排除的输入通过，不能静默越界读取。

预览绑定具体草稿/配置版本和规范化清单。受理原子保存这份清单及目标；受理后新增文件、改名或删除不触发重新枚举，不自动混入新文件。更新选择需生成新草稿版本并重新预览；原请求重放始终查回旧批次。实际执行时源文件缺失、被替换或发生协议一致性变化，按原任务错误和恢复边界处理。

目录上传是这份清单的一次性批次，不是镜像或实时同步，不自动删除网盘额外文件。引擎仅接收 Core 已冻结的逐文件上传或逐目录操作，不调用引擎 folder API 重新递归发现任务。[R4]

### 5.4 远端目录、命名与碰撞

目标父目录由用户浏览选择或输入，平台验证其属于当前账号和认证路线的可写范围；可以受控创建缺少的目录。每账号保存默认/最近目录用于下次填写，不用偏好变化修改旧任务。

| 本地输入 | 目标父目录 | 实际目标 |
| --- | --- | --- |
| 单文件 `D:/资料/说明.txt` | `/备份` | `/备份/说明.txt` |
| 目录 `D:/资料/项目A` 中的 `说明.txt` | `/备份` | `/备份/项目A/说明.txt` |
| 同目录中的 `视频/片段.mp4` | `/备份` | `/备份/项目A/视频/片段.mp4` |
| 同目录中的空目录 `空目录` | `/备份` | `/备份/项目A/空目录/`，持久目录项 |

实际允许的根和限制由 P0 确认；官方应用若仅能写其应用目录，页面只提供该范围，不伪装能写全盘。引擎路线也不能承诺任意账号目录均可写。

文件名、目录段、长度、路径分隔符和规范化必须按真实平台规则校验。禁止 `..`、绝对相对路径混用及越出选择根/目标父目录。多输入形成相同远端路径、选中父目录又选中其中同一文件、文件与目录同名冲突等，均在预览明确报错，不静默截断、覆盖、重命名或重复上传。仅名称不同但经平台规则归一后相同的情况，也必须检测。

预览展示账号、本地来源、实际网盘路径、文件/目录数量、文件字节数和未纳入条目；受理时冻结账号与路径。Work/Unit/Asset ID 只用于内部关联，不默认进入网盘名称。再次上传到已存在文件的位置按 fail 处理，必要时用户为新的提交选择另一父目录。

### 5.5 同一作品中的两类单元

三个视频需要一份 B 站多 P 稿件和三个百度文件时，使用两个稳定单元：B 站 multipart 视频单元生成一个 B 站 Task，百度 file_set 生成三个百度 Task，并按需生成目录操作。二者可引用同一批本地原件，不复制文件。

P1 明确视频视图和通用文件视图如何关联受控源引用，维持已有资产 ID 唯一约束，不在不同资产组随意复用冲突 ID。不能向旧 multipart 单元追加百度目标后在执行器里暗改粒度，也不能以支持 file_set 为由让 B 站接受任意文件。[S7] [S13]

### 5.6 公开 API 与统一提交

| 入口 | 本轮变化 |
| --- | --- |
| 手动输入草稿能力 | 在平台服务所在机器选择/引用文件和目录，生成稳定草稿及规范化清单；只是输入准备，不直接创建上传执行 |
| POST /api/v1/submissions/preview | 按草稿或现有 YAML 输入解析文件集、目录项、账号、能力和实际目标，绑定 config_version |
| POST /api/v1/submissions | 原子保存不可变批次、文件 Task 引用、DirectoryOperation 引用、目录依赖、冻结快照及提交回执；目录-only 输入不按 no_targets 拒绝 |
| GET /api/v1/submissions/result | 按原请求键返回原批次，不依赖源 YAML 或输入目录仍完整存在 |
| 现有账号及登录会话 API | 按认证路线返回扫码或官方授权挑战、账号摘要，不返回 Cookie、SecretKey 或令牌 |
| GET /api/v1/platforms | 返回已验证的普通文件、目录、授权、恢复和查询能力，不把候选能力标成已支持 |

本轮是本机 Windows 部署，“浏览本地文件”指平台服务所在机器。手动页使用受控本机文件选择/路径浏览接口读取引用，不将普通浏览器 File 对象上传成另一份服务端副本，也不擅自增加远程客户端字节上传协议。

现有 YAML 自动入口继续使用，MuMu 当前 generated 流程保持兼容；新增文件集输入与 YAML 最终进入同一规范化和提交链路。一次性定时、每日/每周调度继续沿用原去重和重试规则，不增加 Cron，也不把引擎自带定时功能接入业务链路。[S8]

### 5.7 目录执行主体、固定批次与生命周期

当前 Worker 只从 tasks 领取，Attempt 的所有权检查依赖 task_id；当前统一提交回执以 work_id、task_ids、status、config_version 为主。目录只有持久结果而没有执行主体，无法覆盖空目录批次的领取、取消和恢复。本轮明确引入下列逻辑契约，物理表及消息字段在 P1 固定。[S17] [S18] [S19]

| 对象 | 固定职责与关联 |
| --- | --- |
| Core Task | 保留已有业务身份、Task/Attempt 和历史；百度文件每账号一个 Task，B 站仍可是一份多 P 投稿 |
| DirectoryOperation | 归属稳定业务目录/目标和创建它的受理批次，关联账号、冻结路径、业务轮次、父目录依赖、当前执行记录和结果；其他批次仅可引用其明确终态，不创建伪文件 Task |
| 共同执行所有者 | 以 owner_kind=task 或 directory_operation 加 owner_id 判别；共用 Core 领取、租约、账号名额、执行代次和进程监督规则 |
| 目录执行记录 | 独立保存尝试 ID、代次、重试预算、操作意图、响应、错误和退出证据；重试追加记录，不能填入旧 Task/Attempt 外键冒充文件尝试 |
| 受理批次及回执 | 保存不可变清单版本、文件 Task/目录操作引用、依赖及本批次新建项/旧终态引用的区别；能独立于后续 Work 编辑查询、取消和汇总 |

目录生命周期应表达等待依赖、排队、运行、成功、失败、待核验、取消及定时过期；“本次新建”和“已存在且可用”是不同成功来源。P1 确定具体枚举及事件 Schema。旧 Task/Attempt 的 ID、状态、历史外键和 B 站交接后规则保持兼容，不把 B 站 Task 统一改称单文件任务。

**领取与依赖：** 首版同一百度账号至多有一个活动远端写操作，文件 Task 和 DirectoryOperation 共用该名额。父目录确认可用后才放行子目录和文件；等待父目录的项不先占账号名额，避免单名额死锁。父目录失败或待核验时，依赖项记录明确阻塞原因并进入批次汇总，不作为普通可执行项永久排队。账号停用、重新授权及维护互斥也检查目录操作。预览和受理不创建远端目录。

**去重与协调：** 同一逻辑目录、平台账号和业务轮次的普通重复提交，复用当前目录操作及结果；显式重新执行才生成新轮次。批次内相同父目录可归并；不同业务身份的目录操作即使目标路径相同，也只按账号和规范化路径协调在途 mkdir，各自保留归属与取消范围，不形成“该路径永久成功”的全局台账。后续查询发现目录被删除，只更新远端观察；普通重复发现不能自动改写原成功或重建目录。

**批次与回执：** 相同幂等键返回原受理结果；对相同已受理清单版本及冻结目标的新键普通提交，仍复用原业务项、轮次和批次，包括原批次仍在执行的情况。清单修改产生新的批次版本/身份，旧批次成员不变。首版新文件集批次跨批次只引用结果明确的旧终态；若需复用在途、排队、恢复中或待核验的 Task/目录操作，受理前明确报告受阻项并拒绝创建新批次，原单查回和原批次普通重放不受此限制。该限制针对新增文件集批次，不改写旧 B 站/MuMu 接口的既有行为。

明确终态引用只读关联历史结果，不新增执行需求。显式重提只为所选且可重提的项生成新业务轮次和新批次；未重提的成功项可保留只读引用，其他在途项不作为新批次成员。字段命名及响应版本在 P1 固定，新文件集响应至少能定位 batch_id、task_ids 与目录操作引用，并区分本批次新建项和旧终态引用；旧 B 站/MuMu 响应保持兼容，历史回执按原存储内容返回。只有目录时允许 task_ids 为空，但必须有可查询、可取消、可观察状态的批次及目录操作。

**调度与取消：** 目录操作冻结执行时间、迟到规则和重试策略，定时派发记录包含新建/复用的目录操作；没有文件 Task 也必须有派发结果。定时遇到新批次需要引用在途项时，同样记录受理阻断，不偷偷换业务键新建执行。批次取消只作用于本批次拥有的可取消执行项，阻止它们继续领取；只读引用的旧终态不写取消标记。已发出的 mkdir 先核验并保留真实结果。单文件取消不取消同批其他成员仍依赖的父目录；独立批次的 Task 和目录操作不连带取消。恢复须证明旧执行者已停止，校验当前代次及原操作证据，不能只凭租约到期再次执行。

批次状态由冻结成员的文件状态、目录状态及依赖阻塞共同计算。无文件 Task 不能被解释成未提交或自动成功，目录-only 批次也必须经过实际执行后得到明确结果。

### 5.8 旧请求规范化与幂等兼容

保留旧幂等记录之外，还必须保留旧请求的规范化语义。当前 Service 将 normalized_request 的规范化字符串与历史 request 精确比较；Manifest.normalized() 使用包含默认值的 model_dump()，并已专门省略 hide_in_space=false 以保持旧请求重放兼容。直接向旧 DTO 加入 files、directories 或 kind 默认值，可能使相同 Key、相同原 JSON 在升级后产生 409。[S13] [S18]

本轮采用分版本规范化边界：旧 Manifest 保持当前基线的字段投影、默认值及省略/null 区别；新增 file_set 使用明确的新规则。若新增规范化版本标记，应作为可追踪元数据保存，缺少标记的历史记录按已支持旧规则解释，不能把新标记或新默认字段注入旧请求比较串。新字段必须参与新契约的比较；不能通过全局丢弃默认值或忽略未知字段让不同请求被误判成同一请求。

历史 request、HTTP 状态和 response 原样保留；不得批量改写旧记录来消除冲突，也不按新版 DTO 重建历史响应。旧请求原键命中应先返回历史结果，不重新读 YAML、枚举目录或访问本地原件。

兼容验收分别覆盖 POST /api/v1/works，以及显式携带 Manifest 的 POST /api/v1/works/{id}/submit、POST /api/v1/tasks/{id}/resubmit：在旧基线建立记录、升级副本、移走原件后，用原 Key 和原 JSON 重放，返回原 HTTP 状态/响应且没有新业务项；同 Key 的实质不同输入仍拒绝。当前统一 submissions 的自动请求仅含路径/版本等信息，手动请求含 preview_id，新增 Assets 默认字段本身不会直接改变它们的请求比较串；GET /submissions/result 读取原响应，须与上述 POST 重放分开验收。[S19]

## 6. 后端结构与引擎治理

### 6.1 代码职责

### 6.2 Core 与本机引擎的边界

Core 保存业务受理、调度、Task/Attempt、DirectoryOperation/目录执行记录、重试、取消、结果和事件；自有 Rust 程序只作为 Adapter 控制的协议执行引擎。其私有持久状态可保存 uploadid、分片确认及恢复信息，但不能成为第二套独立接受用户提交的业务队列。

必须固定下列边界：

1. 引擎源码/构建版本和桥接补丁受控，私有数据放在当前部署所属目录，不混用其他实例的账号或断点。
2. 正式引擎优先沿用 B 站的受监督进程与结构化消息通道，由 Core 启动和控制。P0 若使用上游 HTTP 服务，仅监听受控本机接口并隔离访问；Dashboard 始终经平台后端调用。
3. 每次操作绑定稳定 `owner_uid`，不能依赖引擎当前界面所选账号；源引用、冻结目标及 Core 执行所有者映射必须持久一致，文件对应 Task，目录对应 DirectoryOperation。
4. Core Worker 分配执行名额并监督进程生命周期。引擎重启先恢复到受控暂停/等待状态，未经本轮执行资格检查不得自行开跑。
5. 关闭自带自动同步、定时、分享同步、加密、下载等本轮外功能；禁止利用 folder API 再次枚举并自行新增文件任务。
6. 文件上传和目录操作接受 Core 已冻结输入；引擎事件只是观察和协议证据输入，Core 根据可靠证据决定终态，不能直接照抄引擎绿色成功标签。
7. 引擎进程退出、进度 100%、HTTP 200、CLI 输出或退出码 0 均不足以单独证明远端成功。Go 备选也必须提供可关联的结构化操作与结果证据。

### 6.3 引擎操作受理必须可查回

上游原版的 HTTP 创建请求可能已被受理而响应丢失；正式自有引擎的命令交接同样存在“已执行、结果未收到”的窗口。两种通道都要按原操作查回，不得以本机调用失败为由新建上传。[R1] [R2]

最低桥接契约为：Core 先可靠保存稳定 operation_id 及不可变结构化输入摘要（非文件内容摘要）；引擎按该 ID 幂等、持久受理，并支持查回原操作记录。相同 ID 不同输入必须拒绝。持久受理与执行开始分离，待 Core 提供当前执行所有者、执行尝试及代次的许可后，才发可能造成远端效果的请求。文件使用 Task/Attempt，目录使用 DirectoryOperation/独立执行记录；执行授权、恢复和取消均校验完整所有者身份及代次，防止旧宿主继续启动或覆盖结果。

交接回复丢失后只查回原 operation_id，不能另建一份。未能证明是否受理或是否执行的孤立项要隔离并核验；不能用“本地未找到 Task ID”推断远端未发生。在自有引擎中落实受理、执行、查询和恢复契约，保留必要协议补丁及版本记录；上游原版 API 只作为探针和源码参考，不作为正式版必须长期运行的完整服务。

## 7. 账号授权与凭据路线

### 7.1 推荐路线：自有引擎承接扫码会话

Dashboard 账号页按百度能力显示扫码授权、有效期、等待、取消和错误状态。后端通过受控引擎完成挑战和会话建立，成功后取得并核验稳定 UID，可靠保存私有凭据和 Core 账号映射，才将账号标为可用。[G5] [R1]

Cookie 等登录凭据只留在私有后端或受控引擎私有存储；前端只得到扫码展示所需公开信息和账号摘要，不要求用户将 Cookie 粘贴进普通配置或聊天。

同一平台和同一远端用户标识只对应一个业务账号身份。昵称变化或重复授权不能增加另一套去重及并发名额。会话失效时阻塞需要授权的操作，提示重新扫码；重新授权必须绑定原 UID。若扫入另一账号，明确拒绝替换原账号的凭据，不把旧任务切到新网盘。

扫码/Cookie 会话不假设具备 OAuth refresh token。实际凭据换代、会话刷新和过期行为按选定引擎实现验证；任何换代都需要单一持久所有者和凭据版本条件更新，避免旧响应覆盖新会话。

### 7.2 条件路线：官方 OAuth/API

只有选择官方路线时，才配置部署者可用的 AppKey/SecretKey，核实应用准入、权限和可写目录，并按实际获准模式实现设备码或其他授权。设备码并不消除应用参数；官方 SDK 的设备码换令牌及刷新接口都使用相应参数。[E3] [E4] [E7] [E10]

access token、refresh token 的换代由后端串行化并可靠落盘。刷新回复丢失时不能无限重放旧令牌；必要时重新授权。应用身份需绑定账号会话和协议 checkpoint，更换应用不能把旧 uploadid 静默挪到新应用；正常 Secret 换代不自动改变应用身份。

官方 SDK 的刷新换代说明和实际服务端表现需在该分支 P0 验证，不将它们直接套用到扫码/Cookie 路线。

### 7.3 共同凭据边界

Cookie、SecretKey、access/refresh token 和引擎管理凭据不进入 upload.yaml、普通任务快照、公开事件、日志、Git、发布包或 iframe 消息。对外只返回账号摘要、就绪状态和重新授权原因。

没有成品疑点时，授权失效按账号阻塞和任务错误规则处理。已有可能形成成品的请求在途或回复未知时，重新授权只恢复核验能力，不能成为再上传一次的理由，也不自动重开已结束或 UNCERTAIN 任务。

账号删除/停用、引擎凭据清理及重新授权应区分处理，不能让删除一条界面记录静默抹掉未决上传的唯一证据。

## 8. 原件读取、0 字节文件与协议分片

Q2 已确认；本节规定其实现边界，所有相关实现及实测仍未执行。

1. 登记、预览和统一提交只枚举显式输入并保存引用与配置，不计算文件内容摘要。
2. 百度首次执行实际打开当前源文件，计算该路线协议必需的 MD5，保存有序分片清单、输入大小和分片规则。额外非必需摘要、整份缓存及复制必须关闭。
3. 使用有界缓冲区按片读取；不能把整个大文件装入内存或在磁盘另存完整副本。
4. 实际发送时核对将发送的同一缓冲区与清单，防止核对后重读另一个内容却沿用旧值。
5. 跨进程恢复前重新读取所选文件并比较协议分片清单；不能仅凭路径、size、mtime 放行。checkpoint 在引擎私有存储中也必须满足这一要求。
6. 源内容不一致时停止复用旧会话。已证明无成品副作用且旧执行停止时明确失败并提供重新提交；存在未决效果时保留待核验。
7. 不使用新清单加旧 uploadid，不因源变化自动生成第二份远端成品，不清理调用方原件或未知远端临时分片。
8. 0 字节文件是真实文件输入，使用实际协议允许的空文件路径创建和核验。不能因分片数为 0 而跳过任务、误报完成或在重启后丢失；摘要、会话和恢复分支须单独验证。

这些约束保证同一会话的协议输入一致，不承诺任意时刻的文件系统原子快照。调用方仍需保留可读原件；目录冻结也只冻结清单和引用，不冻结原文件字节。用户接受的 MD5 例外不扩展为 SHA-256、全盘扫描或通用内容去重。

## 9. 持久执行、恢复与取消

### 9.1 状态和证据

文件任务继续使用 Core 既有 Task 状态；准备分片、协议预创建、传输、最终合并和核验属于执行阶段。目录采用 §5.7 的独立生命周期。文件夹按不可变批次成员汇总文件状态、目录状态和依赖阻塞，不建立另一个能独立改变业务事实的引擎终态。

| 阶段 | 最低持久证据 | 允许的行为 |
| --- | --- | --- |
| 引擎受理 | 执行所有者、业务轮次、operation_id、不可变输入、引擎操作记录映射及受理状态 | 回复丢失查回原单；未获执行许可不启动 |
| 目录准备 | DirectoryOperation、执行尝试/代次、批次/账号、冻结路径、依赖、操作意图和已存在/创建结果 | 先满足父目录依赖，再领取账号名额；可信目录存在条件只用于目录，不替代文件成功证据 |
| 分片准备 | Task/Attempt、当前源引用、输入大小、完整分片清单 | 无未决成品操作时可安全停止 |
| 可能形成成品的请求 | 操作 ID、请求意图、执行许可、账号/目标和响应或未知状态 | 发出前持久授权，失联核验原操作 |
| 分片传输 | 会话 ID、已确认分片和响应证据引用 | 只重发经协议证明安全的分片请求 |
| 最终核验 | 原操作成功证据、远端标识及观察 | 提交真实回执，或保留 UNCERTAIN |

数据库事务不跨网络或长时间读盘。引擎须通过受控桥接遵守成品请求的发送许可，不能仅在 Core 开始整次上传时授权后就不再记录内部关键副作用。

### 9.2 checkpoint 位置与唯一关联

checkpoint 可保存在引擎私有持久存储，Core 不必机械复制其所有分片数据库。但 Core 必须保存严格关联、所有权和证据引用；若引擎字段不能可靠表达必需证据，则补充桥接持久记录。核心关联至少包括：

| 记录 | 最低内容 |
| --- | --- |
| 受理批次 | 固定清单/版本、稳定项 ID、文件 Task/目录操作引用、本批次拥有项与旧终态引用的区分、依赖、冻结目标及原回执；Work 编辑不改变成员 |
| 目录操作及执行记录 | 目录业务身份/轮次、批次归属、账号、冻结路径、执行时间/重试策略、当前尝试/代次、租约、意图和结果证据 |
| 引擎映射 | owner_kind/owner_id、业务轮次、operation_id、引擎操作记录、引擎版本/实例、owner_uid、冻结输入与目标绑定 |
| 上传会话 | 分片规则和完整清单、输入大小、会话 ID、checkpoint 引用及版本、阶段、所有权代次 |
| 分片确认 | 会话和序号、已确认字节、可靠响应/证据引用及时间；确认后才计入可恢复进度 |
| 成品操作 | 操作类型、Core 执行所有者/尝试/代次、无凭据请求摘要、发送许可、响应或待核验状态；文件关联 Task/Attempt，目录关联独立执行记录 |
| 文件回执 | 平台、账号、远端文件标识、实际路径、大小、核验时间和原成功操作证据 |

引擎数据不能被当作可随时丢弃的缓存。私有数据损坏或映射缺失时应报告恢复阻断，不重新创建一个看似同名的任务。文件 checkpoint 属于当前 Task 的提交轮次，安全接管时可由该 Task 的新 Attempt 使用，不跨显式重提的新 Task 自动复用。目录意图和响应属于原 DirectoryOperation/轮次，可由其新执行尝试接管，不借用文件 Attempt，也不因重启改变原 operation_id。

即时传输字节与持久已确认进度分开显示，重复引擎进度/SSE 事件不重复累计。引擎自动重试规则须受审核，不能越过 Core 的重试预算、源一致性和终态边界。

### 9.3 所有成品路径都需要覆盖

官方 SDK 将 precreate 的 `return_type=2` 作为秒传成功，高层函数随后不再调用 create；因此官方协议参考中的 precreate 也可能形成成品，不能一律视为无副作用准备动作。[E8] [E11]

这个返回码说明不直接套用到 Rust、Go 的 PCS 实现。P0 追踪实际引擎所有可能形成成品的请求，包括快速上传/预创建命中、普通上传完成、最终合并等，查明错误、返回值和重试规则并给出控制改造点。正式 P2/P3 必须落实同一约束：发送前持久记录意图并与取消竞争，取得当前所有者/代次许可后发送，保存关联原操作的可靠响应，再由 Core 确认结果。

不能继承第三方客户端对创建、合并或快速上传的自动重试而跳过该边界。可重发分片不代表可重发最终创建。

### 9.4 故障决策

| 情况 | 原任务的处理 |
| --- | --- |
| 创建引擎任务的回复丢失 | 按原 operation_id 查回持久映射；不另发新上传操作，不能用未知状态启动第二任务 |
| 尚无成品请求获准，执行失败 | 确认旧执行停止后，按错误分类安全重试或失败 |
| 分片传输断线 | 只有已证明安全的片段请求可重发，保持原会话、账号和目标 |
| Worker/引擎进程退出再启动 | 恢复 Core 所有权并排除旧执行者，校验 owner_uid/目标及原映射；文件复核源清单并授权原 Task 新 Attempt，目录接管原 DirectoryOperation 的新执行尝试 |
| 引擎发现 checkpoint 但无当前 Core 执行许可 | 保持暂停/隔离，不能自主恢复上传 |
| 会话过期 | 先查是否有成品疑点；无副作用且旧执行停止有证据时才可在原 Task 建新协议会话 |
| 任一成品请求已获许可而回复丢失 | 核验原操作；无法确定时 UNCERTAIN，不自动重投 |
| 成功证据落盘但 Core 终态事务失败 | 从原证据恢复一次成功，不再次远端写入 |
| 仅找到同路径同大小文件 | 只展示候选，不能认作原请求成功 |
| 查询未发现文件 | 不能据此单独证明从未创建，不能自动重传 |
| 源分片清单变化 | 停止旧会话复用，按副作用证据决定失败或待核验 |
| 旧代次/迟到事件写入 | 不覆盖新代次、当前进度或已确认终态 |
| 空文件或空目录在重启前处于处理中 | 空文件按文件 Task 恢复，空目录按独立所有者/代次恢复；不能因无分片或无文件 Task 而丢弃 |
| 父目录失败、待核验或被取消 | 未满足依赖的子项不得占账号名额或发送上传，记录具体阻塞；按批次处置或显式重提继续 |

可信 fs_id 的价值来自它与原成功操作的关联；从目录列表找到一个 ID 不能补上归属证据。必要时复用已有 Resolution，保留原 Attempt 及异常历史。

### 9.5 取消与目录部分完成

没有未决成品请求时可以停止准备或已明确处于纯分片传输的执行，确认对应执行者停止后才提交 CANCELLED。有成品请求在途或结果未知时先核验；已成功的事实不被取消覆盖。

目录操作按自身执行所有者保存意图和结果。mkdir 回复丢失后，在排除旧执行者、取得当前代次后，可核实原账号目标路径确为目录并继续使用；无法证明是本次新建时仅记录“已存在且可用”。这一目录条件不能外推成把同名文件当上传成功。

用户取消文件夹批次时，按 §5.7 持久取消本批次拥有且尚可取消的文件和目录项；旧终态引用只读，成功与在途未决事实不被覆盖。首版不共享跨批次在途执行项；单文件取消不取消同批其他成员仍需要的父目录，独立批次操作不连带取消。取消不删除本地原件或远端对象，文件失败不回滚其他成功文件；只有目录的批次同样支持取消、恢复和汇总。B 站原有交接后取消规则保持不变。

## 10. 冲突和远端结果

### 10.1 文件 fail，目录存在可继续

文件冲突策略固定为 fail：不覆盖、不自动改名、不把同名文件当成功。上传前列表检查用于提示，不能替代并发创建时的实际保护；快速上传和最终合并也必须遵守策略。

已存在且类型正确的目录可用于容纳后续文件；同路径却是普通文件时失败。目录操作按账号和规范化路径协调、持久记录，不能依赖多个文件任务各自无记录地创建父目录。只包含空目录的批次也要得到明确结果。

P0 若发现候选只能覆盖或自动重命名，不能通过包装文案把它说成 fail；应修补、选择另一个实现或提交具体路线调整。未经本方案修订，不隐含增加“远端暂存后移动”流程，因为移动会带来新的副作用与恢复窗口。

### 10.2 文件及目录回执

文件回执显示平台、账号、远端实际路径、文件标识、大小、结果来源及核验时间，并关联原成功操作。任务成功不能只依赖进度 100%、HTTP 200、CLI 退出 0、引擎 Completed 或列表中存在一个文件。

目录结果区分“新建完成”“已存在且可用”“失败”“待核验”，不伪称既有目录由本批创建。文件夹汇总分别显示文件成功/失败/待核验/取消数量及目录结果；部分失败只处理对应项，不重新上传已成功文件。

后续回查发现远端对象被移动或删除，新增远端观察，不倒改过去已经发生的上传成功事实。查询失败保留此前可靠观察和时间，不伪造最新核验。

### 12.3 正式交付 B：当前基线一步升级

用户于 2026-11-23 确认最终日常交付采用 B。本轮纳入从 `160a9a01…` 对应当前库到百度版本的一步升级、演练和回退，不建立全部历史版本迁移链。本次文档入库同步 DB-MIGRATION 的承接位置及本轮待实施范围，其他历史版本迁移链继续暂缓；真实数据库升级尚未执行。[S4] [S5]

当前库为 schema v4。Portable.start() 在正常初始化前调用 existing_deployment()，后者要求当前 SCHEMA_VERSION；Database.initialize() 还执行新版完整结构检查。升级引导必须先于这两个新版检查运行，不能把迁移放到正常初始化成功之后，也不能放宽检查让旧库直接启动。[S4] [S20]

正式 B 的便携入口提供专门升级引导，顺序固定为：

1. **只读识别与阶段检查。** 先读取并校验部署所属的持久迁移阶段记录，再识别原 home/settings 指定的数据库。只有迁移已完成或确认没有未完成迁移的当前新版，才交给正常严格启动；数据库已是新版但配套文件、配置或最终校验未完成时，进入受控收尾/回退，禁止业务派发。已知 v4 同时验证完整受支持结构和 deployment_id 后进入迁移；未知、缺失或损坏结构明确拒绝，不重建空库。
2. **停止旧执行。** 取得部署启动/升级互斥，停止新领单及定时派发，核实 API、Worker、引擎及在途执行已停止，保留未决结果。进程记录、锁文件、PID 和活动租约不能直接成为新版执行许可。
3. **一致备份。** 制作 SQLite 一致备份及下表所列配套文件快照，校验引用完整；不能只复制依赖 WAL 的主文件。演练已通过的方案才用于正式数据。
4. **迁移结构与数据。** 首次迁移写入前可靠保存与 deployment_id/目标版本绑定的迁移意图及阶段，再在数据库事务中按明确映射变更表、外键、CHECK、唯一约束及索引，保留原主键、业务轮次和历史关系；例如 accounts.platform 与 upload_units.mode 的旧约束需要实际变更，不能只改版本号。新版物理结构及版本在 P1 一次固定。
5. **处理文件配置。** 私有路径承接、配套引擎配置及原子替换记录在可恢复的迁移阶段中；崩溃后能判断未开始、已迁移待收尾或已完成，不能重复迁移或在半完成状态派发业务。原凭据与证据保持可追溯。
6. **严格校验后启动。** 完成配套文件/配置收尾及新版完整结构、foreign_key_check、关键记录/引用检查，再可靠标记迁移完成，进入正常 existing_deployment()/initialize() 和新版启动；保留 deployment_id、日常服务地址及 MuMu 绑定，按新代次恢复合法执行。
7. **业务与回退验收。** 验证旧任务、回执、账号、source roots、定时和事件；分别验证旧 POST 原键重放与 GET 查回。失败时恢复配套一致状态；新版已有新业务记录后，不能静默换回旧备份丢弃新增记录。

备份和路径承接清单至少包括：

| 现有位置或引用 | 承接要求 |
| --- | --- |
| 原 launcher home/settings.json | 保留实际 data 路径、deployment_id 及已有配置；程序换解压目录不能改成另一部署 |
| data/core/core.sqlite3 及 Core 私有请求/证据 | 采用一致数据库备份；原请求、响应、事件序列和证据引用可恢复 |
| data/bilibili-private | 保留账号凭据、结果证据及已有恢复资产；不把私有文件当可丢弃缓存 |
| data/engine.json 及新增平台引擎配置 | 备份配套构建与路径信息，新版启动指向固定兼容构建；程序包不包含凭据 |
| 数据库/配置引用的其他私有文件、已有百度私有状态 | 建立明确清单并保持引用完整；复验外部私有路径，不能仅备份默认 data 目录 |
| 锁、进程记录与旧活动租约 | 可保存为诊断和历史证据，不按原 PID/锁记录恢复控制权；重新核实进程与执行代次 |

原件、既有 YAML、MuMu 录制库及远端内容不属于迁移修改对象。实际便携包还须通过解压、重开、换程序目录和升级入口验收；固定依赖及引擎构建，附必要许可证。
