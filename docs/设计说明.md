# 设计说明

更新日期：2026-11-15。本文维护当前采用的架构边界及初始设计基线，承接[需求说明](需求说明.md)、[初始任务书](../依据/upload-platform-implementation-taskbook-v1.md)和用户已确认的调整。以下均为待实现设计，不是对现有代码的描述；详细字段、状态转换、参数及部署命令仍须在对应实施方案中明确和验证。

原始 rc2 资料集中在根目录“依据”中，编写相关方案时按需查阅，参考身份见[根 README](../README.md)。不能直接作为冻结契约使用，也不能借此重新引入已取消的文件内容校验或预定数据库升级迁移方案。

## D01 模块与入口边界

对应 R01、R10。采用独立的 API Server 与 Worker Runtime 运行角色，核心业务通过 Application Services 组织；CLI 可经应用入口调用服务，SDK 通过公开 REST 调用，Dashboard 只走 REST/SSE。

| 模块 | 职责与依赖边界 |
| --- | --- |
| Domain | 领域实体、状态转换及不变量；不依赖 FastAPI、SQLAlchemy、SQLite、httpx 或具体 Adapter |
| Application | 提交、查询、取消、重试及业务流程协调；各入口复用业务语义 |
| Scheduling | 定时规则计算、触发记录生成和到期分发 |
| Execution | Worker、领取、租约、进程监督、取消和恢复 |
| Adapters | 目标平台能力及协议实现；通过独立受监督的执行宿主运行，可替换 |
| Infrastructure | 数据库、文件、进程等外部能力，提供 Repository、Unit of Work 和事务支撑 |
| API / SDK / CLI / Dashboard | 各自入口和呈现，不另造一套业务规则；SDK 与 Dashboard 不直接读库 |

初始代码目录建议仍可在任务书中查阅，实际文件布局随实施方案确定。Core 不依赖旧项目或第三方上传程序；Bilibili 兼容后端如被采用，只处于 Adapter 边界内。

## D02 领域与数据约束

对应 R03—R07。Task、Schedule、ScheduleRun、Attempt 分离生命周期；Account、Asset、TaskAsset、Worker、任务及账号名额的 Lease、Receipt、DomainEvent 承载相应状态。名词含义见 [CONTEXT](../CONTEXT.md)。

- 使用稳定资源标识和带时区的 UTC 时间；初始基线采用 UUID。状态变化经统一规则处理，不允许任意覆盖。
- 一个 ScheduleRun 最多生成一个 Task，一个 Task 最多一个活动 Attempt，一个账号名额最多一个活动 Lease。
- 状态、事件和领取结果按所需原子性提交；不能先对外宣称成功再补关键持久化。
- 数据访问经 Repository 和 Unit of Work 组织，写事务保持短小。网络上传、文件复制或扫描、等待进程等耗时操作不放入数据库写事务。
- 初始持久化方向为 SQLAlchemy 2 与 SQLite WAL；数据库仅放单主机的可靠本地文件系统，不做跨主机共享。空库初始化属于后续实现范围，旧库升级策略见[待办](待办.md)。

字段、外键、CHECK、唯一索引及部分索引在对应数据库方案与实际资产中落定，并用真实临时 SQLite 验证；不把候选 SQL 或表名存在当成约束已生效。

## D03 文件引用、接收与清理

对应 R02，取舍见 [ADR 0001](adr/0001-reference-local-upload-files.md)。本地登记保存原文件引用；执行时读取当前路径，不额外复制、冻结内容或比较提交后的变化。网页接收则由平台持有接收中的文件，完整落位后才向任务提供可用素材。

网页接收的初始方向是用操作记录跟踪接收与落位，在受控目录保存未完成文件，并以适用的原子改名和持久写入机制完成落位。对应方案须说明中断和写入失败如何恢复；本地引用不走这套复制暂存过程。任何路径的接收完成都不能替代远端上传成功证据。

TaskAsset 保存素材角色与顺序。清理重新核对 Task、Attempt 和 Recovery 引用，只处理平台拥有且符合条件的文件，保留幂等恢复能力。远程 API 的素材提交不接受任意服务器绝对路径；本机受控入口的路径准入细节在实施时明确。

## D04 提交、定时与到期分发

对应 R03、R04。TaskSubmissionService 组织即时、定时、取消、重试、查询和列表。重复提交按请求标识与提交内容判断，不为此读取媒体文件；具体存储结构在方案中确定。

Schedule 带规则版本与 IANA 时区；修改规则只影响后续生成。Evaluator 计算下次触发并物化 ScheduleRun，以规范化 UTC 时刻标识一次触发。Due Dispatcher 在一个短事务内创建任务、更新触发记录、写入事件及 Outbox，防止并发生成重复任务。

错过时间、夏令时、队列公平性与重试到期规则遵循需求 R04。方案细化计算和事务边界，并用可控时间及并发持久化测试证明这些规则。

## D05 Worker、执行宿主与恢复

对应 R05、R06。Worker Registry 记录 Worker 身份、主机启动身份、进程身份、角色、心跳和状态。领取时，在同一个短事务内核对到期任务、账号与名额，创建 Attempt、取得任务及账号名额 Lease、递增执行代次令牌并写入状态与事件。

Worker Supervisor 负责启动 Adapter Execution Host、核对进程身份、收集事件、续租、取消、等待退出、判断结果并提交状态；Adapter 不自行续租。代次令牌拒绝旧执行者写入本地终态，但不能凭此断言旧进程已停止远端请求。

Lease 过期先进入待恢复检查。Recovery 结合实际进程、事件、进度记录、结果、回执和远端阶段判断后续动作；不能直接再次上传。无法确认远端结果时保留 UNCERTAIN，由明确处置流程承接，不自动重试。

先用可控 Fake Adapter 验证正常、失败、崩溃、超时、迟到/无效结果及取消等行为，再接真实平台。具体故障窗口、覆盖范围和证据写入对应方案，长期方法由[测试规范](测试/README.md)维护。

## D06 契约、事件与结果

对应 R01、R07—R09。REST 初始方向为 `/api/v1` 和 OpenAPI 3.1；平台 metadata 由相应 Adapter 契约约束。Adapter Request/Event/Result 在实际建立时明确版本和业务语义，不能原样复制候选 schema。

事件带版本和聚合内递增序号，与需要保证一致的状态及 Outbox 在同一事务持久化。发布允许至少一次投递，消费按事件标识避免重复业务效果；SSE 支持续接。日志脱敏，结果必须关联到任务、执行尝试和相应远端证据。

平台协议的具体字段、错误分类、远端查询和恢复策略由对应方案细化。凭进程退出码、结果文件存在或单个接口成功不足以提交业务成功；也不得借契约对齐恢复已取消的本地文件内容扫描。

## D07 部署、依赖与旧代码借鉴

对应 R01、R10。初始语言与工具方向可参考任务书，依赖版本、启动方式、测试命令和 Docker 配置在实际工程方案中选择和验证。本轮不生成空工程或虚构可运行入口；不配置 CI 的工程约定及仓内外文件归属见[根 README](../README.md)。

先形成本地可运行的 Server、Worker 及必要验证，再随相关范围完善 Docker 持久化、健康检查、认证、备份和恢复。宿主机路径不硬编码到产品中，默认访问和远程认证遵循 R10。

旧项目按模块借鉴，不整体复制。真正迁入时在对应实施方案中记录原始文件、版本/commit、功能、许可证、第三方来源、已有测试、迁入决定、新位置和实际验证；采用后的长期设计维护在本文。mumu 的模块职责与文档组织可以借鉴，其具体业务限制不能自动成为本项目要求。
