# 文档职责与生命周期

本文件维护文档归属、更新顺序、方案状态和归档规则。日常入口见[根 README](../README.md)，协作边界见 [AGENTS](../AGENTS.md)。按任务阅读相关正文，不把完整资料包和历史目录作为每次工作的必读清单。

## 文档入口与唯一职责

| 文档或位置 | 负责什么 | 何时维护 |
| --- | --- | --- |
| [根 README](../README.md) | 项目入口、当前可用程度、安装启动导航、文件存放约定 | 入口、运行方式或文件归属改变时 |
| [AGENTS](../AGENTS.md) | 跨任务的协作、授权、工具与数据红线 | 用户明确要求调整项目约束时 |
| [需求说明](需求说明.md) | 已确认的产品范围、业务规则和验收目标 | 确认采用后同步并标明待实现；实现状态变化时按实际结果更新 |
| [设计说明](设计说明.md) | 已确认采用的架构、模块职责、关键流程和设计边界 | 确认采用后同步；区分待实现设计与已实现行为 |
| [CONTEXT](../CONTEXT.md) | 业务术语和容易混淆的概念关系 | 概念含义变化时；不放实施步骤 |
| [待办](待办.md) | 跨任务未完事项、恢复条件、完成条件和承接位置 | 新增、转交或解决遗留事项时 |
| [方案入口](方案/README.md)及 `docs/方案/YYYYMMDD-主题.md` | 一次任务的具体改动、步骤、验收、授权与状态 | 实施前创建；执行、修改和验证时持续更新同一份方案 |
| [测试规范与设计入口](测试/README.md) | 选测、测试设计、阶段、隔离、失败处理和证据规则 | 验证要求或设计方法变化时 |
| [测试运行入口](../tests/README.md) | 已存在的测试目录、环境、夹具、命令和运行方法 | 测试实现或运行方式变化时 |
| 方案中的结果记录；确有需要时的 `docs/测试/报告/` | 实际验证结果、覆盖限制及原始证据位置 | 普通文档任务直接记在方案；独立报告的建立条件见[测试规范](测试/README.md) |
| [ADR](adr/0001-reference-local-upload-files.md)及 `docs/adr/` | 重要设计取舍的原因、代价和后继关系 | 重大取舍需要长期解释时 |
| `docs/operations/` | 部署、备份、恢复、凭据和排障的实际操作 | 对应功能和可运行入口形成时 |
| `依据/` 中的[初始任务书](../依据/upload-platform-implementation-taskbook-v1.md)和 ZIP | 建立项目和编写方案的初始输入、追溯参考；使用边界见[根 README](../README.md) | 保留参考身份，不用来管理当前需求和进度；目录只保留这两份资料 |
| [归档入口](../archive/README.md) | 已完成方案和已退出活动管理的历史文档 | 文档归档时 |

一项事实只在所属正文维护，其他位置保留必要摘要和链接。需求写“要实现什么、怎样算满足”，设计写“如何组织和约束”，方案写“这次具体改什么”，证据写“实际验证了什么”。任务书和归档不成为第二份现行正文。

旧代码迁入的来源、版本、许可证、审查和验证结果放在对应实施方案中；实际采用后需要长期维护的设计写入设计正文。不另设架构资料索引或开发过程目录，编写方案时按需要查阅“依据”中的原资料。

公开接口结构在实际契约建立后由 `schemas/` 等契约资产维护；数据库物理结构由实现及已安排的初始化/迁移资产维护。设计解释语义和不变量，不手抄字段全集。原始包中的样例尚不是这些现行资产。

先确定职责和规则，再随实际内容建立文件；不预建空的功能说明、测试报告或实施方案。正文过大时可拆分到本主题目录，同时迁移归属、保留入口并修复引用。

## 先方案，再按明确指令实施

正常顺序是：以现行需求、设计及按需查阅的初始资料为输入 → 在方案中提出本次改动 → 确认采用后同步待实现的需求和设计 → 用户明确实施指令 → 按方案实施、验证并更新实际说明 → 归档。方案只引用已有约定、没有新增需求或设计时，不重复改写长期正文。

- 开展功能、修复、重构或专项文档修订，先形成可审阅的方案；小任务可以是短方案，不要求固定篇幅。只读审查可先给结论，不能因此开始修改。
- 方案从当前需求、设计及相关初始资料推导，不能把任务书中的 Task、Batch 或 Sprint 直接当成实施指令。用户引用某批次时，先据此形成具体方案。
- “确认方案内容”和“授权开始实施”分开记录。状态改成“待实施”、用户仅认可内容、方案文件已存在，均不单独构成实施授权。用户指令不要求固定口令，须能明确对应方案或已具体说明的范围。
- 已有的有效实施授权持续覆盖同一任务的未完成范围，不逐步骤重复询问。若前文已给出具体可审阅做法，用户明确要求照此修订，可以先将该做法登记成方案再继续。
- 范围内的步骤细化、纠错和验证调整可直接更新方案；新增业务目标、改变已确认核心约定或引入明显副作用，先写清变化，取得对应明确指令后再做新增部分。无依赖的已授权工作可继续。
- 尚未确认的新需求、设计和替代方案，只保留在方案正文并标明拟议；不能因为正在编写或修改方案，就把提议写成现行要求。已确认部分仍有效时，与正在修改的提议分开标识。
- 用户确认采用后，将确认范围同步到需求、设计等所属正文，标明“已确认、待实现”并引用来源方案；只记录已确认的取舍，不把拟议 ADR 标为已接受。已有确认不因方案文字修订而要求重复确认；内容确认仍不代替产品实施指令。
- 实施并完成相应验证后，再按真实结果更新实现程度、运行入口和操作说明；失败或未验证部分如实保留。文档维护任务本身已经获准的纠错、整理和引用修复可直接进行，不新增业务决定。

## 方案内容与状态

方案放在 `docs/方案/`，文件名使用 `YYYYMMDD-主题.md`，日期为创建日期；同一任务持续修订原文件，不为每轮反馈另开一份活动方案。入口只维护导航，状态由各方案正文负责。

每份方案至少写明：创建/更新日期、当前状态、关联需求或待办、目标与不做的范围、受影响文件或模块、具体步骤、验收条件、测试范围与阶段、文档同步项、风险/未决项，以及实施授权的指令来源与覆盖范围。没有授权时明确写“尚未取得实施指令”。执行中补实际结果、证据和剩余事项。

| 状态 | 含义与处理 |
| --- | --- |
| 编写中 | 正在形成初稿，尚不可据此开始实施 |
| 待确认 | 方案已可审阅，相关范围或设计仍待确认 |
| 修改中 | 正在按反馈改方案正文；不表示代码正在修改。若已开工，写明哪些已授权工作继续、哪些暂停 |
| 待实施 | 方案内容已明确；须另有覆盖该范围的实施指令才能开工 |
| 实施中 | 已有实施指令，正在按方案修改和完成阶段验证 |
| 待验证 | 改动已落地，仍有必要验证或文档同步未完成；失败或环境阻断需写明 |
| 已完成 | 约定范围、必要验证、长期文档同步全部完成，具备归档条件 |
| 暂停 | 暂停原因和恢复条件已记录；仍保留活动方案，不当作完成 |
| 已取消 | 明确终止，记录原因及已有产物的处理 |
| 已替代 | 已由新方案承接，链接新方案并交代未完部分 |
| 已转交 | 明确将剩余工作移交到其他方案或待办；当前任务不是完整交付 |

通常按“编写中 → 待确认 → 待实施 → 实施中 → 待验证 → 已完成”推进；收到反馈可转“修改中”，验证失败需返工时回“实施中”。不强制留下瞬时状态流水，但状态必须反映当前实际情况。内容已确认且已有明确实施指令时可直接进入“实施中”，在文中保留依据。

归档是文档位置变化，不能用“已归档”代替结果状态。暂停、待验证、仍在修改的方案留在活动目录；已完成、已取消、已替代、已转交的方案按对应归档类型处理。

## 待办与归档

待办使用稳定 ID，记录性质、状态、剩余工作、完成条件、依据及承接方案；没有方案时如实说明。状态可用待确认、待实施、实施中、暂缓；暂缓写明恢复条件。待办不复制全量产品需求，也不代替实施方案或授权。

方案退出活动管理前依次完成：

1. 核实退出原因。只有范围和必要验证均满足才标“已完成”；不能为归档把失败、阻断或剩余工作写成已完成。
2. 将有效需求、设计、测试方法和操作说明同步到所属正文；将剩余工作放入明确的待办或后继方案，并注明它是否影响完成结论。余项转交不等于原范围全部完成。
3. 在方案中写明归档日期、归档类型（完成/取消/替代/转交）、结果、必要证据位置和后续去向。普通文档任务直接在方案结果中写检查范围、结果及限制，不再另拆确认索引和验证摘要；已有确需独立报告时引用它，不复制报告全文。纯文档方案完成约定文档检查即可归档，不等待不在范围内的产品开发。
4. 核对源和目标路径及目标重名情况，移动到 `archive/方案/`，不保留两份活动正文，不覆盖已有归档。修复移入文件内部链接、所有直接引用及活动/归档入口。
5. 再检查内容一致性和链接。历史记录保留当时版本与未测项，只修必要链接或追加带日期的更正，不倒填通过结果。

与某份方案相关的简短确认和讨论，直接记录在该方案中；只有无适合承接的方案或确有独立追溯价值时才保留讨论文档，结论移交后放入 `archive/讨论/`。有效 ADR 留在 `docs/adr/`；完全失效或被替代时标明状态、原因与后继关系后移入 `archive/adr/`，仍部分有效的先明确有效部分的承接。编号检查活动与归档后递增，不复用。

合并既有历史记录时，保留原日期、结果、失败记录与覆盖限制，另加本次合并日期和去向说明；检查内容承接完整后再移除原副本。历史描述不因后来规则变化而被倒改，当前变化用带日期的说明承接。

## 更新后的检查

1. 核对本次变化是否同步到拥有该事实的正文，需求、设计、方案、测试和运行说明之间是否冲突。
2. 搜索直接引用、旧路径和旧要求；新增未跟踪文件也要检查完整内容，不能只看 `git diff`。
3. 移动或归档后检查相对链接、目标存在性和实际使用的标题锚点；未来位置写作路径约定，不做失效链接。
4. 区分候选输入、现行约定、已实现功能和实际验证结果。代码偏离约定时记录问题，不能为了消除差异直接降低预期要求。
5. 分别报告内容检查和引用检查；链接有效不证明业务正确，外部证据未访问就标未核验。纯文档任务不运行产品构建、业务测试或真实平台操作。

当前使用文件工具及一次性只读检查，不为这次整理新建检查框架。必要时在对应工具实施方案中建立固定检查器及其正反例。
