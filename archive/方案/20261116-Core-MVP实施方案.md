# Core MVP 实施方案 v0.2

阅读说明：第 1—13 节保留确认时的范围、契约与测试设计；逐项确认和文档检查记录保留当时状态。2026-11-16 已收到产品实施指令，当前实施与验收结论以第 14 节及[产品实施结果](#产品实施结果)为准。

## 1. 目标

在现有 `fileUploadPlatform` 仓库内，建立以“作品包（Upload Work）”为入口的第一个可运行上传闭环：

1. 用户准备一个作品目录，其中包含作品描述文件 `upload.yaml` 和一个或多个素材文件。
2. CLI 将作品描述文件提交给本机 API；API 校验描述文件、登记其中引用的本地素材，并创建 UploadWork。
3. 一个作品可以包含多个上传单元（Upload Unit），每个单元明确声明多个视频是作为一个多 P 投稿，还是分别作为独立作品上传。
4. 每个 Upload Unit 按其模式面向每个启用目标生成一个或多个 Task；API 持久化任务并返回 Work ID / Task ID。
5. 独立 Worker Runtime 从同一台主机的 SQLite 数据库领取任务。
6. Worker 通过独立受监督的 Fake Adapter Execution Host 模拟执行。
7. 作品、任务、进度、Attempt、事件和结果均可查询，服务重启后记录仍存在。
8. CLI 作为 REST API 客户端，提供作品登记、作品查看、上传启动、任务查询和取消等操作。
9. 支持立即执行、一次性定时、每日和每周任务；周期规则保存目录，到点只为新作品生成任务，并保留调度与选材记录用于重启恢复。

本方案采用用户已确认的两个运行决策：
- API Server 与 Worker Runtime 是两个独立启动的进程，初期运行在同一台主机，共享本机 SQLite 和受控数据目录。
- CLI 是 API 客户端，统一通过 REST API 操作，不直接连接数据库，也不直接调用内部 Repository。

本方案是具体实施范围，不重新设计整个上传平台，也不接入 MuMu 录播项目。

## 2. 本次范围

### 2.1 本次实施

- 新增可运行的 Python 工程结构和配置入口。
- 最小 Domain：UploadWork、UploadUnit、Account、Asset 引用、Task、Schedule、ScheduleRun、Attempt、Event、Receipt、Resolution。
- 作品描述文件 `upload.yaml`：描述作品元数据、素材清单、上传单元及目标平台/账号。
- 本地文件引用登记：保存路径和必要文件属性；不复制、不计算 SHA-256、不额外扫描文件内容。
- 两种视频组织模式：`multipart`（多个视频组成同一个多 P 上传任务）和 `independent`（每个视频分别生成独立上传任务），由描述文件显式指定。
- SQLite 初始数据库创建及必要约束；使用短事务。
- REST API：创建、列表、详情、取消、事件查询。
- 幂等创建：同一 Idempotency-Key 与相同规范化请求返回原任务；同 Key 不同请求返回冲突。
- 立即执行、一次性定时、每日和每周规则；周期目录选材只处理新作品，持久化规则、触发记录及作品提交对应关系，覆盖并发调度和重启恢复；契约见第 4.10、6、7 节。
- 独立 API Server 与 Worker Runtime 启动入口。
- Worker 原子认领、Task Lease、Account Slot Lease、Heartbeat、Fencing Token。
- Adapter Execution Host 独立进程运行。
- Fake Adapter：模拟正常进度、成功、可重试失败、永久失败、安全取消、不确定取消、执行中崩溃和迟到/无效结果。
- 开发环境自动初始化一个 Fake Account；用户无需手动创建虚拟账号。
- 最小 CLI：通过 REST API 创建、列表、查询、取消任务。
- 对应单元、真实 SQLite 集成、进程和恢复测试。
- 更新 README 的实际安装/启动导航，以及 tests/README.md 中真实可用的测试入口。

## 3. 已确认的运行与调用模型

### 3.1 API Server

API Server 负责：
- 接收和验证 REST 请求；
- 调用 Application Services；
- 持久化任务和请求幂等记录；
- 提供任务、Attempt、事件查询；
- 接收取消请求并记录取消意图；
- 提供健康状态。

API Server 不执行耗时上传，不在 HTTP 请求期间等待 Fake Adapter 完成。

### 3.2 Worker Runtime

Worker Runtime 负责：
- 注册自身运行身份；
- 发现到期且可执行的任务；
- 在一个短事务内取得 Task Lease 和 Account Slot Lease，并创建 Attempt；
- 启动并监督 Adapter Execution Host；
- 收集事件、续租、处理取消请求；
- 验证执行结果并提交任务状态；
- 对失去心跳或异常退出的执行进行恢复判断；
- 运行周期规则计算、选材和派发循环，与上传监督分开推进，不增加第三个常驻进程。

### 3.3 CLI

CLI 的业务操作只作为 API 客户端；本地准备命令只编辑用户指定的 manifest：
- 读取本机 API 地址和请求日志目录配置；本轮不配置 Token；
- 通过 HTTP 调用公开 API；
- 显示服务端返回的 Task ID、状态和错误；
- 不直接打开 SQLite，不绕过 API 修改任务；
- 本轮不实现 CLI 直连 Application Services 的第二种模式。

### 3.4 部署边界

本轮目标环境为 Windows 本机优先。API Server 和 Worker Runtime 分别启动，使用同一个本地 SQLite 文件及受控运行目录。进程监督实现必须使用适合 Windows 的机制；不得假设 Linux cgroup、POSIX process group 或 fcntl 在 Windows 可用。

API Server 默认只绑定 loopback（127.0.0.1），本轮不设置 Token。不得监听局域网或公网地址；若未来需要远程访问，必须另行设计认证和授权。

本机业务接口只供可信本机非浏览器客户端：检查 Host 为配置的 loopback 地址与端口，拒绝 Origin（含 null）、浏览器 Fetch Metadata 和转发头；禁用 CORS，修改接口只接受 application/json，并要求 `X-Upload-Platform-Client: cli-v1`。CLI 固定使用 loopback 地址、不跟随重定向。该来源限制阻止网页直接调用本机目录接口，不是对恶意本机进程的身份认证；本轮不提供多用户隔离或反向代理模式。

Docker 不作为本轮首要验收环境。不得把宿主机绝对路径硬编码到产品代码；本机入口接收用户指定的作品目录，登记目录引用后，通过目录 ID + 作品目录内相对路径解析素材，不要求用户逐个作品另改目录配置。跨容器/跨主机文件可见性不在本轮支持范围。

## 4. 最小业务模型

作品包是用户侧主要入口；Task 仍是 Worker 实际执行的最小单位。一个 Work 可以展开成多个 UploadUnit，每个 UploadUnit 再按目标账号生成一个或多个 Task。

### 4.1 UploadWork

代表一个用户准备上传的完整作品包，是对外的主要管理对象。

至少包含：
- work_id（工具自动生成并保存在 manifest 的固定 UUID，见下文 Q5）；
- manifest_version；
- ready：准备方的可上传声明，与下方聚合 status 分开，具体语义见 Q6；
- title、description、tags 等通用作品信息；
- manifest 原始内容或规范化快照；
- source_root_id 和 manifest 相对路径；
- status、created_at、updated_at。

作品元数据与平台任务分离。创建 Task 时保存实际采用的元数据快照，后续编辑 Work 不应静默改变已经排队的 Task。

Q5 已确认采用工具自动生成的固定作品编号，身份与持久化约束遵循[设计 D03](../../docs/设计说明.md#d03-文件引用接收与清理)。本轮将 `upload.yaml` 的 `work.id` 对应到 `UploadWork.work_id`，不在每次登记或周期触发时生成另一个作品编号；路径移动或改名不作为新作品判据。Q14 确认同编号按同一作品处理，不比较投稿描述变更、不要求显式确认更新；新任务使用本次有效描述，既有任务快照和提交对应关系保持不变。

### 4.2 UploadUnit

一个 UploadWork 可以包含一个或多个 UploadUnit。每个 UploadUnit 明确描述一组视频的上传组织方式：

- `multipart`：该单元内多个视频按 order 排列，面向一个目标账号生成一个 Task；Bilibili Adapter 将其映射为一个投稿的多个 P。其他平台若不支持多文件组成一个作品，应在目标能力校验时拒绝或要求改用 independent。
- `independent`：该单元内每个视频分别生成一个 Task；每个 Task 只关联一个视频及其适用的封面/字幕/元数据。

UploadUnit 至少包含 unit_id、work_id、mode、metadata_overrides、assets 顺序和 targets。每个 target 指定 platform、account reference、enabled 和平台 options。

### 元数据继承与覆盖规则

Q13 已确认区分多 P 整组字段与分 P 字段；长期解析规则见[设计 D02](../../docs/设计说明.md#d02-领域与数据约束)。本轮实现要求：

1. **independent**：每个视频按 `Work defaults < UploadUnit overrides < Video overrides` 解析自己的标题、介绍、标签和封面。
2. **multipart**：整份投稿的标题、介绍、标签和封面仅按 `Work defaults < UploadUnit overrides` 解析；视频的 `metadata.title` 用作该视频的分 P 标题，不覆盖整组总标题。单视频介绍、标签和封面不参与多 P 整组覆盖。
3. 解析结果分别保存投稿级 metadata 与有序分 P 信息，创建 Task 时保存独立快照；后续修改 manifest 或 Work 不改变已创建 Task 的投稿内容。
4. 提交前由工具展示最终采用的信息及来源层级、字段作用范围；同一视频供不同模式复用时，明确哪些字段仅用于独立投稿，不能静默误报其在多 P 中生效。
5. 未设置的字段继承上一层；description 的 null/空字符串清空，tags 的 null/空数组清空，cover 的 null 清空；数组整体替换而非合并。title 显式 null/空白、cover 空字符串均非法。最终投稿标题必须非空；其余缺省为无简介、空标签、无封面。
6. 平台专属字段放在 target options 或平台扩展字段中，由对应 Adapter Schema 校验；平台映射不作为第四层覆盖，目标不支持的设置在生成 Task 前明确报错，不静默舍弃。

一个 UploadUnit 对一个启用的 target 生成一个或多个 Task：multipart 为一个；independent 为每个视频一个。Task 是实际执行单位，Work 是作品组织和批量管理单位。

### 4.3 Account

- 内部 UUID。
- 平台标识、外部账号标识、显示名和状态。
- 并发额度，MVP 默认每账号一个活动上传 slot。
- 不在 Task metadata 中存储 Cookie 或 Token。
- 开发环境自动初始化一个 Fake Account（例如 `fake-default`），不要求用户手动创建；真实平台账号管理留到对应 Adapter 阶段。

### 4.4 Asset

本轮的主要入口不是逐个登记文件，而是登记一个作品目录和描述文件：

1. 用户准备作品目录，例如 `D:\\Works\\LiveHighlights\\`。
2. 目录内准备 `upload.yaml`，其中声明作品名称、介绍、标签、素材相对路径、视频组织模式、目标平台和账号；`work prepare` 生成并保存编号，已有合法编号时复用；素材准备完成后用 `work ready` 保存可上传标记，生成编号本身不标记就绪。命令见第 7 节。
3. 用户执行 `upload-platform work register --manifest "D:\\Works\\LiveHighlights\\upload.yaml"`。
4. CLI 将 manifest 内容及受控的本地目录引用提交给本机 API Server，不直接写数据库。
5. API 按本机登记入口的准入规则校验请求，核对 manifest schema、所选作品目录边界、相对路径和文件基本可读性，登记目录引用并创建 UploadWork、UploadUnit、Asset 及关联记录，返回 `work_id`。
6. 用户执行 `upload-platform work show <work_id>` 检查解析结果；再执行 `upload-platform work upload <work_id>` 创建各目标任务。
7. Worker 根据 Asset 保存的作品目录引用 ID + 作品目录内相对路径读取原文件。

本地文件不复制、不计算 SHA-256、不额外扫描文件内容。执行时读取当前路径；调用方负责保持文件可用。平台不保证提交后内容未变化，也不获得删除调用方原件的权限。manifest 中的素材路径必须是相对于作品目录的安全相对路径，禁止绝对路径和 `..` 路径穿越。内部目录记录保存本机目录映射，Asset 通过目录 ID 和相对路径引用文件；本机专用登记入口与远程 API 的路径读取边界遵循[设计 D03](../../docs/设计说明.md#d03-文件引用接收与清理)。

Q2—Q6 的业务要求由[需求 R04](../../docs/需求说明.md#r04-定时与队列)维护；同编号描述按 Q14 直接采用，手动与自动按 Q15 共用提交记录。准备命令见第 7 节，周期目录契约见第 4.10 节，请求来源见第 3.4 节。不加入目录监视功能；当前实施授权见第 14 节。

本方案字段 `source_root_id` / `root_id` 均指上述已登记的作品目录引用；素材的 `relative_path` 相对于该目录，不再混用管理员总目录作为路径基准。

作品根目录须为本机绝对目录，素材只允许普通文件。拒绝 UNC/设备路径、盘符相对路径、ADS、绝对素材路径、`..` 以及经 junction/symlink 逃出作品目录的引用；API 与 Worker 共用路径解析器，打开文件时复核最终路径和可读性，不读取媒体内容来做完整性校验。任务快照固定采用的 root_id 与相对路径；Work 移动后为新位置登记新映射，不修改旧映射来重定向既有任务。路径检查不承诺冻结文件内容。

### 4.5 Task

Task 表示一个 UploadUnit 在一个目标平台/账号上的一次实际上传业务意图，至少包含：
- task_id；
- platform（本轮可为 fake）；
- account_id；
- execution_type（immediate 或 scheduled；周期触发生成 immediate Task，并另存 schedule_run 关联）；
- scheduled_at；
- 一次性定时安排的允许迟到配置，随 Task 保存，业务规则见 Q10；
- status；
- metadata；
- options；
- attempt_count / max_attempts、retry_delays_seconds、next_attempt_at：任务创建时保存配置，后续规则修改不改变既有预算；
- submission_round / previous_task_id：显式再提交的轮次与前一任务关联，区别于同一 Task 下的 Attempt；
- cancel_requested_at；
- created_at / updated_at / completed_at。

### 4.6 Attempt

每次实际执行单独创建 Attempt，记录：
- attempt_id、task_id、attempt_number；
- worker_id；
- adapter 名称、版本、协议版本；
- 状态、阶段；
- 进程执行身份；
- fencing token；
- 是否进入远端操作阶段（Fake Adapter 用于验证边界）；
- 开始、心跳、结束时间；
- 错误分类及脱敏摘要；
- checkpoint/result 引用。

### 4.7 Event 与 Receipt

- Event 记录 Task / Attempt 状态变化和执行进度，带稳定 event_id 与递增 sequence。
- Receipt 记录 Fake Adapter 的成功证据，明确标注为模拟结果，不得伪装成真实平台回执。
- Q17 的 Resolution 独立记录人工核对结论、依据及操作来源；人工确认成功生成的 Receipt 区分人工来源，Fake 场景继续标注模拟。原始异常、事件与 Attempt 终态不得覆盖，具体边界见[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)。
- 状态变化与对应 Event/Outbox 在同一事务提交。



## 4.8 作品描述文件 upload.yaml

本轮定义 manifest version 1。一个 Work 可以包含多个 UploadUnit；每个单元明确声明 `multipart` 或 `independent`。示例：

```yaml
version: 1

work:
  id: "6e4f1a80-6b25-4f30-9d0c-12b38ad78591" # 工具自动生成；此值仅为示例
  ready: true # 示例作品已准备完成；仅生成编号时不得自动置为 true
  title: "2026年11月16日直播精彩回顾"
  description: "本期直播精彩片段整理。"
  tags: ["直播", "精彩回顾"]
  cover: "main-cover"

assets:
  videos:
    - id: "part-1"
      path: "video_01.mp4"
      subtitles: ["zh"]
      metadata:
        title: "上半场" # multipart 中作为分 P 标题
    - id: "part-2"
      path: "video_02.mp4"
      metadata:
        title: "下半场" # 不覆盖整组投稿总标题
    - id: "clip-1"
      path: "clip_01.mp4"
      metadata:
        title: "高光时刻"
        description: "本场直播最精彩的片段"
        tags: ["高光", "精彩"]
  covers:
    - id: "main-cover"
      path: "cover.jpg"
  subtitles:
    - id: "zh"
      path: "subtitle.srt"
      language: "zh-CN"

upload_units:
  - id: "full-episode"
    mode: "multipart"
    videos: ["part-1", "part-2"]
    targets:
      - platform: "fake"
        account: "fake-default"
        enabled: true

  - id: "short-clips"
    mode: "independent"
    videos: ["clip-1"]
    targets:
      - platform: "fake"
        account: "fake-default"
        enabled: true
```

规则：

- `work.id` 是工具生成并持久保存的固定作品编号；重复运行工具应保留已有合法编号，不以目录改名、移动或内容变化自动换号。编号非法或无法保存时明确报错，不静默替换已有编号。
- `work.ready` 为明确的布尔值，缺省按 false 处理；准备方确认素材准备完成后，由工具可靠保存为 true。周期选材只接受已就绪的新作品，且仍须通过正常的描述文件和路径校验；不得以生成编号或文件存在自动设置该标记。就绪语义由[设计 D03](../../docs/设计说明.md#d03-文件引用接收与清理)维护。
- `assets` 声明文件；所有 path 都相对于 manifest 所在作品目录。
- `upload_units` 声明上传组织方式，不能仅凭目录中有多个视频推断。
- `multipart`：videos 数组顺序就是分 P 顺序；对每个 enabled target 创建一个 Task。
- `independent`：videos 中每个视频各创建一个 Task；对每个 enabled target 分别创建 Task。
- Work 的 title、description、tags 及封面提供默认值，UploadUnit 可提供 metadata_overrides；Video 覆盖的适用范围按[元数据继承与覆盖规则](#元数据继承与覆盖规则)区分 independent 与 multipart。
- Target 可提供平台专属 options；由 Adapter 对应的 metadata/options schema 校验。
- 目标账号使用 account 引用；MVP 自动提供 `fake-default`。
- 未被任何 UploadUnit 引用的 Asset 可以登记，但不会自动创建上传任务。
- 同一 Asset 可以被多个 UploadUnit 引用；不会因此复制文件。
- 不支持的目标能力必须在生成 Task 前报出明确错误，不得静默拆分或丢弃视频。

Schema 收口：拒绝重复 YAML 键、自定义 YAML tag、未知字段和版本，使用安全解析器；manifest 只含描述数据，不执行表达式。Unit ID、Asset ID 是作品内稳定逻辑标识（非数据库行号），各自唯一；注册或展开不得按数组位置重编号。切换 mode 或主动新增逻辑标识会改变投稿身份，工具须展示影响，普通标题修改不改变身份。Unit 内视频引用不得重复，至少一个视频；同一 Unit 的启用目标按 platform/account 唯一，账号引用解析为内部账号 ID 后参与去重。

`work.cover`、`metadata_overrides.cover`、视频 `metadata.cover` 均引用 `assets.covers[].id`，不隐式选择第一个封面。字幕仅通过视频的 `subtitles` 数组引用 `assets.subtitles[].id`，缺省为空，按所属视频绑定并保存 language；multipart 的字幕随对应分 P，independent 随对应视频，不把所有字幕自动绑定到所有视频。悬空或类型错误的引用拒绝；同一字幕可显式复用。分 P 标题取视频 metadata.title，缺省取视频文件名（不含扩展名）；最终为空则拒绝。本轮只接收已定义的视频、封面、字幕角色，其他附件留到有明确契约时扩展。

## 4.9 Work 展开规则

提交 Work 时，根据 UploadUnit 生成 Task：

| UploadUnit mode | 视频数量 | 每个 enabled target 生成的 Task 数 |
|---|---:|---:|
| multipart | N | 1 |
| independent | N | N |

每个 Task 记录 work_id、upload_unit_id、target、素材关联及元数据快照。一次 Work 提交只有一份请求幂等响应；展开项通过共享投稿记录去重，不另拼接未定义的 Task 请求 Key。投稿身份为 `(work_id, unit_logical_id, mode, item_key, platform, account_id)`，multipart 的 item_key 固定为 group，independent 为视频逻辑 ID。

Q7/Q15 已确认按实际投稿和目标账号跨规则、跨手动与自动入口去重，具体身份与原子性要求见[设计 D04](../../docs/设计说明.md#d04-提交定时与到期分发)。共享投稿记录唯一标识当前轮次；Task 历史按投稿身份和轮次区分，不能将共享唯一约束错误施加为永久只允许一个历史 Task。多 P 整组与 independent 每个视频分别保留正确粒度，不能只按 work_id 整体标为已处理，不能把 schedule_id 或入口类型放入业务去重身份。不同目标各自创建任务，描述变化按 Q14 不改变身份。普通提交返回当前任务，Q16 的显式重新上传或重新安排才可创建下一轮任务，保留全部历史。

Work 不直接代表一次上传结果。Work 的聚合状态由其 Task 状态派生，例如全部成功、部分成功、执行中、失败或存在不确定任务。

聚合只看每个投稿身份的当前轮次，历史可单独查询：没有任务为 NOT_SUBMITTED；有 UNCERTAIN 优先显示 NEEDS_ATTENTION，其次有活动/恢复/等待任务显示 IN_PROGRESS；全部成功为 SUCCEEDED，部分成功为 PARTIAL_SUCCESS，其余明确终态为 FINISHED_WITHOUT_SUCCESS，同时保留各终态数量，避免把取消或过期笼统报成上传失败。ready 不参与该聚合。

## 4.10 周期规则与目录选材

Schedule 保存 id、version、enabled、parent_directory、kind（daily/weekly）、local_time（HH:mm:ss）、timezone（IANA）、weekday（weekly 时 ISO 1—7）、max_lateness_seconds、retry_policy、next_fire_at。规则缺省时区为 Asia/Shanghai，保存后始终使用该值；迟到和重试默认值由[需求 R04](../../docs/需求说明.md#r04-定时与队列)维护。时间在数据库以 UTC 保存，禁止无时区的一次性执行时间。新建/改时/重新启用规则从操作时刻之后的首个计划点开始，不补规则创建前或停用期间的历史；已物化的旧版本触发继续处理，停用规则不自动取消既有 Task。

Worker 计算到期点时按 R04 跳过夏令时不存在的本地时刻，重复时刻选第一次。恢复发现多个错过点时只物化最近点的一轮，保存合并数量及范围，按该点核对迟到窗口；超窗记录 SKIPPED，窗口内处理恢复时的新作品。计划点、实际开始时间和下次计划更新与唯一 ScheduleRun 插入在短事务内提交，约束 `(schedule_id, version, planned_at_utc)` 唯一；版本条件失败重新读取，不能给已经停用/修改的规则补造新触发。

周期目录仅枚举父目录的直接子目录，每个子目录含自己的 upload.yaml；不递归发现作品、不推断散放视频、不自动生成编号或标记 ready。普通手动入口仍直接指定一个作品目录。按规范化目录名稳定排序；清单持久化后固定该轮候选，之后出现的作品等下次触发。未就绪记录 SKIPPED_NOT_READY，非法/缺失编号或描述、不可读目录等记录作品错误，不创建提交标记；同编号出现多次按同一身份去重，无须比较描述，按稳定顺序先处理者确定本轮新任务快照。

ScheduleRun 的派发状态为 PENDING、DISPATCHING、COMPLETED、COMPLETED_WITH_ERRORS、SKIPPED；派发完成不等于上传成功。保存规则快照、候选清单、逐作品结果和 task 关联（created/existing），查询返回关联任务的当前状态。枚举在写事务外进行，候选清单仅能由持有当前派发代次的 Worker 条件保存；清单未保存时崩溃可重新枚举，已保存后只续做未处理项。作品校验在事务外，作品登记快照、本作品新增任务、共享提交记录、run 关联、作品结果及事件同一短事务提交。个别作品错误单独记录，数据库不可用则停止剩余派发，恢复后续做。

派发所有权记录 owner/generation/expires_at，续租和每次写入都校验代次；到期后可接管，因为派发不执行远端上传。它与 Task/账号租约分开，不能凭派发接管释放上传名额。规则 PATCH 使用 expected_version；冲突返回 409，不覆盖别人修改。


## 5. 状态和执行规则

### 5.1 Task 状态

本轮实际使用：QUEUED、CLAIMED、VALIDATING、RUNNING、RETRY_WAIT、SUCCEEDED、FAILED、UNCERTAIN、CANCELLED、EXPIRED、RECOVERY_PENDING。

EXPIRED 按 Q10 承接一次性定时任务超过允许迟到窗口、尚未开始执行的结果；过期不会删除原件或自动再次上传，具体领取互斥和事件边界见[设计 D04](../../docs/设计说明.md#d04-提交定时与到期分发)。其他长期设计状态（如 PAUSED、QUARANTINED）可保留枚举设计，但不要求本轮全部提供用户操作入口。

### 5.2 Attempt 状态

本轮实际使用：CREATED、STARTING、RUNNING、RETRYABLE_FAILURE、PERMANENT_FAILURE、SUCCEEDED、UNCERTAIN、CANCELLED。

Attempt 终态不可重开；重试创建新的 Attempt。

Q17 人工处置只追加 Resolution 并按规则更新 Task，不将原 UNCERTAIN Attempt 改写为成功或失败，以保留当时实际执行结论。

### 5.3 领取与并发

- Worker 只领取 scheduled_at 已到期、状态允许执行的 Task。
- Task Lease 和 Account Slot Lease 在同一短 SQLite 事务内获取。
- 同一 Task 同时最多一个活动 Attempt。
- 同一 Account 的活动 slot 数量不超过 concurrency_limit。
- fencing token 对对应 scope/slot 单调递增。
- Heartbeat 由 Worker Supervisor 发出，不由 Adapter 自行续租。
- 旧 fencing generation 不得提交本地终态。

Task 与 slot 使用显式 occupied/released 状态；领取只选择 released 名额，不把 expires_at 过期视为释放。默认心跳 10 秒、租约 30 秒，可配置且租期必须大于心跳周期；心跳失败停止授权新动作并进入恢复。按可领取时间、创建时间、task_id 稳定 FIFO 取任务，跳过暂时无账号名额的任务以免阻塞其他账号；本轮不开放额外优先级参数。每次领取同时检查取消标记、剩余预算、scheduled_at/next_attempt_at 和首次定时过期条件。

### 5.4 进程与恢复

- Adapter Host 在独立进程中执行。
- 先持久化 STARTING / execution intent，再启动进程；启动窗口状态不明时保守恢复。
- Lease 过期只触发 RECOVERY_PENDING，不直接重排。
- 必须检查执行进程身份、退出状态、事件和结果证据。
- Q1 已确认采用自动检查和收尾；账号名额释放、进程身份核验和 UNCERTAIN 的边界遵循[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)。本轮实现须使账号领取逻辑识别恢复期间仍被占用的名额，不能只按 Lease 到期时间判断可用。
- 能证明 Adapter 未启动或远端副作用未发生时，才允许自动重试。
- 无法确认远端结果时进入 UNCERTAIN，不自动再次执行。
- 本轮 Fake Adapter 用可控场景证明本地监督和状态处理；不能据此宣称真实平台 exactly-once。

Windows 监督实施约束：每个 Attempt 使用独立命名 Job Object，先保存 execution intent（attempt_id、随机执行标识、主机启动身份、Job 名和结果位置），以 CREATE_SUSPENDED 创建宿主，加入禁止 breakaway 的 Job，再保存 PID/进程创建时间，最后恢复主线程。宿主在收到执行许可前只能完成握手，不得进入模拟远端阶段；Supervisor 先持久化许可再发送 GO。尚未记录许可且身份可信、进程树已退出时，可证明未获准远端执行；许可已记录但响应丢失按结果证据判断，不能推断未发生。创建后尚未记录进程身份的窗口若无法排除孤儿进程，保留名额并提示，不能因数据库没有 PID 就认定未启动。

恢复先以条件更新取得独立 recovery owner/generation，原 Worker 的续租/终态写入立即失效；恢复程序核验旧 Attempt 的 Job、主机启动身份及 PID/创建时间，停止已确认属于它的整个 Job，查询确认活动进程数为零并核验宿主退出。禁止只杀主 PID 或凭完成通知推断全部退出；身份不符不杀其他进程。已发生整机重启且能确认启动身份变化时，可证明旧启动期进程已不存在，仍须单独判断远端结果。旧执行结果由恢复所有者核验其原 Attempt/执行标识后采用，旧 Worker 自己不得提交；没有可靠退出证据就保留 RECOVERY_PENDING 和占用名额。相关 Windows API 依据：[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)；具体行为须在本机进程故障测试验证。

宿主 IPC 使用标准输入/输出上的版本化 NDJSON，stderr 只写脱敏日志；宿主不访问数据库。Request/Event/Result 包含 protocol_version、task_id、attempt_id、execution_id 和执行代次；Event 另带递增 host_sequence，重复消息按 Attempt/sequence 去重。拒绝错误版本、身份不符、越序终态和无效结构。Result 先可靠落位到该 Attempt 独占的仓外结果文件，再输出引用；文件存在或退出码为零都不是成功证据，仍须验证结果内容、模拟回执和进程退出。宿主退出未落库时恢复读取同一结果，不重复执行。

执行配置设有限的握手、取消等待和总执行超时（Fake 默认分别 10、10、300 秒），等待和终止均在事务外。超时先按上述身份收尾，能证明安全失败才按预算重试，否则 UNCERTAIN；无效、迟到或当前代次不匹配的结果保存异常证据，不覆盖终态。运行目录、详细日志及结果在仓外配置，禁止写凭据。

### 5.5 取消

Q18 区分未领取与执行中的取消，具体互斥和证据要求见[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)：

| 当前情况 | 取消处理与结果 |
| --- | --- |
| QUEUED，尚未领取且无活动执行 | 与 Claim 条件互斥，直接 CANCELLED，不创建 Attempt 或启动 Adapter |
| 已领取或正在执行 | 记录 cancel_requested，由 Supervisor 通知宿主并核验安全停止，API 返回真实当前状态，不先承诺 CANCELLED |
| RETRY_WAIT，前次执行已退出且结果明确，无活动 Attempt | 可取消等待并阻止下一次领取，保留前次 Attempt |
| 已取得当前有效执行的成功结果 | 满足退出及回执边界后保留 SUCCEEDED，记录取消未生效 |
| 远端结果不明或仍待恢复判断 | 不直接标为取消；安全收尾后仍不明则 UNCERTAIN，交 Q17 人工处置 |
| 已结束的任务收到迟到或重复取消请求 | 返回实际结果，保留原终态与历史；不将成功、失败或过期改成取消 |

### 5.6 不确定结果的人工处置

Q17 通过人工处置入口承接 UNCERTAIN：确认成功、确认未成功、保持不确定分别按[设计 D05](../../docs/设计说明.md#d05-worker执行宿主与恢复)处理。结果明确前不开放再提交；人工确认未成功并安全收尾后只开放 Q16 显式操作，不自动重传。所有处置及其证据与原任务历史一并可查询。

### 5.7 状态转换与重试

| 起点/条件 | Task 及 Attempt 结果 | 名额与后续动作 |
| --- | --- | --- |
| 到期 QUEUED 或 RETRY_WAIT，领取条件满足 | Task CLAIMED；创建 Attempt CREATED，attempt_count 加一 | 同事务占用 Task/账号名额，生成新代次 |
| 领取后预检、启动、收到有效运行握手 | Task VALIDATING / Attempt STARTING；获准执行后两者 RUNNING | 保持占用，按监督心跳续租 |
| 有效成功结果且执行树已退出 | Task/Attempt SUCCEEDED，保存 Receipt | 终态、回执、事件、两项名额释放同事务 |
| 明确安全可重试失败且已退出，仍有预算 | Attempt RETRYABLE_FAILURE；Task RETRY_WAIT | 释放名额，持久化 next_attempt_at 后等待 |
| 明确永久失败或安全失败已耗尽预算 | Attempt PERMANENT_FAILURE 或 RETRYABLE_FAILURE（保留实际错误类别）；Task FAILED | 释放名额，不再自动领取 |
| 取消且确认安全停止/未开始 | Task CANCELLED；若已创建 Attempt 则记 CANCELLED | 释放名额；有效成功竞争按第 5.5 节 |
| 租约失效、崩溃或退出尚待核验 | Task RECOVERY_PENDING，保留 Attempt 阶段 | 名额保留；恢复证明未启动/无远端副作用后，按安全失败和剩余预算处理 |
| 已确认退出，但远端结果无法确定 | Task/Attempt UNCERTAIN | 可释放名额供其他任务使用；本 Task 禁止自动重试，人工结论按第 5.6 节 |
| 一次性定时超窗，仍 QUEUED 且无 Attempt | Task EXPIRED，不创建 Attempt | 不占名额，显式重新安排保留旧记录 |

表中之外的转换拒绝并记录原因；原终态 Attempt 不覆盖。恢复取得有效结果时按相应成功/失败行条件提交；已有终态但完成事务重放只能返回原结论。所有完成、恢复和人工处置核验任务版本、当前 Attempt、执行或恢复所有权，不能最后写入者覆盖先前结论。

retry_policy 的 `max_attempts` 是含首次的正整数；`retry_delays_seconds` 为长度恰好 `max_attempts - 1` 的非负秒数数组（关闭自动重试用 1 和空数组）。默认值引用需求 R04，即 3 次及 [30,120]。第 n 次安全失败在确认失败时刻 T 持久化 `next_attempt_at = T + delays[n-1]`；第 1 次失败到 T+30 秒、第 2 次到 T+120 秒，第 3 次失败即 FAILED。计数以 Claim 创建 Attempt 为准，启动失败也占一次，防止无限启动循环；恢复检查不新增 Attempt、不重置预算。系统时钟通过统一时钟入口读取，到期事务再检查时间；重启不得将 RETRY_WAIT 立即排队。配置随每个新 Task 保存，显式新轮次使用新的配置，历史记录不改。

| POST | /tasks/{task_id}/resubmit | Q16：对已结束且结果明确的当前任务显式重新上传或重新安排，创建新 Task |
| POST | /tasks/{task_id}/resolve | Q17：对 UNCERTAIN 追加人工结论与证据，按规则处理 Task 状态 |
| GET | /tasks/{task_id}/attempts | 查询全部执行尝试及原始结果摘要 |
| GET | /tasks/{task_id}/resolutions | 查询人工处置及证据来源 |
| GET | /tasks/{task_id}/events | 查询任务事件 |
| GET | /tasks/{task_id}/events/stream | SSE 订阅，按 Last-Event-ID 续接 |
| POST / GET | /schedules | 创建每日/每周规则，分页查询规则 |
| GET / PATCH | /schedules/{schedule_id} | 详情或条件修改配置/启停，保留版本历史 |
| GET | /schedules/{schedule_id}/runs | 查询触发、跳过和派发摘要 |
| GET | /schedule-runs/{run_id} | 查询逐作品处理结果与新建/已有任务关联 |
| GET | /system/health | 服务健康状态 |

作品登记请求包含 manifest 版本、作品元数据、UploadUnit、素材相对路径、视频顺序和 target 配置。作品登记本身不启动上传。

提交作品时，可为本次提交指定 `immediate` 或 `scheduled`（一次性定时）执行方式；服务端按每个 UploadUnit 的 mode 和启用 target 展开 Task。每个生成的 Task 都保存独立的目标账号、素材关联、元数据快照和执行时间。请求支持 Idempotency-Key。

`POST /works` 接受 `{directory, manifest}`，directory 是本机作品根目录绝对路径；同 work.id 登记更新当前描述和位置，按 Q14 不比较历史描述，不改变既有任务。`preview` 从已登记位置读取一次当前 upload.yaml，返回规范化 manifest、目录引用、投稿展开和字段来源；CLI 随后将这份 manifest 与 directory 放进 submit/resubmit 请求，复用同一解析规则，保证显示内容与新任务快照对应。直接 API 调用若省略 manifest，服务端只读取一次当前描述并用于整个请求；已有任务返回自身快照与真实状态，不把新预览冒充已有任务内容。无须单独登记 Asset。读取当前描述属于被明确指定作品的本机操作，路径与来源按第 3.4、4.4 节限制。

API 的实际 OpenAPI 资产随实现建立并验证。错误统一 `{code,message,request_id,details}`：400 为格式错误，403 为来源限制，404 为资源不存在，409 为幂等/版本/状态冲突，422 为描述、时间、路径或能力校验错误，503 为数据库/服务暂不可用；不暴露凭据或完整内部堆栈。请求失败但写入已提交时按幂等记录恢复原成功响应，不能通过重建任务补偿丢失的响应。

`resubmit` 使用 Idempotency-Key，请求指定新的 `immediate` 或 `scheduled` 执行方式；定时时携带执行时间和适用迟到配置。它只重新提交所引用任务对应的投稿与目标，不把整个作品的其他目标自动重传。当前描述按 Q14/Q13 解析；若原投稿的单元/模式/视频/目标已被移除或改变，不能把 resubmit 偷换成另一投稿，返回明确校验错误。返回新 Task ID、原 Task ID 与提交轮次；普通提交继续返回当前轮次任务。前置状态、并发切换和历史保留遵循[设计 D04](../../docs/设计说明.md#d04-提交定时与到期分发)。

`resolve` 使用 Idempotency-Key，请求为 `{conclusion,reason,evidence_refs,expected_task_version}`，conclusion 为 succeeded/failed/uncertain，理由非空；终结结论须有可查询依据和旧执行已退出的核验记录。返回 Resolution ID 与 Task 状态，历史保留原始执行记录，明确人工来源。本轮只验证模拟证据及处置流程，不宣称自动核验真实平台证据；证据不足、旧执行未安全停止或版本已改变时拒绝覆盖。

提交与再提交请求的执行字段为 `{execution_type,scheduled_at,max_lateness_seconds,retry_policy}`：immediate 禁止传 scheduled_at，由首次成功提交事务保存执行时刻；scheduled 必须传带偏移的 RFC3339 时间，迟到配置为非负整数秒，缺省值见 R04。重试配置见第 5.7 节。响应为每个展开投稿的 task_id、submission_round、created/existing 与实际状态；整份 Work 校验或事务失败不新增半批任务。没有启用目标时拒绝上传但允许保存准备中的描述。仅周期选材要求 ready=true，手动明确提交本身是用户执行意图，仍进行完整描述和路径校验。

submit/resubmit 的 manifest.work.id 必须匹配 URL 对应 Work；不接受借该参数替换成另一作品。登记和预览不创建 Task，单个 Task 的创建只经 Work 展开或明确 resubmit，不另设绕过共同去重与文件边界的高级入口。

Schedule POST 字段见第 4.10 节；PATCH 仅修改提供的字段并要求 expected_version，每次成功修改增加 version，响应包含 next_fire_at。启停以 enabled 表达，不提供硬删除规则或历史记录的接口。每日禁止 weekday、每周必须提供 weekday；时区、当地时间、重试与迟到参数创建时校验。列表采用稳定 cursor/limit（默认 50，最大 200），响应含 items/next_cursor；Task 支持 work_id/status 过滤。事件用 task 内持久 sequence 排序，after_sequence 与 SSE Last-Event-ID 指同一已提交序号，断线续接返回严格大于游标的事件；至少一次投递，消费者按 event_id 去重，Outbox 发布失败不丢事件。health 返回 API/数据库就绪性及 Worker 最近心跳摘要；API 可达不代表 Worker 已运行。

### 6.1 请求幂等与 CLI 重放

除只读 preview 外，所有 POST/PATCH 修改请求必须携带 UUID Idempotency-Key。唯一范围为 method + 路由模板 + 资源 ID + Key；保存规范化请求正文、HTTP 状态及业务响应，与该次状态修改在同一事务提交。规范化固定对象键顺序、保留数组顺序、填补 schema 默认值、将时间统一为 UTC，使用确定性的 JSON 表示直接比较，不计算请求或媒体内容摘要。immediate 的服务端实际执行时间、资源生成 ID 不进入规范化输入；请求中的本地路径只做词法规范化，不能为判断重放先访问文件。

处理顺序：来源与结构校验 → 规范化 → 查已提交 Key；存在且正文相同则返回原响应（即使任务后来终结、manifest 已修改或文件已移走），不同则 409。Key 不存在才读取必要当前数据、校验业务并进入事务；事务内再次核验 Key、当前状态及唯一约束，提交完整响应。并发插入冲突后读取获胜记录，不留孤立占位；回滚时不保留成功 Key，校验失败/服务不可用不缓存成已完成业务。当前版本保留 Key 随业务历史，不自动过期删除。

幂等响应表示原操作的确认，不保证携带最新任务状态；CLI 重放成功后再 GET 当前 Task 并分别显示原操作结果与当前状态。取消同 Key 重放可能仍是“意图已记录”，不得据此覆盖随后成功/取消/不确定的真实结果；新的取消请求按第 5.5 节返回当前结论。

CLI 在任何网络发送前，将生成的 Key、完整请求正文、目标路由和操作类型可靠保存到配置的仓外请求日志，保存失败不发送。响应丢失或断线保留 pending，显示 request_id；`request resume <request-id>` 用原 Key 和原正文重发，不重新读取 manifest，也不生成新 Key。恢复成功后保存原业务响应；服务不可达不退回直接写库。同一次命令内重试复用 Key，新的普通 work upload 仍受共享投稿去重保护，显式再提交另受旧任务/current_task 条件约束。日志不保存凭据，路径与保留方式在实际配置入口说明。

## 7. CLI 契约

CLI 通过 REST API 工作，最小命令：

- `upload-platform server`：启动 API Server（可由部署命令启动）。
- `upload-platform worker`：启动 Worker Runtime。
- `upload-platform work prepare --dir <directory>`：在已有 upload.yaml 中为缺失的 work.id 生成 UUID 并可靠保存，复用合法编号；缺失文件时生成 ready=false 的最小待编辑模板。保留用户已有字段，拒绝非法编号/重复键；不推断视频组织方式，不自动标记 ready。
- `upload-platform work ready --dir <directory>`：准备方明确声明准备完成，校验描述及基本路径后原子保存 ready=true；不能通过扫描媒体推断准备状态。保存失败不得向 API 继续提交。
- `upload-platform work register --manifest <path>`：登记作品描述文件和其中引用的本地素材，返回 Work ID。
- `work register --dir <directory>` 为等价入口，manifest 固定为该目录 upload.yaml；登记前复用 prepare 的编号持久化逻辑，缺少必需描述则报错。准备工具并发写入使用同目录独占锁及临时文件替换，失败保留原文件；不覆盖无法确认是否属于当前写入的锁或临时文件。
- `upload-platform work preview <work-id>`：显示最终投稿与分 P 信息、字段来源及目标能力错误；upload/reupload/reschedule 同样先展示将提交的同一描述，既有任务明确标为已有，不额外要求逐次确认描述变更。
- `upload-platform work show <work-id>`：查看作品元数据、素材、UploadUnit 和 targets。
- `upload-platform work upload <work-id>`：立即按描述文件创建各目标 Task。
- `upload-platform work upload <work-id> --at <RFC3339>`：按指定时间创建一次性定时任务。
- `upload-platform work status <work-id>`：查看作品下各目标、各视频任务的状态。
- `upload-platform task list`：查询任务列表。
- `upload-platform task status <task-id>`：查询单个任务。
- `upload-platform task cancel <task-id>`：请求取消单个任务。
- 取消命令必须区分“取消请求已记录”“已取消”“已成功，取消未生效”“结果不确定”等实际结果，不将 HTTP 成功等同于取消成功。
- `upload-platform task reupload <task-id>`：显式立即重新上传，调用 resubmit，返回新 Task ID。
- `upload-platform task reschedule <task-id> --at <RFC3339>`：显式重新安排已结束且结果明确的任务，调用 resubmit，保留原任务；支持本次迟到配置。
- `upload-platform task resolve <task-id> --conclusion <succeeded|failed|uncertain> --reason <text> --evidence <reference>`：查询当前版本后提交处置，evidence 可重复；查询历史包含原始 Attempt、事件和 Resolution，不通过直接改库处置。
- `upload-platform task events <task-id> [--follow]`：分页历史或 SSE 续接，重连保留最后序号。
- `upload-platform schedule create --dir <parent> --kind <daily|weekly> --time <HH:mm:ss> [--weekday <1-7>] [--timezone <IANA>]`：创建周期规则；允许 `--max-lateness-seconds`、`--max-attempts`、`--retry-delays-seconds` 覆盖默认配置。
- `upload-platform schedule list/show/update/enable/disable`：分别查询或调用条件 PATCH；除 list 外指定 schedule-id，update 使用与 create 相同的配置选项，先读取版本，409 时报告冲突而不静默覆盖。
- `upload-platform schedule runs <schedule-id>`、`upload-platform schedule run <run-id>`：查看触发、逐作品错误和关联任务。
- `upload-platform request resume <request-id>`：重放已持久保存的未确认请求。
- `upload-platform doctor`：检查 API 可达性、数据库健康和配置。

CLI 不直接读写数据库。API 地址、运行目录和请求日志目录通过明确配置文件或环境变量提供，本轮不设认证配置。server/worker 是运行角色启动命令；本地 prepare/ready 是描述文件工具，不构成 CLI 直连业务数据库。普通业务查询/修改始终走 REST。

upload/reupload/reschedule 同样支持迟到与重试配置，字段约束与 API 共用；迟到配置只用于 scheduled。命令退出码区分成功、校验/状态冲突、服务不可达；`--json` 输出服务端结构，文本输出保留请求标识、Task ID 和实际状态。“创建成功”“取消意图已记录”“上传成功”不可混为一谈。

## 8. 数据库与事务

本轮只实现空库初始化，不做历史库升级迁移体系。实际 schema 以实现代码和初始化 SQL/metadata 为准，并在测试中验证。

启动时仅对不存在的数据库或无用户表的空库建立当前 schema、版本标识及唯一的 system-managed Fake Account；并发初始化串行化，成功后再对外 ready。重复启动只核验受支持版本和必要约束，不重建表、不清空数据、不重复创建账号；无版本但有用户表、版本不支持或结构异常时明确停止并保留原库，不将旧库当空库覆盖。数据库路径和运行目录由配置指定，不默认为用户已有业务库。

至少实现以下关系：
- `upload_works`：作品元数据、manifest 版本和规范化 manifest 快照。
- `upload_units`：作品内的上传单元，保存 `multipart` / `independent` 模式、覆盖元数据和顺序。
- `assets`：本地文件引用，保存 root_id、relative_path、文件名及登记时必要属性。
- `source_roots`：不可变的本机目录映射；Work 当前引用可以改变，既有 TaskAsset 的映射不变。
- `upload_unit_assets`：上传单元与素材的关联，保存角色和顺序。
- `upload_targets`：上传单元的目标平台、账号引用、启用状态和平台 options。
- `tasks`：实际上传执行任务，关联 work_id、upload_unit_id、target_id 和独立元数据快照。
- 共享投稿记录保存当前轮次及 current_task_id；Task 保存轮次和 previous_task_id，允许同一投稿存在多个显式提交的历史任务，但普通提交不增加轮次。
- `task_assets`：每个实际 Task 使用的素材及其顺序。
- `schedules`、`schedule_runs`、触发任务关联及作品提交对应关系：保存每日、每周规则与选材记录，按 Q11 支持一轮关联多个任务，并区分新建和去重后关联已有任务。
- `attempts`、`leases`、`events`、`outbox_events`、`receipts`、`idempotency_keys`：执行、所有权、事件和结果记录。
- `resolutions`：追加式人工处置记录，关联 Task、原 Attempt 和依据，不替换原执行状态或异常记录。

必须覆盖：
- FK / UNIQUE / CHECK；
- 一次性定时任务直接保存 `scheduled_at`、Q10 迟到配置和到期领取条件，不另建周期 Schedule/ScheduleRun；
- 每日、每周规则的版本、时区、触发记录持久性及并发去重；按 Q11 约束同一规则版本、同一触发点的 ScheduleRun 唯一，按 Q7/Q15/Q16 约束投稿共享记录唯一、同一投稿同一轮次 Task 唯一，不能限制所有历史轮次只能有一个 Task，也不能将 schedule_run_id 在关联中误设为单任务唯一；
- 一个 Task 一个活动 Attempt；
- 一个账号 slot 一个活动 Lease；
- Idempotency-Key 冲突；
- Task/Attempt/Event/Receipt 的一致性。

活动 Attempt 部分唯一索引覆盖 CREATED/STARTING/RUNNING；任务进入恢复仍保留其活动 Attempt，直到有合法终结结论。占用名额按 released_at IS NULL 唯一约束，不能按当前时刻建立“已过期就不占用”的索引。submission ledger 按第 4.9 节身份唯一，Task 按 ledger_id/submission_round 唯一；current_task_id、前序关联和 TaskAsset 使用外键，禁止更新 Work 描述时级联删除历史关联。事件按聚合/sequence 唯一，Receipt 按 Task 的终结结论去重；状态 CHECK、非负计数及 Attempt 的 task_id/attempt_number 唯一共同验证。

事务边界：
- 登记 Work：幂等记录、UploadWork、UploadUnit、Asset 引用、UploadUnitAsset、UploadTarget、Event/Outbox 同一事务；提交 Work：当前描述快照、幂等响应、展开后的 Task、TaskAsset、共享投稿记录及 Event/Outbox 同一事务。
- 显式再提交：新 Task、TaskAsset、轮次及前序关联、共享记录当前指针、幂等响应与 Event/Outbox 同一短事务；条件核验当前任务及其终态，失败不改变原任务或当前轮次。
- 周期派发：Q11 一轮多任务、Q12 按作品隔离；单个作品本次应新增的 Task、TaskAsset、触发任务关联、提交对应关系及 Event/Outbox 同一短事务，失败时仅回滚该作品本次写入。目录枚举与作品校验在写事务外完成；作品错误单独保存到该轮处理记录，不产生虚假上传任务或已提交标记。具体失败及共享环境边界遵循[设计 D04](../../docs/设计说明.md#d04-提交定时与到期分发)。
- Claim：Task、Attempt、Task Lease、Account Slot Lease、fencing counter、状态事件同一事务。
- 取消：记录意图或未领取任务的直接 CANCELLED 与 Event/Outbox 同一短事务，条件核验与 Claim、终态提交互斥；执行中停止进程在事务外完成，最终结论按有效证据条件提交。
- Heartbeat：短条件更新。
- 进度事件：Event/Outbox 短事务。
- 完成：先在事务外验证 Adapter 结果与进程退出，再在事务内写 Receipt、Attempt/Task 结论、重试到期时间（如适用）、两项名额释放及 Event/Outbox；恢复和取消同样不能分开释放名额与提交结论。
- 人工处置：先核验当前状态、依据与适用的退出条件，再在短事务内条件更新 Task，追加 Resolution、必要 Receipt、幂等响应及 Event/Outbox；不更新原 Attempt 终态。
- 任何网络、文件复制、文件内容扫描、进程等待不得在数据库写事务中执行。

SQLite 使用 WAL、foreign_keys、synchronous=FULL 和有限 busy timeout，数据库位于本机可靠文件系统。

foreign_keys、同步和忙等待配置逐连接设置并验证，busy 超时作为暂时不可用返回，不伪造成功。占用权、当前指针、版本和状态以条件更新/唯一约束处理竞争；不依赖“先查后写”在事务外保证唯一。

## 10. 验收标准

### 功能闭环
1. 通过 CLI 登记一个包含多个素材的作品 manifest，API 返回唯一 Work ID。
2. 数据库中存在 Work、UploadUnit、Asset、Task 及其关联；多 P 与 independent 两种展开规则正确。
3. 独立 Worker 领取任务并创建 Attempt。
4. Fake Adapter 产生可查询的阶段和进度事件。
5. 成功时 Task 为 SUCCEEDED，存在标明 fake 的 Receipt。
6. 失败时按分类进入 FAILED / RETRY_WAIT / UNCERTAIN，不混淆。
7. CLI 可查询 Work 状态，并查看其下各 Task 的状态和历史。
8. 通过 CLI/API 创建、修改、启停及查询每日和每周规则；保存指定目录与时间安排，到点只为新作品生成任务，规则、触发及任务关系可查询，按第 6、7 节验收。

### 持久化与幂等
1. API Server 重启后 Task 仍存在。
2. Worker 重启后未执行任务仍可领取。
3. 相同 Idempotency-Key + 相同请求不重复创建。
4. 相同 Key + 不同请求返回冲突。
5. 状态、Attempt、事件和结果在事务失败时不留下半提交。
6. 规则、触发与作品提交对应关系重启后仍存在；并发派发和下一周期不会重复创建同一批任务。错过时间按第 4.10 节处理，重试按第 5.7 节到期领取。

### 并发与恢复
1. 多 Worker 竞争不重复领取同一 Task。
2. 账号并发额度生效。
3. 旧 fencing token 无法提交终态。
4. Worker/Adapter Host 崩溃不导致盲目重试。
5. 远端阶段不明的场景进入 UNCERTAIN。
6. 取消请求与最终取消结果区分。

### 文件边界
1. 本地文件不产生平台副本。
2. 不计算 SHA-256、不做额外内容扫描。
3. 文件不存在或不可读时返回明确错误。
4. 平台不删除调用方原件。

### 工程与验证
1. Windows 本机可以分别启动 API Server 和 Worker Runtime。
2. CLI 通过 REST 操作，不直接访问数据库。
3. 本地检查、单元测试、真实 SQLite 集成测试和进程故障测试按测试规范执行。
4. 测试结果区分通过、失败、跳过、未执行和环境阻断。
5. 更新实际运行文档；不配置 CI，不实施历史数据库升级迁移。
